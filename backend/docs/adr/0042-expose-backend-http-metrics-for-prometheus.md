# 0042. 백엔드 HTTP 메트릭을 Prometheus 형식으로 노출한다

- 날짜: 2026-09-29
- 관련 이슈: [#408](https://github.com/woowacourse-teams/2026-ChongChong/issues/408)
- 관련 ADR: [0041. 백엔드 구조화 로그를 CloudWatch Logs로 수집한다](0041-collect-structured-backend-logs-with-cloudwatch.md)

## 배경

ADR-0041에 따라 백엔드의 요청과 Web Push 전달 결과는 구조화 로그로 남기고 CloudWatch Logs에서 검색한다. 로그는 개별
요청의 원인을 추적하는 데 유용하지만, 일정 시간 동안의 요청 수, 5xx 오류 비율과 응답 시간 추세를 지속적으로 비교할
시계열 메트릭은 아직 없다. 대시보드와 알림을 맡은 팀원이 공통 지표를 사용할 수 있도록 백엔드에서 수집 가능한 형식과
지표의 의미를 정해야 한다.

현재 백엔드에는 Spring Boot Actuator가 있지만 Prometheus registry는 없다. `/actuator/health`는 Nginx를 통해 공개
접근할 수 있으나, 백엔드의 다른 Actuator 엔드포인트는 공개 프록시와 익명 허용 목록에 포함되지 않는다. 배포 대상에는
자원이 작은 단일 EC2가 포함되고, 개발·운영 환경의 계정과 사설 네트워크 연결도 확인되지 않았다.

## 결정

Spring Boot Actuator와 Micrometer의 Prometheus registry를 사용하여 백엔드 HTTP 요청 메트릭을
`/actuator/prometheus`에서 노출한다. 애플리케이션은 메트릭을 생성·노출하고, Prometheus 호환 수집기가 이를
주기적으로 읽어 저장한다. 기존 CloudWatch Logs 수집 경로와 요청 로그 형식은 유지한다.

- `http.server.requests`의 완료된 요청을 기준으로 요청 수와 응답 시간을 측정한다. 5xx 오류율은 같은 측정 집합의
  `status=5xx` 요청 수를 전체 요청 수로 나누어 계산한다. 4xx는 별도 조회할 수 있지만 서버 오류율의 분자에는 넣지
  않는다.
- 응답 시간의 환경·경로 간 p95를 계산할 수 있도록 HTTP 요청 시간의 Prometheus 히스토그램 버킷을 활성화한다.
  버킷 범위와 개수는 실제 노출되는 시계열 수와 요청 시간 분포를 확인하며 조정한다.
- 환경은 `dev`와 `prod`로 구분한다. Prometheus target에는 환경을 나타내는 고정 라벨을 설정하고, 같은 환경의
  애플리케이션 메트릭을 혼동하지 않도록 서비스 이름을 함께 사용한다.
- 메트릭 라벨에는 HTTP 메서드, 경로 패턴, 상태 코드처럼 값의 종류가 제한된 정보만 사용한다. 사용자 ID, 이메일,
  토큰, `request_id`, 원본 요청 URI와 같은 요청별 값은 라벨에 넣지 않는다.
- 서비스 요청량·오류율·응답 시간 계산에서 `/actuator/health`와 `/actuator/prometheus` 요청은 제외한다. 기본
  계측은 유지하고 대시보드·알림에 공유할 PromQL에서 Actuator 경로 패턴을 일관되게 제외한다.
- `/actuator/prometheus`는 수집기에 필요한 읽기 접근만 허용한다. Nginx의 공개 80/443 프록시 경로에 추가하지
  않으며, 수집기의 접근은 사설 네트워크 또는 동등한 접근 제한을 통해 제공한다. 기존 `/actuator/health` 공개 경로와
  다른 Actuator 엔드포인트의 접근 범위를 넓히지 않는다.
- 실제 요청 전후의 counter 증가, 통제된 5xx 요청의 오류율 반영, 응답 시간 버킷과 p95 계산, 환경 구분 및 외부
  접근 차단을 완료 검증에 포함한다.

Prometheus 서버 또는 관리형 저장소의 **운영 위치는 이 ADR에서 결정하지 않는다**. 현재 EC2의 자원과 환경별
네트워크 조건을 확인한 뒤 별도 ADR로 수집기 배치, 연결 경로, 수집 간격, 보존 기간, 데이터 접근 권한과 운영 비용을
정한다. 로컬 계측은 먼저 개발할 수 있지만, dev·prod 수집기 배포는 이 후속 결정 전에는 완료로 간주하지 않는다.

## 선택 이유

Actuator는 현재 배포 검증에 이미 사용 중이고, Micrometer는 Spring MVC 요청의 개수와 소요 시간을 계측할 수 있다.
Prometheus registry를 추가하면 애플리케이션에서 저장소 전송 로직이나 자체 집계 코드를 작성하지 않고 표준 수집
형식으로 지표를 제공할 수 있다. 같은 요청의 상세 원인은 CloudWatch 로그에서, 전체 추세는 메트릭에서 확인한다.

경로 패턴과 제한된 상태 코드로 집계하면 사용자별 값을 저장하지 않으면서 경로별 이상 징후를 볼 수 있다. 히스토그램
버킷은 여러 경로 또는 인스턴스의 응답 시간을 Prometheus에서 합쳐 분위수를 계산할 수 있게 한다. 수집기와 저장소의
위치는 애플리케이션 계측과 독립적인 운영 결정으로 남겨, 작은 EC2에 추가 프로세스를 넣거나 환경 사이에 공개 경로를
만드는 결정을 사전 검증 없이 고정하지 않는다.

## 검토한 대안

### CloudWatch 로그만으로 요청 수와 지연 시간을 집계한다

이미 남기는 `status`와 `duration_ms` 필드를 활용할 수 있다. 그러나 요청 로그 조회 결과와 장기 시계열 메트릭의
수집·보존·알림 요구는 다르며, 이번 이슈의 Prometheus 기반 메트릭 수집 완료 기준도 충족하지 못한다.

### 요청 필터에서 별도 카운터와 타이머를 구현한다

ADR-0041의 요청 필터에는 상태 코드와 소요 시간이 이미 있다. 그러나 직접 계측하면 Spring MVC의 기본 계측과 중복되고
메트릭 이름, 라벨, 버킷과 예외 경로를 별도로 유지해야 한다. 기본 계측을 먼저 사용하고, 누락된 업무 지표가 확인될
때만 별도 메트릭을 추가한다.

### Prometheus 엔드포인트를 공개 Nginx 경로로 제공한다

외부 수집기에서 접근하기 쉽다. 하지만 운영 메트릭과 내부 경로 정보가 공개될 수 있고 현재의 접근 경계를 넓힌다.
수집기의 위치와 사설 연결을 결정한 뒤 그 경로로만 접근하게 한다.

## 영향

### 긍정적 영향

- 요청 수, 서버 오류율과 응답 시간 추세를 PromQL로 조회할 수 있는 표준 메트릭 출력을 제공한다.
- 로그 수집과 메트릭 수집이 독립적으로 동작하면서 시간대와 경로를 기준으로 함께 조사할 수 있다.
- 대시보드·알림 담당자가 같은 지표 정의와 환경 라벨을 사용할 수 있다.

### 부정적 영향과 위험

- 히스토그램 버킷과 경로·상태 라벨의 조합이 시계열 수와 수집·저장 비용을 늘린다.
- 메트릭 출력만으로는 수집·저장이 이루어지지 않는다. 수집기와 접근 경로에 대한 후속 ADR 및 운영 구성이 필요하다.
- 보안 규칙이나 네트워크를 잘못 설정하면 수집이 실패하거나 운영 메트릭이 외부에 노출될 수 있다.
- 애플리케이션 재시작 시 프로세스 내부 counter가 초기화되므로, 대시보드에서는 누적값 자체가 아닌 시간당 증가율로
  해석해야 한다.

## 미확정 사항

- dev·prod별 Prometheus 수집기와 저장소의 위치, 계정·VPC 간 연결 방식, 운영 주체.
- 수집 간격·보존 기간·디스크 한도·백업 및 예상 비용.
- 실제 요청 시간 분포에 맞춘 히스토그램 버킷 경계와 과도한 시계열 수의 허용 범위.
- Grafana 데이터 소스와 알림 조건·수신 채널. 이는 대시보드·알림 담당 작업에서 정한다.

## 후속 작업

- `micrometer-registry-prometheus`를 추가하고 필요한 Actuator 웹 노출과 접근 제어를 설정한다.
- 로컬 요청·오류 시나리오로 실제 메트릭 이름, 라벨, counter와 히스토그램 출력을 검증한다.
- dev·prod의 EC2 자원·네트워크·계정 상태를 조사하고, 수집기 배치와 보존 정책을 별도 ADR로 결정한다.
- 결정한 사설 경로로 Prometheus를 연결하고 두 환경의 target과 실제 요청 반영을 확인한다.
- 메트릭 이름·라벨·PromQL·저트래픽 시 해석 방법을 대시보드·알림 담당자에게 전달한다.
