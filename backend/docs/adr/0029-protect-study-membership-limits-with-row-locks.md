# 0029. 스터디 멤버십 상한을 행 잠금과 트랜잭션으로 보호한다

- 날짜: 2026-09-08
- 관련 이슈: [#284](https://github.com/woowacourse-teams/2026-ChongChong/issues/284)
- 관련 ADR: [0003. 백엔드 테스트 범위와 역할을 정의한다](0003-define-backend-test-strategy.md),
  [0022. 스터디 멤버 제거 시 종속 데이터를 명시적으로 삭제한다](0022-explicitly-delete-study-member-dependencies.md),
  [0024. 하드 삭제 시 데이터베이스 외래 키 CASCADE로 종속 데이터를 삭제한다](0024-use-database-cascades-for-hard-delete.md)

## 배경

스터디에는 멤버 수 30개 상한이 있고, 사용자 한 명이 현재 참여할 수 있는 스터디 수에는 50개 상한이 있다.
기존 구현은 현재 `StudyMember` 수를 조회한 뒤 새로운 `StudyMember`를 저장하는 방식이었다. 두 Transaction이 같은
개수를 읽으면 다음과 같은 경쟁 조건이 발생할 수 있다.

- 스터디에 29명이 있을 때 두 가입 요청이 모두 29명을 읽고 저장하면 정원이 31명이 될 수 있다.
- 사용자가 49개 스터디에 참여 중일 때 두 스터디 생성 또는 초대 수락 요청이 모두 49개를 읽고 저장하면 51개가 될 수 있다.

`StudyMember`의 `(study_id, user_id)` 유일 제약은 같은 스터디의 중복 멤버십만 막는다. 정원과 사용자별 스터디 수의
상한은 보호하지 않으며, 중복 가입 경쟁에서 애플리케이션의 도메인 오류 대신 데이터베이스 예외가 노출될 수도 있다.

현재 모델에서 `StudyMember`는 현재 참여 중인 멤버십을 나타낸다. 탈퇴와 방출은 멤버십을 Hard Delete하고, 초대 대기
상태는 별도 데이터로 저장하지 않으며 초대 수락 시점에 멤버십을 생성한다.

## 결정

### 상한에 포함하는 멤버십

- 사용자별 50개 상한은 해당 사용자의 현재 `StudyMember` 행만 센다.
- 리더 멤버십과 일반 멤버십을 모두 포함한다.
- 탈퇴·방출로 삭제된 멤버십은 포함하지 않는다.
- 초대 대기 멤버십은 존재하지 않으므로 포함하지 않는다.
- 초대 수락 시점에 사용자별 50개 상한을 다시 확인한 뒤 멤버십을 생성한다.
- 현재 멤버십을 생성하는 스터디 생성과 초대 수락 경로 모두 같은 사용자별 상한 정책을 적용한다.

### Transaction 경계와 행 잠금

스터디 정원과 사용자별 스터디 수를 조회하고 멤버십을 생성하는 작업은 하나의 쓰기 Transaction 안에서 수행한다.

- `StudyService.createStudy`는 Transaction 안에서 사용자의 행을 `PESSIMISTIC_WRITE`로 잠근다. 잠금을 획득한 뒤
  사용자의 현재 `StudyMember` 수를 확인하고, `Study`와 리더 `StudyMember`를 같은 Transaction에서 저장한다.
- `StudyMemberService.join`은 먼저 사용자의 행을 `PESSIMISTIC_WRITE`로 잠근다. 사용자별 상한을 확인하고 초대 토큰을
  검증한 뒤 대상 `Study` 행을 `PESSIMISTIC_WRITE`로 잠근다. 이후 중복 가입과 스터디 정원을 확인하고 멤버십을 저장한다.
- `User` 행 잠금은 같은 사용자의 스터디 생성과 초대 수락을 직렬화해 사용자별 50개 상한을 보호한다.
- `Study` 행 잠금은 서로 다른 사용자가 같은 스터디에 동시에 가입하는 요청을 직렬화해 30명 정원을 보호한다.
- 잠금은 테이블 전체가 아니라 대상 행에 적용되고, 해당 Transaction이 끝날 때 해제된다. 잠금을 기다리는 다른 요청은
  대상 행에 대한 Transaction이 끝난 뒤 최신 membership 수를 다시 확인한다.
- 초대 수락의 잠금 순서는 `User` 후 `Study`로 통일한다. 이후 같은 경로에 잠금 대상을 추가할 때도 잠금 순서를 검토한다.

중복 가입에 대한 `(study_id, user_id)` 유일 제약은 데이터베이스의 마지막 무결성 방어선으로 유지한다. 애플리케이션은
행 잠금 후 중복 여부를 확인하여 정상적인 중복 수락 요청을 `ALREADY_JOINED_STUDY` 도메인 오류로 처리한다.

### 동시성 검증

동시성 테스트는 실제 PostgreSQL의 Transaction 및 행 잠금 동작을 검증해야 한다. 최종 테스트 환경은 Testcontainers로
PostgreSQL 컨테이너를 실행하고 Spring datasource 속성을 컨테이너에 연결하는 방식으로 구성한다. H2의 PostgreSQL
호환 모드는 일반적인 서비스 테스트에는 사용할 수 있지만, 이 ADR의 행 잠금 동시성 계약을 최종적으로 증명하는 환경으로
사용하지 않는다.

다음 시나리오를 별도의 Transaction에서 병렬 실행해 검증한다.

- 29명인 스터디에 두 사용자가 동시에 가입하면 한 요청만 성공하고 최종 멤버 수는 30명이다.
- 49개 스터디에 참여 중인 사용자가 두 스터디를 동시에 생성하면 한 요청만 성공하고 최종 멤버십 수는 50개다.
- 49개 스터디에 참여 중인 사용자가 서로 다른 두 초대를 동시에 수락하면 한 요청만 성공하고 최종 멤버십 수는 50개다.
- 같은 사용자가 같은 스터디 초대를 동시에 두 번 수락하면 한 요청만 멤버십을 생성하고 다른 요청은 중복 가입 오류로 실패한다.

## 선택 이유

현재 모델에는 사용자별 또는 스터디별 membership counter가 없다. 기존 `countByUserId`와 `countByStudyId`를 유지하면서
상한을 보호하려면, 해당 개수를 기준으로 삼는 부모 행을 잠그고 확인과 저장을 같은 Transaction에 두는 변경이 가장 작다.

사용자 행 잠금은 사용자 데이터 자체를 변경하려는 목적이 아니라, 같은 사용자에 대한 상한 검증 구간을 직렬화하기 위한
동기화 지점이다. 스터디 행 잠금도 스터디의 일반 정보를 변경하려는 목적이 아니라, 같은 스터디의 정원 검증 구간을
직렬화하기 위한 것이다. 두 잠금은 테이블 전체의 요청을 막지 않고 동일한 사용자 또는 동일한 스터디를 대상으로 하는
경쟁 요청에만 대기 비용을 만든다.

생성 경로에서 `Study`와 리더 멤버십을 하나의 Transaction으로 묶으면 둘 중 하나만 저장되는 부분 성공을 방지할 수 있다.
생성 중 예외가 발생하면 Transaction 전체가 롤백되어 `Study`와 리더 멤버십이 함께 저장되지 않는다.

## 검토한 대안

### 잠금 없이 개수만 조회한다

구현은 단순하지만 조회와 저장 사이의 경쟁 구간을 보호하지 못한다. 정원과 사용자별 상한을 초과할 수 있으므로
채택하지 않는다.

### `(study_id, user_id)` 유일 제약만 사용한다

중복 멤버십은 막을 수 있지만 정원 30명과 사용자별 상한 50개는 보호하지 못한다. 또한 중복 요청의 실패가 도메인 오류가
아닌 데이터베이스 제약조건 예외가 될 수 있으므로 단독 전략으로 채택하지 않는다.

### versioned counter를 추가한다

개수 조회 없이 충돌을 감지할 수 있지만, 사용자와 스터디에 counter 컬럼을 추가하고 생성·가입·탈퇴·방출 시 counter를
정확히 갱신해야 한다. 현재는 Hard Delete와 count 쿼리 모델을 유지하는 편이 변경 범위와 운영 위험이 작다.

### 조건부 원자 갱신을 사용한다

`UPDATE ... WHERE count < limit`과 같은 방식은 원자성을 제공할 수 있지만 현재 모델에는 갱신할 counter가 없다. 멤버십
행의 INSERT와 집계 조건을 하나의 SQL로 표현하려면 별도 SQL과 충돌 결과 처리 설계가 필요하므로 우선 채택하지 않는다.

### 테이블 잠금 또는 SERIALIZABLE 격리를 사용한다

더 넓은 범위의 직렬화를 제공할 수 있지만 관련 없는 사용자와 스터디 요청까지 대기시키거나 재시도 비용을 키울 수 있다.
현재 상한의 경쟁 단위가 명확하므로 필요한 부모 행만 잠그는 방식을 선택한다.

## 영향

### 긍정적 영향

- 동시 가입에도 스터디 멤버 수가 30명을 초과하지 않는다.
- 스터디 생성과 초대 수락을 포함해 사용자의 현재 참여 스터디 수가 50개를 초과하지 않는다.
- 같은 사용자의 생성·초대 수락 경쟁이 하나의 사용자 행을 기준으로 직렬화된다.
- 같은 스터디에 대한 서로 다른 사용자의 가입 경쟁이 하나의 스터디 행을 기준으로 직렬화된다.
- 스터디 생성 실패 시 `Study`와 리더 멤버십이 함께 롤백된다.
- 탈퇴·방출을 Hard Delete하는 현재 모델을 유지하면서 별도 활성 상태 컬럼을 추가하지 않아도 된다.

### 부정적 영향과 위험

- 같은 사용자 또는 같은 스터디에 요청이 집중되면 해당 행의 잠금을 기다리는 시간이 생긴다.
- 개수 조회는 계속 수행하므로 membership 수가 커질수록 적절한 인덱스와 쿼리 실행 계획을 확인해야 한다.
- 새로 멤버십을 생성하는 진입점이 추가되면 사용자별 상한과 동일한 Transaction·잠금 경계를 누락하지 않아야 한다.
- 잠금 순서가 다른 쓰기 경로와 결합되면 교착 상태가 발생할 수 있으므로 `User` 후 `Study` 순서를 유지해야 한다.
- H2 호환 모드만으로는 PostgreSQL의 실제 행 잠금 동작을 완전히 검증할 수 없다.

## 미확정 사항

없음.

## 후속 작업

- `StudyMembershipConcurrencyTest`의 H2 설정을 Testcontainers PostgreSQL과 `@DynamicPropertySource` 설정으로 교체한다.
- `org.testcontainers:junit-jupiter`와 `org.testcontainers:postgresql` 테스트 의존성을 추가한다.
- 개발 환경과 CI에서 Docker를 사용할 수 있는지 확인하고, 실제 PostgreSQL에서 동시성 테스트와 전체 테스트를 실행한다.
- 새로운 멤버십 생성 경로가 추가되면 이 ADR의 사용자·스터디 잠금 순서와 30개·50개 상한 검증을 재사용한다.
