# 0065. OSIV를 끄고 DB 연결을 트랜잭션이 끝날 때 반납한다

- 날짜: 2026-11-24
- 관련 이슈: 없음
- 관련 결정: [ADR-0054](0054-separate-upload-verification-from-database-transactions.md)의 S3 호출과 트랜잭션 분리,
  [ADR-0031](0031-run-postgresql-specific-tests-with-testcontainers.md)의 PostgreSQL 전용 테스트

## 배경

OSIV(Open Session In View)는 요청이 들어올 때 영속성 컨텍스트를 열어 응답이 끝날 때까지 유지하는 기능이다.
`application.yaml`에 `spring.jpa.open-in-view`를 지정하지 않아 Spring Boot 기본값인 켬으로 동작하고 있었다.
애플리케이션 시작 시 기본값을 명시하라는 경고도 출력된다.

Spring은 Hibernate 연결 처리 모드를 `DELAYED_ACQUISITION_AND_HOLD`로 지정한다. 처음 필요할 때 DB 연결을 얻고,
영속성 컨텍스트가 닫힐 때까지 유지한다는 뜻이다. 따라서 연결의 반납 시점은 영속성 컨텍스트가 언제 닫히는지에 달려 있다.

- OSIV 켬: 영속성 컨텍스트가 요청 전체에 묶인다. 첫 트랜잭션에서 얻은 연결을 응답 본문 작성이 끝날 때까지 유지한다.
- OSIV 끔: 영속성 컨텍스트가 트랜잭션 단위로 열리고 닫힌다. 커밋 직후 연결을 반납한다.

[ADR-0054](0054-separate-upload-verification-from-database-transactions.md)는 업로드 완료 처리에서 S3 조회 동안
DB 연결을 유지하지 않도록 `FileService.completeUpload`를 `NOT_SUPPORTED`로 두고 트랜잭션을 둘로 나눴다.
그러나 OSIV가 켜져 있으면 첫 조회 트랜잭션에서 얻은 연결이 S3 응답을 기다리는 동안에도 반납되지 않는다.
트랜잭션 경계를 나눈 의도가 연결 점유 측면에서는 적용되지 않고 있었다.

## 결정

- `application.yaml`에 `spring.jpa.open-in-view: false`를 명시한다.
- 엔티티의 지연 로딩은 트랜잭션 안에서 끝낸다. 컨트롤러와 응답 직렬화는 트랜잭션 밖에서 실행되므로
  서비스가 응답 DTO로 변환해 반환하는 현재 방식([ADR-0005](0005-transfer-data-across-layer-boundaries.md))을 유지한다.

## 선택 이유

켬과 끔을 같은 조건에서 측정했다.

- 측정 환경: PostgreSQL 16(Testcontainers, 로컬), `@SpringBootTest(RANDOM_PORT)`, Hikari 풀 크기 10
- 데이터: 스터디원 30명, 과제 40개, 리더가 속한 스터디 15개
- 측정 방법: DataSource를 감싸 요청마다 연결 대여부터 반납까지의 시간을 기록했다.
  `hikaricp.connections.usage`와 같은 구간이다. 조회 API는 50회 워밍업 후 300회씩 순서대로 호출했다.
  업로드 완료는 S3 HeadObject 응답을 100ms 지연으로 대체해 40회 호출했다. 같은 측정을 두 번 실행해 결과가 비슷한 것을 확인했다.
- 측정 코드는 저장소에 남기지 않았다. 매 테스트 실행마다 별도 Spring 컨텍스트 두 개를 띄워야 해서
  일반 테스트 시간을 늘리기 때문이다.

| API | OSIV | 요청당 연결 대여 | 연결 점유 평균 | p50 | p95 |
| --- | --- | --- | --- | --- | --- |
| 과제 목록 `GET /studies/{id}/assignments?size=20` | 켬 | 1회 | 3.25ms | 3.23ms | 4.12ms |
|  | 끔 | 1회 | 3.22ms | 3.14ms | 4.33ms |
| 과제 상세 `GET /studies/{id}/assignments/{id}` | 켬 | 1회 | 2.87ms | 2.84ms | 3.67ms |
|  | 끔 | 1회 | 2.85ms | 2.89ms | 3.67ms |
| 내 스터디 목록 `GET /studies/me` | 켬 | 1회 | 1.71ms | 1.65ms | 2.31ms |
|  | 끔 | 1회 | 1.73ms | 1.65ms | 2.44ms |
| 업로드 완료 `POST /files/{id}/complete` (S3 100ms) | 켬 | 1회 | 115.7ms | 115.5ms | 119.9ms |
|  | 끔 | 2회 | 7.9ms | 8.8ms | 9.4ms |

요청 한 건의 이벤트 순서를 기록하면 반납 시점의 차이가 드러난다(요청 시작 기준).

```text
업로드 완료, OSIV 켬
  연결 대여(2.3ms) → 커밋(4.7ms) → S3 호출(6.3~109.5ms) → 커밋(115.0ms) → 연결 반납(115.5ms)
업로드 완료, OSIV 끔
  연결 대여(2.0ms) → 커밋(4.2ms) → 연결 반납(4.2ms) → S3 호출(5.2~108.8ms)
  → 연결 대여(109.1ms) → 커밋(114.8ms) → 연결 반납(114.8ms)
```

조회 API는 커밋 뒤 응답 작성이 0.1~0.2ms 안팎이어서 두 방식의 차이가 측정 오차 수준이다.
반면 트랜잭션 사이에 외부 호출이 있는 업로드 완료는 OSIV를 끄면 연결 점유가 115.7ms에서 7.9ms로 줄어든다.
S3가 느려지거나 시간 초과가 나면 켬에서는 그 시간만큼 연결이 묶이고, 동시 요청이 몰리면 풀이 고갈될 수 있다.

`open-in-view: false`로 전체 테스트 1,660개를 실행했고 모두 통과했다. `LazyInitializationException`은 발생하지 않았다.
현재 코드는 트랜잭션 밖 지연 로딩에 의존하지 않으므로 끄는 비용이 설정 한 줄이다.

## 검토한 대안

### OSIV를 켠 채 유지한다

트랜잭션 밖에서도 지연 로딩이 동작하므로 응답 조립 위치를 신경 쓰지 않아도 된다.
측정한 조회 API에서는 연결 점유 차이도 거의 없다. 그러나 외부 호출을 트랜잭션 밖으로 분리한 경로에서
연결을 반납하지 못하는 문제가 남는다. 앞으로 트랜잭션 밖에 느린 작업을 추가할 때마다 같은 문제가 생기므로 선택하지 않는다.

### OSIV를 켜고 외부 호출 경로만 영속성 컨텍스트를 분리한다

업로드 완료처럼 필요한 곳에서만 `EntityManager`를 직접 닫거나 별도 실행 흐름으로 분리하는 방식이다.
전역 설정을 바꾸지 않지만, 경로마다 OSIV를 의식한 코드를 추가해야 하고 빠뜨린 경로는 드러나지 않는다.
현재 코드가 OSIV에 의존하지 않으므로 전역으로 끄는 편이 단순하다.

## 영향

### 긍정적 영향

- DB 연결을 트랜잭션이 끝날 때 반납하므로 트랜잭션 밖의 외부 호출·응답 작성 시간이 연결 점유에 포함되지 않는다.
- ADR-0054의 트랜잭션 분리가 의도대로 연결 점유를 줄인다.
- 시작 시 OSIV 기본값 경고가 사라진다.

### 부정적 영향과 위험

- 트랜잭션 밖에서 지연 로딩을 시도하면 `LazyInitializationException`이 발생한다.
  테스트가 지나가지 않은 경로에 그런 코드가 있다면 운영에서 처음 드러날 수 있다.
- 한 요청이 트랜잭션을 여러 번 열면 연결도 그만큼 다시 빌린다(업로드 완료는 1회에서 2회).
  풀에서 빌리는 비용은 작지만 0은 아니다.
- 같은 요청의 트랜잭션끼리 영속성 컨텍스트를 공유하지 않는다. 앞 트랜잭션에서 읽은 엔티티는 준영속 상태가 된다.

## 미확정 사항

- 측정은 애플리케이션과 DB가 같은 장비에 있는 로컬 Testcontainers 기준이다. 운영 DB와 실제 S3 지연에서의 차이는 측정하지 않았다.
- 측정은 순차 호출이다. 동시 요청에서 풀 대기 시간이 얼마나 줄어드는지는 확인하지 않았다.
- 조회 API에서 끔의 서버 처리 시간이 0.3~0.4ms 길게 나왔으나 원인은 확인하지 않았다.

## 후속 작업

- 배포 후 `hikaricp.connections.usage`와 `LazyInitializationException` 로그를 확인한다.
