# 0059. 캘린더는 원본 콘텐츠의 현재 상태를 월간 이벤트로 조회한다

- 날짜: 2026-11-04
- 관련 이슈: [#639](https://github.com/woowacourse-teams/2026-ChongChong/issues/639)
- 적용 상태: 월간 조회와 본인 상태 응답을 구현하고 단위·H2 저장소·HTTP 계약 테스트를 검증했다. `x-backend.status: in-progress`이며 전체 백엔드 회귀·PostgreSQL 검증과 PR·Merge 이후 Postman 기능 테스트 대기다.
- 관련 계약: [스터디 홈 월간 일정 조회](../openapi/paths/studies/calendar.yaml), [월간 응답 스키마](../openapi/components/schemas/study-calendar.yaml)
- 관련 결정: [ADR-0013](0013-unify-application-time-source.md)의 한국 기준 Clock,
  [ADR-0015](0015-use-records-for-read-projections.md)의 조회 projection,
  [ADR-0028](0028-adopt-spec-first-api-contracts.md)의 명세 우선 흐름과
  [ADR-0032](0032-use-submitted-at-as-assignment-submission-state.md)의 제출 시각 기준을 재사용한다.
- 연계 이슈: [#277](https://github.com/woowacourse-teams/2026-ChongChong/issues/277)의 가입 전 콘텐츠 열람과
  [#637](https://github.com/woowacourse-teams/2026-ChongChong/issues/637)의 현재 제출 대상 및 제출물 보존 정책.

## 배경

스터디 홈에 월간 캘린더를 도입하면서 공지 생성·과제 생성·과제 제출 마감을 날짜별로 조회해야 한다.
기존 홈 API는 역할별 미완료 항목과 진행 현황을 반환하고, 공지·과제 목록은 ID 커서 기반이다.
이 응답을 그대로 사용하면 이미 완료된 항목이나 다른 월에 생성되어 이번 달에 마감하는 과제를 누락할 수 있다.

사용자는 공지는 가입 전·후 전체, 과제는 본인이 현재 지정된 항목만 조회하도록 결정했다.
제목·마감일 수정과 삭제는 현재 원본을 반영하고 수정 전·삭제 전 일정의 이력은 보존하지 않는다.
완료 상태는 기존 데이터로 작은 범위에서 제공할 수 있으면 이번에 포함하고 프론트 표시는 별도로 진행한다.
기타 일정은 이번 작업에서 제외한다.

따라서 캘린더를 독립적인 일정 저장 모델로 만들지, 현재 콘텐츠에서 파생하는 조회 모델로 만들지 결정해야 한다.

## 결정

### 원본에서 월간 이벤트를 구성한다

- 별도 일정 엔티티·테이블·등록 API 없이 공지와 과제를 조회한다.
- `NOTICE_CREATED`는 공지 `createdAt`, `ASSIGNMENT_CREATED`는 과제 `createdAt`,
  `ASSIGNMENT_DUE`는 과제의 현재 `closeAt`에서 파생한다.
- 같은 날 생성·마감된 과제도 서로 다른 이벤트로 반환한다. 생성 월과 마감 월이 다르면 각 월의 이벤트만 반환한다.
- 제목은 현재 원본 제목이다. 마감 변경은 현재 날짜에 반영하고 원본 삭제 시 관련 이벤트는 응답에서 제외한다.
- `eventType`, `resourceType`, `resourceId` 조합으로 이벤트를 식별한다. 원본 종류와 ID로 기존 상세 조회에 연결한다.
- UI 색상·표시 문구·링크 경로와 전체 대상자 완료 집계는 이 조회 모델에서 제공하지 않는다.

### 조회 대상은 현재 멤버와 지정 여부를 기준으로 한다

- 인증된 현재 스터디 멤버만 조회한다. 기존 인증·접근 오류를 사용하고 원본 조회 전에 스터디와 멤버십을 확인한다.
- 공지는 가입 전·후 및 본인 확인 대상 기록 유무와 관계없이 해당 스터디 전체를 조회한다.
- 과제는 현재 본인이 제출 대상으로 지정된 것만 생성·마감 이벤트로 반환한다. 리더에게도 같은 조건을 적용한다.
- #637은 대상 제외 후에도 제출 기록을 보존한다. 제출 기록이 있다는 이유만으로 현재 대상이라고 판단하지 않는다.
  대상 제외 시 보존된 제출물이 있어도 제외하고 재지정 시 다시 포함한다.
- 실제 구현 기준 브랜치의 현재 지정 여부 표현을 사용한다. 이 API를 위해 별도의 대상 지정 상태를 복제하지 않는다.
- 기존 공지·과제 목록/상세, 읽음 처리, 제출, 리마인드의 권한·할당 정책은 변경하지 않는다.

### 한 달의 모든 이벤트와 현재 본인 상태를 함께 반환한다

- 전용 `GET /api/studies/{studyId}/calendar`에 필수 정수 `year`, `month`를 받는다.
  `year`는 1~9998, `month`는 1~12다. 다음 달 경계도 기존 네 자리 날짜 계약 안에서 계산한다.
- Asia/Seoul 기준 `[월 1일 00:00, 다음 달 1일 00:00)`을 조회한다. 과거 월도 허용한다.
  월말을 초 단위 최댓값으로 계산하지 않아 소수 초 데이터가 누락되지 않게 한다.
- 선택 월의 모든 조회 대상 이벤트를 반환한다. 페이지 크기로 자르거나 프론트에 커서 순회를 요구하지 않는다.
- `eventAt` 오름차순, 동률이면 공지 생성·과제 생성·과제 마감 순서, 같은 종류이면 원본 ID 오름차순이다.
- 공지는 `readStatus`를 반환하고 본인 확인 대상 기록이 없으면 `NOT_ASSIGNED`로 구분한다.
  미대상 공지를 `UNREAD`로 추정하거나 누락시키지 않는다.
- 과제는 기존 `submissionStatus` 중 `NOT_SUBMITTED`, `SUBMITTED`, `LATE_SUBMITTED`, `MISSING`을 반환한다.
  현재 미지정 과제는 조회에서 제외하므로 과제 이벤트에 `NOT_ASSIGNED`는 없다.
- 상태는 원본 시각에서 파생한다. 최초 제출 시각과 현재 마감 시각을 비교하는 기존 규칙을 유지하고,
  지각 제출도 제출 완료로 구분하며 마감 후 미제출을 제출 완료로 바꾸지 않는다.
- 완료·마감 여부로 이벤트를 숨기지 않는다. 상태는 과거 이벤트 당시가 아닌 조회 시점 기준이며
  한 요청에서 한 번 구한 애플리케이션 Clock 기준 시각을 모든 이벤트에 사용한다.
- 상태 판정에 필요한 기존 필드를 조회 projection에 포함해 이번 계약에 제공한다. 프론트는 사용을 나중에 적용할 수 있다.

### 필요한 필드만 조회하고 원본 저장 흐름을 바꾸지 않는다

공지 생성·과제 생성·과제 마감에 대한 범위 조회 결과를 읽기 전용 서비스에서 합치는 방식으로 시작한다.
공지의 본인 읽음 정보는 본인 멤버 조건을 JOIN 조건에 둔 LEFT JOIN으로 조회해 미대상 공지가 사라지지 않게 한다.
과제 조회에는 현재 본인 지정 조건을 적용하고 본인 제출 시각과 원본 마감 시각을 함께 읽는다.
본문·첨부·제출 내용·전체 수신자와 제출자 컬렉션을 로딩하거나 이벤트마다 추가 쿼리를 실행하지 않는다.

별도 이벤트를 쓰지 않으므로 공지·과제 생성/수정/삭제 트랜잭션에 캘린더 동기화 작업을 추가하지 않는다.
기존 인덱스와 실행 계획을 확인한 뒤 필요하면 인덱스를 별도 변경으로 추가한다.

## 선택 이유

요구사항은 현재 콘텐츠의 날짜와 상태를 보여주는 것이며 일정 자체의 편집이나 과거 이력 보존이 아니다.
원본 기반 조회는 제목·마감·삭제를 중복 저장소와 동기화할 필요가 없고 기존 데이터도 바로 조회할 수 있다.
전용 월간 API는 현재 홈의 미완료 집계와 목록의 커서 계약을 바꾸지 않으면서 조회 목적을 분리한다.

현재 대상 여부와 제출 기록을 구분하면 제출물을 보존하는 #637의 변경 이후에도 제외된 과제를 노출하지 않는다.
읽음·제출 상태는 기존 시각과 현재 대상 여부로 판단할 수 있어 새 상태 저장 모델 없이 함께 제공할 수 있다.

## 검토한 대안

### 별도 일정 테이블을 만들고 콘텐츠 변경 때 동기화한다

원본과 독립적인 일정 편집과 과거 이력 확장에는 유리하지만, 현재 범위에 없는 저장 모델과 동기화 책임이 생긴다.
원본 수정·삭제 반영을 위해 중복 데이터의 일관성을 관리해야 하므로 채택하지 않는다.

### 기존 목록과 상세 API를 순회해 프론트에서 구성한다

서버 신규 API는 줄지만 조회 월과 관련 없는 페이지까지 순회해야 하고 마감 월만 다른 과제를 놓칠 수 있다.
상세 추가 호출과 역할별 상태 조합도 필요하므로 월간 조회 계약을 별도로 둔다.

### 미완료 항목만 반환하거나 제출 기록 존재만으로 과제를 포함한다

기존 홈 조회를 재사용하기 쉽지만 완료한 항목의 날짜가 사라지고 제출물이 보존된 제외 대상도 노출된다.
현재 합의한 전체 공지·현재 지정 과제 조회 정책과 일치하지 않아 채택하지 않는다.

## 영향

### 긍정적 영향

- 기존 콘텐츠와 현재 지정·읽음·제출 데이터로 조회하여 일정 저장과 변경 동기화가 필요 없다.
- 가입 전 공지, 완료된 항목과 다른 달에 생성·마감된 과제를 일관되게 조회할 수 있다.
- 프론트는 한 번 받은 월간 데이터에서 날짜 점·목록과 상세 연결을 구성할 수 있다.
- 기존 홈·목록·상세 계약과 쓰기 정책을 유지한다.

### 부정적 영향과 위험

- 월 안의 이벤트가 많으면 응답 크기와 정렬 비용이 증가한다. 조회 필드와 실행 계획을 확인해야 한다.
- 현재 원본 상태를 보여주므로 수정 전 마감일·삭제된 콘텐츠·과거 완료 상태를 복원할 수 없다.
- #637의 실제 현재 지정 여부 모델과 연계해야 한다. 구현 기준 브랜치가 해당 기능을 포함하는지 확인해야 한다.
- 생성·마감 조회가 여러 쿼리이므로 동시에 변경되는 데이터의 단일 시점 스냅샷까지 보장하지 않는다.
  변경 요청 완료 후 다시 조회한 결과를 검증하며 별도 잠금이나 격리 수준 변경은 추가하지 않는다.
- 자연어로 정의한 월 경계·권한·수정 반영은 스키마 검증만으로 증명되지 않아 HTTP 시나리오 검증이 필요하다.

## 미확정 사항

- 기능 정책의 미확정 사항은 없다. #637의 병합 상태·구현 구조와 인덱스 추가 필요성은 구현 시 확인한다.
- 예상보다 큰 상태 제공 변경이 발견되면 사용자와 합의된 후속 분리 방침에 따라 OpenAPI·이슈를 함께 갱신한다.
  현재 명세의 상태 필드는 필수이므로 구현에서 임의로 생략하지 않는다.
