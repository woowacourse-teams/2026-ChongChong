# 0005. 레이어 경계에서 전용 데이터 객체를 사용한다

- 날짜: 2026-08-15
- 관련 이슈: [#29](https://github.com/woowacourse-teams/2026-ChongChong/issues/29)

## 배경

웹 요청 형식, 애플리케이션 유스케이스와 도메인 모델은 서로 다른 이유로 변경된다. 외부 요청 DTO나 영속성 Entity를
여러 레이어에서 그대로 사용하면 한 레이어의 변경이 다른 레이어로 전파되고, API가 내부 모델을 노출할 수 있다. 반면 모든
경계에 무조건 새 DTO를 만들면 의미 없는 변환 코드가 늘어난다.

## 결정

- 외부 HTTP 요청과 응답에는 각각 전용 Request DTO와 Response DTO를 사용한다.
- 현재 API 계약과 서비스의 입출력은 형태와 의미가 크게 다르지 않을 것으로 예상하므로 Request DTO와 Response DTO를
  Controller와 서비스 경계에서 사용할 수 있다.
- Request DTO를 도메인 객체나 영속성 Entity 대신 Repository까지 전달하지 않는다.
- 도메인 객체와 영속성 Entity를 API 응답으로 직접 반환하지 않는다.
- 도메인과 영속성 경계에서는 받는 쪽이 요구하는 최소한의 형태로 변환한다.
- 별도 Command, Query 또는 Result는 현재 도입하지 않는다. API 계약과 서비스 유스케이스의 입출력이 달라지거나 HTTP
  외의 진입점에서 같은 유스케이스를 사용하게 되는 등 분리할 필요가 확인되면 도입하고 이 결정을 수정한다.
- 조회 결과가 특정 화면이나 기능에 한정되고 완전한 도메인 객체가 필요하지 않으면 읽기 전용 Projection을 사용할 수 있다.
- Projection은 조회 유스케이스가 요구하는 필드만 포함하며 상태 변경을 위한 도메인 객체처럼 사용하지 않는다.
- 변환 로직은 데이터가 경계를 통과하는 지점에 둔다. 변환을 위해 도메인 객체가 웹 DTO나 영속성 구현에 의존하지 않게
  한다.

## 선택 이유

외부 계약과 도메인 및 영속성 모델을 분리하면 변경의 영향을 격리하고, 의도하지 않은 필드 노출을 막을 수 있다. 현재는
API 계약과 서비스 입출력의 차이가 크지 않으므로 서비스 전용 타입을 미리 만들지 않아 불필요한 변환 비용을 줄인다.
특정 조회에 Projection을 사용하면 화면에 필요한 데이터를 위해 전체 Entity나 도메인 객체를 조립하는 비용을 피할 수
있다. 동시에 모든 계층에 기계적으로 DTO를 추가하지 않아 불필요한 매핑 비용을 제한한다.

## 검토한 대안

### 모든 레이어마다 항상 별도 DTO 생성

레이어 간 결합을 명시적으로 끊을 수 있지만 데이터와 의미가 같은 경우에도 변환 코드와 타입 수가 과도하게 늘어난다.

## 영향

### 긍정적 영향

- 외부 API 계약과 내부 도메인 및 영속성 모델의 변경을 격리할 수 있다.
- 응답에 내부 필드가 의도치 않게 노출되는 것을 방지할 수 있다.
- 읽기 전용 유스케이스는 필요한 데이터만 효율적으로 조회할 수 있다.

### 부정적 영향과 위험

- DTO와 변환 코드가 추가된다.
- Request/Response DTO를 Controller와 서비스가 함께 사용하므로 API 계약이 크게 바뀌면 서비스도 영향을 받을 수 있다.
- 변환 책임을 일관되게 지키지 않으면 매핑 로직이 여러 위치에 흩어질 수 있다.
- Projection을 무분별하게 만들면 조회 모델 수와 Repository 책임이 늘어날 수 있다.

## 미확정 사항

- Projection을 Repository 인터페이스의 반환 타입으로 노출할지, 인프라 구현 내부 타입으로 제한할지 실제 조회 요구사항과
  Repository 추상화 방식을 정할 때 결정해야 한다.
- DTO 변환을 정적 팩터리 메서드, 별도 Mapper 또는 Controller 메서드 중 어떤 방식으로 통일할지는 반복되는 변환의
  복잡도를 확인한 뒤 결정해야 한다.

## 후속 작업

- 첫 API 구현에서는 별도 Command, Query 또는 Result 없이 Request DTO와 Response DTO를 서비스 경계에서 사용한다.
- API 계약과 서비스 입출력의 변경 주기가 달라지면 서비스 전용 타입 도입 여부를 다시 검토한다.
- 첫 화면 전용 조회를 구현할 때 Projection의 위치와 반환 경계를 별도 결정으로 구체화한다.
