# 0049. NotificationDelivery에 최초 푸시 클릭 시각을 기록한다

- 날짜: 2026-10-12
- 관련 이슈: [#495](https://github.com/woowacourse-teams/2026-ChongChong/issues/495)

## 배경

ADR 0038은 논리 알림과 Web Push 전달을 분리하고, 구독별 `NotificationDelivery`에 provider 전송 결과를 기록한다. 현재 `SENT`는 백엔드가 Web Push provider로부터 성공 응답을 받았다는 뜻이다. Push API에서 메시지는 서비스 워커에 전달되고, 서비스 워커가 알림 표시 등 후속 동작을 결정하므로 `SENT`만으로 브라우저 알림이 표시됐거나 사용자가 확인했다고 판단할 수 없다. [W3C Push API](https://www.w3.org/TR/push-api/)

알림 성과를 보려면 전송 결과, 알림 반응, 후속 행동을 구분해야 한다. `Notification.isRead`는 인앱 알림을 읽었는지를 나타내며, 사용자가 푸시를 눌렀다는 증거가 아니다. 푸시 클릭을 인앱 읽음과 분리해 기록할 필요가 있다.

## 결정

### 푸시 클릭은 NotificationDelivery 단위로 기록한다

`notification_deliveries.clicked_at`에 해당 전달 건의 최초 푸시 클릭 기록 시각을 저장한다. 현재 값은 클라이언트가 보낸 발생 시각이 아니라 백엔드가 클릭 기록 요청을 처리한 시각이다. 값이 `null`이면 아직 클릭이 기록되지 않은 상태다. 한 전달 건에 대한 순차적인 반복 요청은 기존 시각을 유지한다. 여러 브라우저 구독에 보낸 알림은 각 전달 건에서 따로 기록한다.

서비스 워커의 `notificationclick` 이벤트에서 payload의 `deliveryId`를 사용해 인증된 `POST /api/notification-deliveries/{deliveryId}/click` API를 호출한다. 이 이벤트는 서비스 워커에서 알림이 활성화될 때 발생한다. [W3C Service Workers](https://www.w3.org/TR/service-workers/#notification-click)

백엔드는 로그인 사용자와 전달 건의 구독 소유자가 일치하는지 확인한 뒤 클릭 시각을 기록한다. `Notification.isRead`는 인앱 알림 읽음 상태로 유지하고 푸시 클릭 여부와 합치지 않는다.

### 통계는 전달, 반응, 효과를 구분한다

- **전달:** 전달 건 수와 상태별 비율, 시도·재시도·실패 건수, `created_at`부터 `sent_at`까지의 대기 시간, `claimed_at`부터 `sent_at`까지의 처리 시간으로 provider 전송 결과를 본다.
- **반응:** `SENT` 전달 건 가운데 `clicked_at`이 있는 건의 비율과 `clicked_at - sent_at`으로 전달 건 기준 클릭률과 클릭까지 걸린 시간을 본다. 이 지표의 단위는 사용자 수가 아니라 구독별 전달 건이다. 사용자 단위 비율은 알림 수신자를 기준으로 중복 구독을 합쳐 별도 집계한다.
- **효과:** 공지 확인이나 과제 제출 같은 후속 행동은 별도 행동 기록과 알림 대상의 연결, 측정 기간을 정한 뒤 집계한다. 클릭이나 시간적 선후관계만으로 알림의 추가 효과를 단정하지 않는다. 추가 효과를 추정하려면 사용자 단위 무작위 대조군과 결과 비율 차이를 사용한다.

`clicked_at`은 클릭 시각만 보존하며 전체 클릭 횟수나 모든 클릭 이력을 보존하지 않는다. 첫 클릭 이후의 반복 클릭을 분석해야 하는 요구가 생기면 단일 컬럼 대신 클릭 이벤트 테이블을 검토한다.

## 선택 이유

`NotificationDelivery`는 논리 알림과 개별 Web Push 구독의 조합을 나타내므로 클릭 시각을 저장하면 어느 구독으로 전달한 알림이 반응을 얻었는지 `sent_at`, 상태, 시도 횟수와 함께 확인할 수 있다. 논리 알림의 `isRead`만 사용하면 인앱 목록에서 읽은 경우와 푸시를 눌러 진입한 경우를 구분할 수 없다.

최초 시각만 필요하므로 이벤트 테이블보다 nullable timestamp 한 개가 현재 요구에 맞다. 별도 행동 이벤트와 대조군 비교는 이번 저장 변경에 포함하지 않아 클릭 지표와 알림 효과를 혼동하지 않는다.

## 검토한 대안

### `Notification.isRead`를 푸시 클릭 지표로 사용한다

인앱 알림 읽음과 푸시 클릭의 출처가 섞여 클릭률을 계산할 수 없으므로 선택하지 않았다.

### `Notification`에 사용자별 `clicked_at`을 저장한다

같은 사용자의 여러 브라우저 구독 전달 결과를 구분할 수 없고, 구독별 provider 성공 여부와 클릭 반응을 연결하기 어려우므로 선택하지 않았다.

### 클릭 이벤트를 매번 별도 테이블에 저장한다

클릭 횟수와 전체 이력이 필요할 때는 적절하지만, 현재 필요한 정보는 전달 건별 최초 시각 하나이므로 선택하지 않았다.

## 영향

### 긍정적 영향

- provider 전송 성공과 사용자의 푸시 클릭을 별도 지표로 볼 수 있다.
- 클릭한 구독별 전달 건과 클릭까지 걸린 시간을 연결할 수 있다.
- 인앱 읽음 여부와 푸시 클릭 여부를 혼동하지 않는다.
- `NotificationDelivery` 상태와 시도 기록을 전달 지표 집계에 재사용할 수 있다.

### 부정적 영향과 위험

- 서비스 워커가 클릭 API를 호출해야 클릭 데이터가 쌓인다. 백엔드 API만 배포한 상태에서는 프론트 연동 전까지 클릭 지표가 수집되지 않는다.
- 한 사용자가 여러 구독을 보유하면 전달 건 단위 클릭률은 사용자 단위 클릭률과 다르다.
- 브라우저 알림의 실제 표시·열람 여부는 기록하지 않으므로 클릭이 없는 이유를 알 수 없다.
- 기록 시각은 백엔드가 클릭 요청을 처리한 시각이므로 클라이언트 이벤트 발생 시각과 네트워크 지연만큼 차이가 날 수 있다.
- 순차 요청에서는 첫 클릭 시각을 보존하지만, 동시에 들어온 클릭 요청의 원자적 최초 시각 보장은 별도 동시성 정책이 필요하다.
- 후속 행동 연결과 대조군 실험이 없으면 알림의 추가 효과를 판단할 수 없다.

## 미확정 사항

- 여러 전달 건에 대한 클릭을 사용자 단위로 집계할 때 사용할 집계 단위와 대시보드 정의
- 공지 확인·과제 제출 등 후속 행동의 연결 방법과 관찰 기간
- 동시에 들어온 중복 클릭 요청에서도 최초 시각을 보장할 데이터베이스 갱신 방식
- 알림의 추가 효과를 측정할 사용자 단위 대조군 실험 설계

## 후속 작업

- 프론트 서비스 워커의 `notificationclick`에서 `deliveryId`를 백엔드 클릭 기록 API로 전송한다.
- 전달 건 단위와 사용자 단위 클릭률을 구분해 집계한다.
- 후속 행동 측정이 필요해지면 행동 이벤트와 알림 식별자, 관찰 기간을 정의한다.
