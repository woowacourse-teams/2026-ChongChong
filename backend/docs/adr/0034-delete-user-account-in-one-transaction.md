# 0034. 사용자 탈퇴를 단일 트랜잭션에서 검증하고 삭제한다

- 날짜: 2026-09-20
- 관련 이슈: [#340](https://github.com/woowacourse-teams/2026-ChongChong/issues/340)
- 관련 ADR: [0024. 하드 삭제 시 데이터베이스 외래 키 CASCADE로 종속 데이터를 삭제한다](0024-use-database-cascades-for-hard-delete.md),
  [0029. 스터디 멤버십 상한을 행 잠금과 트랜잭션으로 보호한다](0029-protect-study-membership-limits-with-row-locks.md),
  [0031. Testcontainers PostgreSQL로 데이터베이스 특화 테스트를 실행하고 CI에서 Docker를 확인한다](0031-run-postgresql-specific-tests-with-testcontainers.md)

## 배경

사용자는 홈 마이페이지에서 계정을 탈퇴할 수 있어야 한다. 사용자에게 현재 리더 멤버십이 남아 있는 상태에서
계정을 삭제하면 스터디의 운영 주체가 사라진다. 현재 리더 위임 API가 없으므로, 리더는 스터디를 먼저 삭제해야 한다.

Flyway V2와 ADR 0024는 `users → study_members → notice_recipients`,
`assignment_submissions`, `notifications`의 DB CASCADE를 정의한다. 알림의 설치별 발송 기록인
`notification_deliveries`도 알림이나 푸시 토큰 삭제 시 CASCADE로 삭제된다. 반면 `auth_sessions`,
`social_accounts`, `push_tokens`가 `users`를 참조하는 외래 키에는 처음에 `ON DELETE CASCADE`가 없었다.
사용자만 삭제하면 외래 키 제약으로 탈퇴가 실패하므로 Flyway V7에서 세 외래 키에 CASCADE를 추가한다.

스터디 생성과 초대 수락은 이미 사용자 행을 잠근 뒤 멤버십을 만든다. 탈퇴도 같은 사용자에 대한 멤버십 생성과
충돌할 수 있으므로 리더 검사부터 삭제 완료까지 하나의 일관된 경계가 필요하다.

## 결정

### 탈퇴 조건과 트랜잭션

- `DELETE /api/users/me`는 Bearer Access Token의 사용자 ID를 사용하며 요청 본문을 받지 않는다.
- 서비스의 쓰기 트랜잭션에서 사용자 행을 `PESSIMISTIC_WRITE`로 잠금 조회한다. 사용자가 없으면
  `404 USER_NOT_FOUND`를 반환한다. 인증 정보가 없거나 유효하지 않으면 기존 인증 경계가
  `401 AUTHENTICATION_REQUIRED`를 반환한다.
- 잠금을 얻은 뒤 현재 `StudyMember` 중 `role = LEADER`가 하나라도 있는지 확인한다. 현재 모델에는 스터디나
  멤버십의 별도 활성 상태가 없으므로 존재하는 리더 멤버십을 차단 기준으로 삼는다. 멤버십 엔티티 전체를
  영속성 컨텍스트에 로드하지 않는 존재 쿼리를 사용한다.
- 리더 멤버십이 있으면 삭제를 시작하지 않고 `409 STUDY_LEADER_WITHDRAWAL_BLOCKED`를 반환한다.
  MVP에서는 해당 스터디를 먼저 삭제한 뒤 탈퇴하도록 안내한다.
- 검사와 삭제는 하나의 트랜잭션에서 실행한다. 중간 단계가 실패하면 전체 변경을 롤백한다.

### 삭제 책임과 순서

리더 검사를 통과하면 애플리케이션은 사용자 행만 삭제한다. Flyway V7의 사용자 외래 키 CASCADE가
`auth_sessions`, `social_accounts`, `push_tokens`를 삭제하고, 기존 Flyway V2의 CASCADE가
`study_members`를 삭제한다. 멤버십에 종속된 `notice_recipients`, `assignment_submissions`,
`notifications`와 알림 또는 푸시 토큰에 연결된 `notification_deliveries`도 기존 외래 키를 따라 삭제된다.
모든 삭제는 같은 데이터베이스 트랜잭션에 속한다.

다른 사용자의 멤버십과 종속 데이터, 스터디 자체, 공지·과제 원본은 삭제하지 않는다. 리더 검사에서
멤버십 엔티티를 로드하면 Hibernate가 삭제된 사용자를 참조하는 관리 엔티티를 flush할 수 있으므로
존재 쿼리를 사용하고, CASCADE 삭제와 다른 사용자 데이터 보존을 인수 테스트로 확인한다.
성공 응답은 본문 없는 `204 No Content`다.

### 인증 상태 정리

- 사용자 행이 삭제되면 `auth_sessions` 외래 키의 CASCADE로 서버의 인증 세션도 항상 삭제된다. 브라우저의
  Refresh Cookie 처리 여부와 관계없이 기존 Refresh Token으로는 새 토큰을 발급받을 수 없다.
- 탈퇴가 성공하면 `204 No Content` 응답에서 기존 쿠키와 같은 이름과 범위의 Refresh Cookie를
  `Max-Age=0`으로 내려 브라우저에 남은 원본 Refresh Token도 정리한다.
- `401 AUTHENTICATION_REQUIRED`, `404 USER_NOT_FOUND`, `409 STUDY_LEADER_WITHDRAWAL_BLOCKED`처럼
  탈퇴가 완료되지 않은 응답에서는 Refresh Cookie를 변경하지 않는다.
- Refresh Cookie 만료는 이미 발급된 Access Token을 무효화하지 않는다. 클라이언트는 탈퇴 성공 후 보관 중인
  Access Token을 제거하고, 서버에서 기존 Access Token을 처리하는 정책과 검증은 별도 후속 작업으로 다룬다.

### 동시 요청

- 탈퇴와 스터디 생성·초대 수락은 모두 사용자 행을 먼저 잠근다. 탈퇴가 잠금을 얻은 뒤에는 같은 사용자의
  새 멤버십 생성이 탈퇴 트랜잭션 종료까지 대기한다. 반대 순서라면 탈퇴가 잠금을 얻은 뒤 최신 멤버십으로
  리더 여부를 검사한다.
- 탈퇴는 스터디 행 잠금을 추가하지 않는다. 사용자 행 이후 스터디 행을 잠그는 기존 가입 순서를 뒤집지 않는다.
- 스터디 삭제와 탈퇴가 동시에 요청되면 잠금 획득 시점에 따라 `409`가 먼저 반환될 수 있다. 스터디 삭제가
  완료된 뒤 탈퇴를 다시 요청하면 현재 멤버십을 기준으로 재검사한다.
- Refresh Token 회전·소셜 로그인·푸시 토큰 등록처럼 사용자 관련 데이터를 쓰는 다른 경로와의 경쟁에서는
  삭제 후 계정 종속 행이 다시 생기지 않는지 실제 PostgreSQL 통합 테스트로 확인한다. 필요한 경우 해당
  쓰기 경로도 사용자 행 잠금을 공유하도록 조정한다.

## 선택 이유

사용자 행 잠금은 기존 스터디 생성·초대 수락과 같은 동기화 지점을 사용한다. 리더 검사와 삭제를 한
트랜잭션으로 묶으면 차단 조건을 확인한 뒤 같은 사용자가 리더 멤버십을 새로 만드는 경로와 직렬화할 수 있다.

기존 스키마의 CASCADE는 멤버십 하위 데이터에 이미 적용되어 있다. 사용자 직접 종속 행 세 종류에도
외래 키 CASCADE를 적용하면 서비스가 삭제 순서를 관리하지 않아도 된다. 새 종속 행이 추가될 때에는
외래 키의 삭제 정책을 검토해야 한다.

## 검토한 대안

### 잠금 없이 리더 여부만 조회한다

조회 직후 다른 요청이 리더 멤버십을 생성하면 차단 기준이 오래된 상태가 된다. 기존 생성·가입 경로의 사용자
행 잠금과 결합할 수 없으므로 선택하지 않는다.

### 사용자 직접 종속 행을 서비스에서 먼저 삭제한다

인증 세션·소셜 계정·푸시 토큰과 멤버십의 삭제 순서를 애플리케이션이 관리해야 한다. 기존 멤버십 하위 데이터는
DB CASCADE로 삭제하므로 책임이 나뉘고, 종속 테이블이 늘어날 때 서비스도 수정해야 하므로 선택하지 않는다.

### 멤버십의 하위 데이터를 서비스에서 모두 삭제한다

새 종속 테이블이 생길 때마다 서비스의 삭제 순서를 수정해야 하며 ADR 0024와 #261에서 채택한 DB CASCADE
책임을 중복한다. 기존 외래 키 CASCADE를 사용한다.

### 사용자를 Soft Delete한다

인증, 소셜 계정 재연결, 멤버십 조회와 개인정보 보관 정책 전반에 탈퇴 상태를 반영해야 한다. 현재 하드 삭제
요구와 범위가 다르므로 적용하지 않는다.

## 영향

### 긍정적 영향

- 리더가 있는 사용자의 탈퇴를 삭제 전에 차단한다.
- 계정과 종속 데이터의 삭제가 모두 성공하거나 모두 롤백된다.
- 사용자 직접 종속 행과 기존 멤버십 CASCADE 정책을 사용하고 다른 회원의 스터디 데이터를 보존한다.
- 같은 사용자의 스터디 생성·가입과 탈퇴가 사용자 행을 기준으로 직렬화된다.
- 탈퇴 성공 시 서버의 인증 세션과 브라우저의 Refresh Cookie를 함께 정리한다.

### 부정적 영향과 위험

- 삭제가 끝날 때까지 같은 사용자의 멤버십 생성 요청이 행 잠금을 기다린다.
- 삭제 대상이 늘어나면 외래 키 CASCADE 경로를 다시 점검해야 한다.
- 이미 발급된 Access Token은 토큰 자체의 만료 시각까지 남는다. 이후 요청은 사용자 존재 여부를 확인하는
  경로에서 계정 부재로 거부되어야 한다.
- 소셜 제공자에 저장된 계정이나 토큰을 원격으로 삭제하지는 않는다.

## 후속 작업

- Flyway가 적용된 PostgreSQL에서 멤버십·알림·발송 기록 CASCADE, 다른 사용자 데이터 보존과 전체 롤백을 검증한다.
- 스터디 생성·가입과 탈퇴, 인증·푸시 쓰기 경로와 탈퇴의 동시 요청을 검증하고 필요한 잠금 경계를 보완한다.
- 탈퇴 후 기존 Access Token으로 요청할 수 있는 범위를 검증하고 필요한 서버 정책을 별도 이슈에서 결정한다.
- OpenAPI 계약과 실제 HTTP 응답을 비교하고 전체 백엔드 테스트를 실행한다.
