# 0030. 설치 단위 upsert와 활성 상태로 푸시 토큰을 관리한다

- 날짜: 2026-09-09
- 관련 이슈: [#286](https://github.com/woowacourse-teams/2026-ChongChong/issues/286)
- 관련 ADR: [0003. 백엔드 테스트 범위와 역할을 정의한다](0003-define-backend-test-strategy.md),
  [0025. 모든 생성 경로에서 성립할 불변식은 도메인 모델이 보호한다](0025-own-stable-invariants-in-domain-model.md)

## 배경

푸시 토큰은 사용자 계정 자체보다 사용자가 로그인한 앱 설치 단위에 종속된다. 같은 설치에서 사용자가 바뀔 수 있고,
푸시 토큰은 갱신될 수 있으므로 설치 식별자와 기존 사용자·토큰 정보를 함께 최신 상태로 바꿀 수 있어야 한다.

기존의 `(user_id, installation_id)` 유일 제약은 같은 사용자의 중복 등록만 막고 같은 설치가 다른 사용자에게 등록되는 것을
허용한다. 또한 등록 전에 조회하고 없을 때 저장하는 방식은 동시에 최초 등록이 발생하면 중복 저장 경쟁을 만들며, 기존
등록이 있을 때 토큰과 플랫폼이 바뀌어도 최신 값으로 갱신하지 못한다.

로그아웃이나 푸시 수신 중단처럼 등록을 잠시 사용하지 않는 경우에는 등록 행을 삭제하지 않고 비활성화할 필요가 있다.
이후 같은 설치가 다시 등록되면 기존 행을 재사용해 활성화해야 한다.

## 결정

### 설치 식별자를 푸시 토큰 등록의 전역 식별자로 사용한다

- `installation_id`는 `push_tokens` 테이블에서 전역적으로 유일하다.
- 하나의 설치 식별자에는 현재 등록 상태를 나타내는 푸시 토큰 행을 최대 하나만 둔다.
- 같은 설치가 다른 사용자로 등록되면 기존 행의 `user_id`를 새 사용자로 갱신한다. 설치 식별자를 계정별 이력 키로
  사용하지 않는다.
- 데이터베이스에 `uk_push_tokens_installation_id` 유일 제약을 두어 애플리케이션 외부의 저장 경로에서도 이 불변식을
  보호한다.

### 등록은 설치 식별자를 기준으로 원자적으로 upsert한다

- `POST /push-tokens`는 `installationId`, `token`, `platform`을 받는다. `installationId`와 `token`은 필수이며 각각
  255자 이내이고, `platform`은 `ANDROID` 또는 `IOS`다.
- `provider`는 현재 HTTP 요청에서 받지 않는다. 서버가 `EXPO`로 고정해 저장하며, `FCM`과 `APNS` 지원은 별도 계약과
  전송 구현을 결정한 뒤 추가한다.
- 신규 설치 식별자는 사용자, provider, 토큰, 플랫폼과 함께 활성 상태로 저장한다.
- 기존 설치 식별자는 사용자, provider, 토큰, 플랫폼과 `updated_at`을 최신 요청 기준으로 갱신하고 활성 상태로 만든다.
- 등록은 데이터베이스의 원자적 upsert를 사용한다. 등록 전 조회 후 저장하거나 유일 제약 위반을 무시하는 방식은 사용하지
  않는다.

### 비활성화는 사용자 소유를 확인하는 논리 삭제로 처리한다

- `DELETE /push-tokens/{installationId}`는 인증된 사용자의 `user_id`와 설치 식별자가 모두 일치하는 행만 `is_active = false`
  로 변경한다.
- 행은 삭제하지 않는다. 같은 설치가 다시 등록되면 upsert가 기존 행의 정보를 갱신하고 `is_active = true`로 재활성화한다.
- 일치하는 등록이 없거나 다른 사용자의 설치 식별자인 경우에도 소유권을 노출하지 않도록 204를 반환하고 아무 행도 바꾸지
  않는다.

## 선택 이유

설치 식별자를 전역 키로 사용하면 같은 설치가 계정을 바꾸거나 토큰을 갱신하는 경우에도 오래된 등록 행이 남지 않는다.
데이터베이스의 유일 제약과 원자적 upsert를 함께 사용하면 서로 다른 사용자가 같은 설치를 동시에 등록하는 경쟁에서도
하나의 최신 등록으로 수렴한다.

비활성화 시 행을 보존하면 등록과 비활성화가 같은 식별자를 기준으로 대칭을 이루고, 재등록 시 별도의 이력 조회나 신규
행 생성 없이 활성 상태를 회복할 수 있다. provider를 서버에서 EXPO로 결정하면 현재 실제로 지원하는 전송 경로와 HTTP
계약이 어긋나지 않으며, 다른 provider를 추가할 때 필요한 계약 변경을 명시적으로 검토할 수 있다.

## 검토한 대안

### `(user_id, installation_id)` 유일 제약을 유지한다

계정별 등록 이력을 보존하기는 쉽지만 같은 설치가 여러 사용자에게 동시에 등록될 수 있다. 이전 사용자의 토큰 행으로
푸시를 보낼 위험을 제거하지 못하므로 선택하지 않았다.

### 조회 후 저장하고 중복 예외를 무시한다

일반적인 중복 요청을 예외 없이 처리할 수 있지만 조회와 저장 사이의 경쟁을 해결하지 못한다. 토큰·플랫폼 갱신도 별도로
처리해야 하고, 데이터베이스 예외를 정상적인 등록 흐름의 제어 수단으로 사용하게 되므로 선택하지 않았다.

### 비활성화 시 행을 삭제한다

비활성 행을 남기지 않아 저장 공간을 줄일 수 있지만 재등록마다 신규 행을 만들고 설치 단위 상태의 연속성을 잃는다.
현재는 재활성화와 향후 등록 상태 관리가 단순해지는 행 보존 방식을 선택한다.

### provider를 클라이언트에서 받는다

향후 provider를 빠르게 추가할 수 있지만 현재 서버가 EXPO 외 전송을 지원하지 않는 상태에서 클라이언트가 저장 provider를
결정하게 된다. 지원하지 않는 provider가 저장되는 것을 막기 위해 서버 고정 방식을 선택한다.

## 영향

### 긍정적 영향

- 설치 식별자마다 현재 등록 정보가 하나만 존재한다.
- 토큰 갱신, 플랫폼 변경, 계정 전환이 기존 행의 최신 상태로 반영된다.
- 동시 최초 등록에서도 데이터베이스 유일 제약과 원자적 upsert가 중복 행을 막는다.
- 비활성화 후 재등록하면 같은 행이 다시 활성화된다.
- 다른 사용자의 설치 등록 상태를 삭제하거나 조회하지 않고 204로 처리한다.

### 부정적 영향과 위험

- 설치 식별자가 유출되거나 잘못 재사용되면 계정 간 등록 전환이 발생할 수 있으므로 클라이언트가 안정적인 설치 식별자를
  생성·보관해야 한다.
- PostgreSQL upsert 같은 데이터베이스 특화 SQL을 사용하므로 저장소 구현과 테스트 환경이 데이터베이스 문법에 영향을 받는다.
- 비활성 행을 보존하므로 장기간 사용하지 않는 설치 등록을 정리하는 정책이 필요하다.
- 기존 데이터에 서로 다른 사용자의 같은 설치 식별자가 이미 존재하면 새 유일 제약을 적용하기 전에 중복을 정리해야 한다.
- FCM과 APNS를 지원하려면 provider별 토큰 검증과 전송 경로를 추가로 결정해야 한다.

## 미확정 사항

- 설치 식별자의 생성·보관·재설치 시 변경 규칙
- 푸시 전송 실패를 `is_active = false`로 반영할지와 비활성 등록 보존 기간
- FCM과 APNS 지원 시 provider별 HTTP 계약 및 전송 어댑터

## 후속 작업

- 클라이언트가 안정적인 설치 식별자를 유지하고 토큰 갱신 시 등록 API를 호출하는 계약을 문서화한다.
- 로그아웃과 알림 권한 변경 시 비활성화 API를 호출하는 클라이언트 흐름을 연결한다.
- 비활성 등록 정리와 provider 확장 시 별도 의사결정을 작성한다.
