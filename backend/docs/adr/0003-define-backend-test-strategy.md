# 0003. 백엔드 테스트 범위와 역할을 정의한다

- 날짜: 2026-08-15
- 관련 이슈: [#29](https://github.com/woowacourse-teams/2026-ChongChong/issues/29)

## 배경

모든 계층에 같은 방식의 테스트를 작성하면 테스트 수와 유지 비용은 늘지만 동일한 동작을 중복 검증할 수 있다. 반대로
인수 테스트에만 의존하면 비즈니스 규칙이 실패한 원인을 찾기 어렵다. 각 테스트가 어떤 위험을 맡는지 정하고 기본적으로
작성할 범위와 필요할 때만 작성할 범위를 구분해야 한다.

## 결정

도메인과 서비스는 단위 테스트로 비즈니스 규칙을 검증하고, 모든 API는 성공 흐름을 인수 테스트로 검증한다.

### 도메인 단위 테스트

- 도메인의 상태 변경, 불변식, 계산 및 정책을 외부 인프라 없이 검증한다.
- 의미 있는 비즈니스 규칙의 정상 및 예외 경계를 검증한다.
- 단순 생성자, 접근자처럼 동작이 없는 코드를 테스트하기 위해 테스트를 만들지 않는다.

### 서비스 단위 테스트

- 유스케이스의 흐름, 도메인 객체 사이의 협력과 트랜잭션 안에서 수행할 판단을 검증한다.
- 저장소나 외부 시스템은 Mock으로 대체한다.
- 프레임워크를 띄우지 않고 빠르게 실행할 수 있도록 한다.

### Repository 단위 테스트

- Repository 테스트는 기본 작성 범위에서 제외한다.
- 프레임워크가 제공하는 단순 저장과 조회를 애플리케이션 단위 테스트로 반복 검증하지 않는다.
- 직접 작성한 쿼리, 복잡한 매핑, 데이터베이스 제약이나 동시성처럼 실제 영속성 계층에서만 확인할 수 있는 위험이 생기면
  해당 Repository에 한해 실제 데이터베이스를 사용하는 단위 테스트를 추가한다.

### Controller 테스트

- Controller 단위 테스트는 기본 작성 범위에서 제외한다.
- 요청 매핑, 직렬화, 검증 및 전체 계층 연결은 API 인수 테스트에서 검증한다.
- 필터나 인터셉터처럼 인수 테스트로 원인을 분리하기 어렵고 독립된 분기가 많은 웹 계층 코드가 생기면 해당 컴포넌트의
  테스트를 별도로 추가할 수 있다.

### API 인수 테스트

- 외부 사용자의 관점에서 실제 HTTP 요청을 보내 요청부터 응답까지 전체 흐름을 검증한다.
- 공개하는 모든 API 엔드포인트마다 대표 성공 케이스를 최소 하나 작성한다.
- 여러 API가 하나의 사용자 흐름을 이룰 때는 시나리오 형태로 구성할 수 있다.
- 에러 응답 공통 형식은 대표 검증 실패와 비즈니스 실패 시나리오로 별도 검증한다.
- 인증·인가, 동시성, 데이터 정합성처럼 실패 시 영향이 큰 동작은 성공 케이스 원칙과 별개로 필요한 실패 시나리오를
  추가한다.

테스트 종류는 계층 이름이 아니라 검증하려는 위험으로 선택한다. 같은 규칙을 여러 테스트 수준에서 중복 검증하지 않는다.

## 선택 이유

비즈니스 규칙은 빠르고 원인 파악이 쉬운 도메인 및 서비스 단위 테스트로 보호하고, API 계약과 계층 연결은 인수 테스트로
보호한다. Repository와 Controller를 기본 단위 테스트 범위에서 제외하면 프레임워크 동작을 반복해서 검증하는 비용을
줄이면서도, 실제 위험이 있는 Repository에는 단위 테스트를 선택적으로 추가할 수 있다.

## 검토한 대안

### 모든 계층에 단위 테스트 작성

각 클래스를 세밀하게 검증할 수 있지만 구현 구조에 강하게 결합된 테스트가 늘고, Controller와 인수 테스트 또는
Repository와 프레임워크 검증이 중복될 수 있다.

### 모든 Repository를 단위 테스트

쿼리와 매핑을 조기에 확인할 수 있지만 단순 CRUD까지 반복 검증하면 실행 시간과 환경 관리 비용이 커진다. 영속성 관련
위험이 있는 Repository에 선택적으로 적용하는 편이 비용 대비 효과가 높다.

### 인수 테스트만 작성

사용자 관점의 동작은 검증할 수 있지만 실패 원인을 찾기 어렵고 비즈니스 규칙의 세밀한 경계를 빠르게 검증하기 어렵다.

## 영향

### 긍정적 영향

- 테스트 수준별 책임이 분명해지고 중복 검증을 줄일 수 있다.
- 핵심 비즈니스 규칙을 빠른 테스트로 피드백받을 수 있다.
- 모든 API의 대표 성공 계약을 사용자 관점에서 보호할 수 있다.

### 부정적 영향과 위험

- Repository 테스트를 생략할 수 있다는 규칙을 실제 쿼리 위험까지 테스트하지 않아도 된다는 의미로 오해할 수 있다.
- 모든 API의 인수 테스트는 실행 시간과 테스트 데이터 관리 비용을 증가시킨다.
- Mock의 호출 검증이 서비스의 구현 세부 사항에 과도하게 결합되지 않도록 주의해야 한다.

## 미확정 사항

- 인수 테스트에서 사용할 데이터베이스와 격리 방식을 결정해야 한다.
- 인증·인가 및 동시성 시나리오의 필수 테스트 범위는 해당 기능을 설계할 때 별도 결정한다.

## 후속 작업

- 첫 API 구현 시 인수 테스트 기반 클래스와 데이터 격리 방식을 정한다.
- 공통 에러 응답 구현 시 성공 케이스 외에 대표 비즈니스 에러와 입력값 검증 에러를 인수 테스트로 추가한다.
