# 0022. 스터디 멤버 제거 시 종속 데이터를 명시적으로 삭제한다

- 날짜: 2026-08-27
- 관련 이슈: [#161](https://github.com/woowacourse-teams/2026-ChongChong/issues/161)
- 관련 ADR: [0011. 스터디 삭제 시 하위 데이터를 서비스에서 명시적으로 삭제한다](0011-explicitly-delete-study-dependencies.md)

## 배경

MVP v1에서 스터디 멤버 목록 조회, 리더의 멤버 방출과 일반 멤버의 자진 탈퇴 기능을 제공해야 한다. 방출과 탈퇴가 완료되면 해당 사용자는 더 이상 스터디 멤버가 아니므로 `StudyMember`를 제거해야 한다.

현재 `StudyMember`는 다음 데이터에서 외래 키로 참조한다.

- `Notification.recipient`: 멤버가 받은 개인 알림
- `NoticeRecipient.member`: 멤버의 공지 수신 및 읽음 기록
- `AssignmentSubmission.member`: 멤버의 과제 제출 기록
- `Notice.writer`: 공지 작성자
- `Assignment.writer`: 과제 작성자

`StudyMember`에 삭제 cascade가 없으므로 멤버만 먼저 삭제하면 외래 키 제약조건 위반이 발생할 수 있다. 반대로 모든 참조 데이터를 보존하려면 `StudyMember`에 Soft Delete를 도입하고, 멤버 목록·접근 권한·집계·가입 제한·재가입을 포함한 조회와 유니크 제약을 함께 변경해야 한다.

현재 MVP v1에는 탈퇴·방출한 멤버의 활동 이력 보존이나 재가입 제한 요구가 없다. 필요한 기능보다 먼저 범용 Soft Delete와 멤버십 이력 모델을 도입하지 않으면서, 외래 키 무결성을 지키는 삭제 정책이 필요하다.

## 결정

MVP v1의 스터디 멤버 방출과 탈퇴는 Hard Delete로 처리한다.

`StudyMemberService`의 하나의 쓰기 트랜잭션에서 다음 순서로 대상 멤버와 종속 데이터를 명시적으로 삭제한다.

1. 대상 멤버를 수신자로 가진 `Notification`
2. 대상 멤버를 참조하는 `NoticeRecipient`
3. 대상 멤버를 참조하는 `AssignmentSubmission`
4. 대상 `StudyMember`

앞의 세 데이터 사이에는 직접 외래 키 의존이 없지만, 구현과 테스트에서 삭제 순서를 일관되게 유지한다. 각 종속 데이터는 멤버 식별자를 조건으로 하는 Repository bulk delete를 사용하고, 전체 과정 중 하나라도 실패하면 트랜잭션을 롤백한다.

멤버 제거 시 다음 데이터는 함께 삭제한다.

- 대상 멤버의 개인 알림
- 대상 멤버의 공지 읽음 여부와 읽은 시각
- 대상 멤버의 과제 제출 내용·링크·제출 여부·제출 시각
- 대상 멤버의 스터디 멤버십

다음 데이터는 삭제하지 않는다.

- 스터디
- 공지와 공지 리마인더
- 과제와 과제 리마인더
- 다른 멤버의 멤버십과 활동 데이터

`Notice`와 `Assignment`는 작성자인 `StudyMember`를 참조한다. 현재 두 리소스의 작성자는 리더이므로 리더의 방출과 자진 탈퇴를 금지하여 작성자 참조를 보호한다. 리더는 기존 스터디 삭제 API를 사용한다.

탈퇴·방출 이력, Soft Delete 상태와 tombstone은 저장하지 않는다. 제거된 사용자가 유효한 초대 링크를 이용해 다시 가입하는 흐름도 MVP v1에서는 차단하지 않는다.

## 선택 이유

현재 제품 요구에서는 제거된 멤버의 제출·읽음·알림 이력을 다시 조회하거나 복구할 필요가 없다. Hard Delete는 이 요구에 필요한 최소 모델로 구현할 수 있으며, `StudyMember`를 현재 멤버십 자체로 해석하는 기존 코드와도 일치한다.

서비스에서 외래 키 의존 순서와 삭제 범위를 명시하면 어떤 데이터가 함께 삭제되는지 코드와 테스트에서 확인할 수 있다. 이는 스터디 전체 삭제 시 하위 데이터를 서비스에서 명시적으로 삭제하기로 한 ADR 0011의 방향과도 일관된다.

또한 Soft Delete를 도입할 때 필요한 다음 결정을 실제 요구가 생길 때까지 유보할 수 있다.

- `ACTIVE`, `LEFT`, `EXPELLED` 상태 구분
- 탈퇴 멤버를 제외할 조회와 포함할 역사 조회의 범위
- `(study_id, user_id)` 유니크 제약과 재가입 정책
- 과거 제출·읽음 기록의 노출 및 개인정보 익명화
- 운영 데이터베이스 마이그레이션

## 검토한 대안

### `StudyMember` Soft Delete

제출·읽음 이력과 멤버 스냅샷을 유지할 수 있고 향후 복구나 방출 이력에도 활용할 수 있다. 하지만 모든 접근 권한, 멤버 목록, 멤버 수, 내 스터디 목록과 공지·과제 집계 쿼리에서 활성 멤버 기준을 정의해야 한다. 재가입 시 기존 멤버십을 재활성화할지 새 멤버십을 만들지도 결정해야 하므로 MVP v1 범위를 넘어선다.

### 제거 이력 또는 tombstone 저장

`StudyMember`를 Hard Delete하면서 `(study_id, user_id)`와 제거 사유를 남기면 방출된 사용자의 재가입을 막을 수 있다. 현재는 재가입 제한 요구가 없고 별도 이력의 개인정보 보존 기간과 스터디 삭제 시 생명주기도 결정해야 하므로 채택하지 않았다.

### 데이터베이스 `ON DELETE CASCADE`

데이터베이스가 종속 데이터를 자동으로 삭제하므로 서비스 코드를 줄일 수 있다. 그러나 삭제 범위가 애플리케이션 코드에서 드러나지 않고, 현재 `ddl-auto` 기반의 개발·테스트·운영 스키마가 같은 cascade 설정을 갖는지도 별도로 보장해야 한다. ADR 0011과 같은 명시적 서비스 삭제 방식을 유지하기 위해 채택하지 않았다.

### 외래 키를 nullable로 변경하거나 작성자·멤버 정보를 익명화해 보존

활동 이력을 보존하면서 멤버십을 제거할 수 있다. 하지만 nullable 참조, 이름·프로필 스냅샷, 역사 조회 계약과 개인정보 처리 정책을 함께 설계해야 한다. 현재 이력 보존 요구가 없으므로 채택하지 않았다.

## 영향

### 긍정적 영향

- 별도의 상태 컬럼과 스키마 변경 없이 MVP 기능을 구현할 수 있다.
- 외래 키 의존 순서와 삭제 범위가 서비스 코드에 명시된다.
- 제거 직후 기존 멤버십 기반 접근 권한과 멤버 수에서 자연스럽게 제외된다.
- 과제·공지 원본과 다른 멤버의 활동 데이터는 유지된다.
- 트랜잭션을 통해 부분 삭제와 고아 데이터를 방지할 수 있다.

### 부정적 영향과 위험

- 제거된 멤버의 제출 내용, 공지 읽음 상태와 알림 이력을 복구할 수 없다.
- 해당 멤버를 제외하면서 과제 제출 수와 공지 읽음 수 같은 과거 집계 결과가 바뀔 수 있다.
- 탈퇴와 방출을 데이터에서 구분할 수 없다.
- 방출된 사용자도 유효한 초대 링크가 있으면 다시 가입할 수 있다.
- 새로운 엔티티가 `StudyMember`를 외래 키로 참조하면 제거 순서와 테스트를 함께 갱신해야 한다.
- bulk delete는 Persistence Context를 우회하므로 같은 트랜잭션에서 삭제된 자식 엔티티를 다시 사용하지 않아야 한다.

## 미확정 사항

- 없음. 활동 이력 보존과 재가입 제한은 MVP v1 미확정 사항이 아니라 명시적인 제외 범위다.

## 후속 작업

- 멤버 목록 조회, 방출과 탈퇴 API를 구현한다.
- 멤버 식별자 기준 Notification, NoticeRecipient와 AssignmentSubmission bulk delete를 구현한다.
- 대상 멤버 데이터만 삭제되고 다른 멤버 및 과제·공지 원본은 유지되는지 Repository 및 인수 테스트로 검증한다.
- 삭제 작업의 트랜잭션 롤백과 외래 키 무결성을 검증한다.
- Notion API 명세의 DELETE 성공 상태를 `204 No Content`로 수정하고 오류 계약을 보완한다.
- 활동 이력 보존, 재가입 제한 또는 리더 위임 요구가 생기면 Soft Delete와 멤버십 생명주기를 별도 ADR로 결정한다.
