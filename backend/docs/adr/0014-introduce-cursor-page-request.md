# 0014. 커서 페이지 요청을 값 객체로 관리한다

- 날짜: 2026-08-21
- 관련 이슈: 없음

## 배경

커서 페이지네이션을 사용하는 서비스마다 커서와 페이지 크기를 개별 값으로 전달하고, 다음 페이지 확인을 위해
`size + 1`을 직접 계산한다. 응답을 만들 때도 같은 페이지 크기를 다시 전달하므로 조회 크기와 응답 크기가 서로 달라질 수
있고, 페이지 크기 검증이 진입점마다 반복된다. 상한 없이 큰 값을 허용하면 데이터베이스 조회와 응답 생성 비용이 과도하게
증가하며 `Integer.MAX_VALUE + 1`은 오버플로를 일으킨다.

## 결정

- 커서와 페이지 크기를 `CursorPageRequest` 값 객체로 묶는다.
- 커서는 생략하거나 양수여야 한다.
- 페이지 크기는 1 이상 100 이하로 제한한다.
- 다음 페이지 확인을 위한 조회 크기는 `CursorPageRequest.fetchSize()`에서 계산한다.
- 외부 요청은 Controller의 Bean Validation으로 검증하여 기존 공통 400 오류 응답을 유지한다.
- 서비스는 저장소를 조회하기 전에 `CursorPageRequest`를 생성하여 방어적으로 검증한다.
- `CursorPageResponse`는 개별 페이지 크기 대신 검증된 `CursorPageRequest`를 사용한다.
- Repository는 페이지 요청 값 객체에 의존하지 않고 기존처럼 `Pageable`과 쿼리 조건을 받는다.

## 선택 이유

커서 페이지네이션에 함께 사용되는 값과 연산을 하나의 객체가 관리하면 서비스마다 검증과 `size + 1` 계산을 반복하지 않아도
된다. 조회와 응답이 같은 요청 객체를 사용하므로 서로 다른 페이지 크기를 전달하는 실수를 방지할 수 있다. 최대 크기를
100으로 제한하면 한 요청이 생성할 수 있는 조회 및 응답 비용을 예측할 수 있고, 상한 검증 뒤 조회 크기를 계산하므로 정수
오버플로도 방지된다.

## 검토한 대안

### 서비스마다 cursor와 size를 개별 값으로 사용한다

새 타입이 필요 없지만 페이지네이션을 사용하는 서비스마다 검증, 조회 크기 계산과 응답 크기 전달이 반복된다. 규칙 변경 시
모든 사용처를 함께 수정해야 하므로 채택하지 않았다.

### Controller에서만 페이지 크기를 검증한다

HTTP 요청은 보호할 수 있지만 서비스가 다른 진입점에서 호출되거나 Controller 검증이 누락되면 큰 페이지 요청과 오버플로를
방지할 수 없다. 값 객체에서도 동일한 범위를 보장하기로 했다.

### 요청한 페이지 크기를 최대값으로 자동 조정한다

서버 부하는 제한할 수 있지만 클라이언트 요청을 조용히 다른 값으로 변경한다. 잘못된 요청을 명시적인 400 오류로 알리는
현재 API 정책과 맞지 않아 채택하지 않았다.

## 영향

### 긍정적 영향

- 페이지네이션 값과 연산의 중복을 줄인다.
- 조회 크기와 응답 크기가 하나의 요청 객체를 기준으로 일치한다.
- 과도한 조회와 정수 오버플로를 진입점과 서비스 양쪽에서 방지한다.

### 부정적 영향과 위험

- 페이지네이션을 사용하는 서비스는 `CursorPageRequest`를 생성해야 한다.
- 최대 페이지 크기를 변경하려면 외부 API 계약과 부하 영향을 함께 검토해야 한다.
