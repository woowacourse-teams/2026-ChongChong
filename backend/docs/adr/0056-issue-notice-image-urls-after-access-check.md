# 0056. 공지 첨부 조회 URL은 조회 권한 확인 후 발급한다

- 날짜: 2026-10-22
- 관련 이슈: [#561](https://github.com/woowacourse-teams/2026-ChongChong/issues/561)
- 적용 상태: OpenAPI 명세 작성 완료, 백엔드 구현 전
- 후속 구체화: [ADR-0055](0055-connect-completed-files-to-notices.md)의 공지 이미지 조회 URL 제공
- 관련 결정: [ADR-0052](0052-use-presigned-urls-for-file-uploads.md)의 클라이언트와 S3 간 직접 파일 전송

## 배경

공지는 업로드 완료 파일을 연결할 수 있지만 상세 응답에는 첨부 메타데이터만 있어 이미지를 표시할 수 없다.
과제·제출물은 이미 공통 FileImageUrlGenerator로 조회용 S3 presigned GET URL을 발급하고 있다.
공지도 같은 기반을 재사용하되, 파일 소유권과 공지 열람 권한을 구분하고 URL의 유효기간을 응답 계약에 반영해야 한다.

## 결정

### 공지 상세 조회 권한을 확인한 뒤 URL을 발급한다

기존 GET /api/studies/{studyId}/notices/{noticeId} 응답의 attachments에 imageUrl을 추가한다.
요청자의 스터디 소속을 확인하고 공지를 studyId·noticeId로 조회한 뒤, 그 공지에 연결된 첨부의 URL을 발급한다.
인증 실패·스터디 외부 사용자·다른 스터디 경로·공지 없음으로 거부하는 요청에서는 URL을 생성하지 않는다.

파일 업로더와 조회자가 같은지는 요구하지 않는다. 현재 스터디원은 가입 전 공지와 이전 리더 소유의 첨부도
기존 권한대로 열람할 수 있다. 파일 소유자라도 현재 스터디원이 아니면 공지 첨부를 조회할 수 없다.

### 서비스가 공통 생성기를 호출하고 DTO는 결과를 전달한다

공지 서비스는 권한과 공지 존재 확인 후 FileImageUrlGenerator를 호출하고 응답 DTO에 URL을 전달한다.
DTO는 S3Presigner나 FileImageUrlGenerator에 의존하지 않는다. 과제·제출물 서비스를 호출하거나
별도의 파일 조회 endpoint를 만들지 않으며, 공통 생성기의 버킷·서명·inline 응답 설정을 재사용한다.

기존 fileId·originalFileName·contentType·size·sortOrder와 첨부 순서를 유지한다.
imageUrl은 항상 포함하는 nullable URI다. 공통 생성기가 지원하는 image/jpeg·image/png·image/webp는
조회 URL을 반환하고, 그 외 contentType은 null을 반환한다. 무첨부는 기존처럼 빈 배열이다.
null 계약은 공통 생성기의 반환 정책을 따르는 것으로, 공지의 신규 첨부 허용 형식을 확대하지 않는다.

조회용 URL은 응답 시 생성하며 DB에 저장하지 않는다. 파일 상태·첨부 관계·수신 상태는 변경하지 않는다.
서명 생성 과정에서 S3 객체의 존재·크기를 재조회하거나 업로드 완료 API를 호출하지 않는다.
URL 생성 성공은 S3 객체의 현재 존재나 실제 파일 내용이 이미지임을 보장하지 않는다.

### 공통 유효기간을 적용하고 상세 재조회로 갱신한다

조회용 URL은 기존 aws.s3.url-validity 설정을 따른다. 기본값은 10분이며 AWS_URL_VALIDITY로 변경한다.
이번 결정에서는 공지 전용 유효기간 설정이나 expiresAt 필드를 추가하지 않는다.
클라이언트는 URL을 이미지 src로 사용하고 영구 파일 식별자로 저장하지 않는다.
만료 시 공지 상세를 다시 조회하여 권한 확인과 URL 발급을 다시 거친다.

각 재조회에서 서명 생성을 수행하지만, 같은 시각에 발급한 URL이 반드시 다른 문자열이라는 계약은 두지 않는다.
프론트의 응답 검증·이미지 표시·재조회 연결은 [#557](https://github.com/woowacourse-teams/2026-ChongChong/issues/557)의 연동 작업에서 처리한다.

## 선택 이유

공지 상세 요청 한 번으로 메타데이터와 이미지 조회 URL을 받을 수 있고, 기존 공지 권한 검사를 그대로 활용한다.
파일 소유권을 열람 권한으로 잘못 사용하지 않으면서 과제·제출물과 동일한 URL 발급 방식을 유지한다.
공통 생성기를 재사용해 새로운 저장 구조·발급 설정·파일 조회 API 없이 이미지 표시를 지원한다.

## 검토한 대안

### fileId로 조회 URL을 발급하는 별도 API를 만든다

다양한 도메인에서 독립적으로 재발급할 수 있지만 파일이 연결된 공지·과제·제출물의 권한을 별도로 판별해야 한다.
현재 요구는 공지 상세의 이미지 표시이므로 기존 공지 조회 경로에서 처리한다.

### 서버가 이미지 본문을 대신 전송한다

매 요청에서 애플리케이션 권한을 확인할 수 있지만 파일 전송량과 S3 응답 대기가 서버에 추가된다.
현재의 클라이언트와 S3 간 직접 전송 구조와 공통 조회 URL 생성기를 활용한다.

## 영향

### 긍정적 영향

- 공지 상세 응답으로 첨부 이미지를 표시할 수 있으며 기존 첨부 메타데이터와 조회 권한을 유지한다.
- File 도메인의 기존 구현을 재사용하고 DTO에는 응답 조립 책임만 남긴다.
- 조회 시 S3 파일 검증이나 DB 상태 변경을 추가하지 않는다.

### 부정적 영향과 위험

- 클라이언트가 nullable imageUrl과 URL 만료 후 재조회 흐름을 처리해야 한다.
- URL을 전달받은 사용자는 유효한 동안 해당 URL로 조회할 수 있어, 스터디 탈퇴·권한 변경 시 이미 발급된 URL의 즉시 철회를 보장하지 않는다.
- 업로드와 조회 URL이 같은 유효기간 설정을 사용하므로 설정 변경 시 두 흐름을 함께 고려해야 한다.
- 서명 URL과 실제 S3 조회 권한·객체 접근은 로컬 응답 계약 테스트만으로 확인할 수 없어 dev에서 별도로 검증해야 한다.

## 미확정 사항

- 프론트에서 URL 만료를 처리하는 구체적인 재조회·표시 UX는 프론트 연동에서 정한다.
- 실제 파일 내용 검증과 미사용 파일 정리는 이번 결정과 구분하는 공통 File 후속 작업이다.

## 후속 작업

- 공지 상세 서비스와 응답 DTO를 imageUrl 계약에 맞게 연결한다.
- 다중 첨부·무첨부·이전 리더 파일·가입 전 공지 열람과 권한 거부 시 URL 미생성을 검증한다.
- 조회 후 파일 상태·첨부 관계·수신 상태 보존과 서명 URL·null 응답 계약을 검증한다.
- 전체 backend·OpenAPI 검증 후 dev에서 반환된 URL로 실제 이미지 조회를 확인한다.
