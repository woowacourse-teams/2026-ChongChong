# 0057. 댓글 원문을 resourceType과 resourceId로 참조한다

- 날짜: 2026-10-30
- 상태: 채택
- 관련 이슈: 없음
- 관련 정책: [댓글 정책](../comment-policy.md)
- 관련 ADR: [0024. 하드 삭제 시 데이터베이스 외래 키 CASCADE로 종속 데이터를 삭제한다](0024-use-database-cascades-for-hard-delete.md),
  [0038. 논리 알림과 Web Push 전달을 NotificationDelivery 파이프라인으로 분리한다](0038-separate-logical-notifications-and-web-push-delivery.md),
  [0045. 자원 삭제 시 관련 인앱 알림을 삭제한다](0045-delete-notifications-with-resources.md)

## 배경

공지, 과제, 제출물에 같은 본문·수정·삭제·조회 규칙을 적용하는 댓글 기능을 추가한다.
기존 `Notification`은 `resourceType`과 `resourceId`로 이 세 종류의 원문을 식별하고,
원문 삭제 시 애플리케이션이 관련 알림을 명시적으로 정리한다.

댓글의 원문 참조에도 같은 식별 방식을 사용할지, 대상별 댓글 테이블을 나눌지,
하나의 댓글 테이블에 원문 외래 키 세 개를 둘지 선택해야 한다.
외래 키를 사용하면 원문 존재와 삭제를 DB가 보장하지만, 대상이 늘 때마다 컬럼과 제약을 변경해야 한다.
다형 참조는 기존 알림과 형식을 통일할 수 있는 대신 삭제 정합성을 애플리케이션이 책임져야 한다.

## 결정

### 하나의 댓글 테이블에서 원문을 종류와 ID로 식별한다

- 댓글은 하나의 테이블에 저장한다.
- `resourceType`은 `NOTICE`, `ASSIGNMENT`, `ASSIGNMENT_SUBMISSION` 중 하나다.
- `resourceId`는 해당 종류의 원문 ID다. 두 값은 필수이며 ID는 양수여야 한다.
- 저장 컬럼은 `resource_type`, `resource_id`로 표현한다.
- 원문별 `notice_id`, `assignment_id`, `submission_id` 외래 키 컬럼은 두지 않는다.
- 댓글을 조회·수정·삭제할 때는 원문 종류와 ID를 함께 조건으로 사용한다.

이 결정은 댓글과 알림의 원문 식별 형식을 통일하는 결정이다.
두 도메인이 같은 Java enum을 직접 공유할지, 그 타입을 어느 패키지에 둘지는 구현 설계에서 정한다.
기존 엔티티 사이의 외래 키와 DB CASCADE 규칙은 변경하지 않는다.

### 원문 존재와 삭제 정합성은 애플리케이션이 보장한다

`resourceId`에는 여러 원문 테이블을 동시에 참조하는 일반 외래 키를 설정하지 않는다.
애플리케이션은 원문의 존재와 요청한 스터디·과제 범위에 속하는지 확인하고 기존 조회 권한 규칙을 적용한다.

원문 삭제와 해당 댓글·관련 논리 알림 삭제는 같은 데이터베이스 트랜잭션에서 수행한다.
하위 원문이 삭제되는 경우에는 그 원문을 가리키는 댓글도 정리해야 한다.
삭제 대상 식별에 원문 행이 필요하면 그 행이 사라지기 전에 정리 범위를 확보한다.

다음 경로를 모두 포함한다.

- 공지·과제의 직접 삭제와 스터디 삭제.
- 과제 삭제에 따른 하위 제출물 삭제.
- 스터디 탈퇴·방출과 회원 탈퇴에 따른 제출물 CASCADE 삭제.
- 과제 제출 대상 변경에 따른 제출물 `orphanRemoval` 삭제.
- 개별 댓글 삭제에 따른 관련 알림 삭제.

같은 트랜잭션이라는 사실만으로 생성·삭제 경합이 해결되지는 않는다.
원문 존재 확인 후 삭제가 진행되거나, 댓글 정리 후 새 댓글이 저장되는 경합에서도
고아 댓글과 관련 알림이 남지 않도록 작성 경로와 삭제 경로가 일관된 동시성 제어를 사용해야 한다.
DB CASCADE로 삭제되는 제출물의 정리를 JPA 엔티티 삭제 콜백에만 의존하지 않는다.

논리 알림 삭제에 따른 `NotificationDelivery` CASCADE와 트랜잭션 밖 Web Push 전달은 기존 결정을 따른다.
이미 전달됐거나 삭제와 동시에 외부 전달이 진행 중인 푸시는 회수하지 못한다.

### 작성자와 원문의 생명주기를 구분한다

원문에 대한 다형 참조는 작성자와의 연결 방식과 별개다.
스터디 탈퇴·방출 또는 회원 탈퇴만으로 원문이 남은 댓글을 삭제하지 않는다.
작성자 연결을 해제하고 `탈퇴한 스터디원`과 기본 이미지로 표시하는 정책을 유지한다.
다른 수신자가 받은 관련 알림도 원문과 댓글이 남아 있으면 유지한다.

탈퇴로 제출물 자체가 삭제되면 그 안의 댓글과 관련 알림은 작성자와 관계없이 삭제한다.
원문 삭제 정책이 작성자 탈퇴 후 댓글 보존 정책보다 우선한다.

## 선택 이유

댓글과 기존 알림이 같은 원문 식별 형식을 사용하면 원문 종류와 ID를 같은 방식으로 이해하고 다룰 수 있다.
대상별 댓글의 공통 규칙을 하나의 저장 구조에 모으고, 새 원문 종류가 추가될 때마다 대상 FK 컬럼을 늘리지 않아도 된다.
기존 알림에서 사용하는 다형 참조와 명시적 삭제 처리 경험을 활용할 수 있다.

이번 선택은 DB가 제공하는 원문 참조 무결성보다 기존 구조와의 일관성을 우선한다.
기존 알림과 컬럼 형식이 같다는 이유로 댓글 삭제까지 자동으로 처리되는 것은 아니며,
누락 없는 삭제 경로와 동시성 검증을 구현 범위에 포함한다.

## 검토한 대안

### 대상별 댓글 테이블을 세 개로 나눈다

각 테이블에 필수 원문 FK를 둘 수 있고 대상별 기능이 달라지면 독립적으로 변경하기 쉽다.
하지만 현재 댓글 규칙은 공통이며 엔티티, Repository, 조회 쿼리와 마이그레이션을 세 구조에서 관리해야 한다.
공통 코드 공유만으로 없어지지 않는 영속 구조의 반복을 피하기 위해 채택하지 않는다.

### 하나의 댓글 테이블에 원문 FK 세 개 중 하나를 둔다

DB가 원문 존재와 CASCADE 삭제를 보장하고, 멤버 삭제나 과제 수정으로 원문이 사라지는 경로에도 적용할 수 있다.
현재처럼 대상이 세 종류인 범위에는 적절한 대안이다.

다만 nullable FK 세 개와 정확히 하나만 연결하는 CHECK 제약이 필요하고,
대상이 추가되면 FK 컬럼·제약·인덱스를 변경해야 한다.
이번에는 기존 알림과 원문 식별 형식을 통일하는 이점을 우선하여 채택하지 않는다.

## 영향

### 긍정적 영향

- 댓글과 기존 알림이 원문 종류와 ID를 같은 형식으로 표현한다.
- 세 대상의 공통 댓글 동작을 하나의 저장 구조에서 관리할 수 있다.
- 새 원문 종류마다 대상 FK 컬럼을 추가할 필요가 없다.

### 부정적 영향과 위험

- 원문의 존재와 삭제를 DB 외래 키가 보장하지 않으므로 애플리케이션 누락으로 고아 댓글이 생길 수 있다.
- 직접 삭제 외에 DB CASCADE와 JPA 고아 객체 제거 경로까지 명시적인 정리에 포함해야 한다.
- 생성·삭제 경합은 트랜잭션 선언만으로 해결되지 않으며 동시성 제어와 실제 DB 검증이 필요하다.
- 향후 원문 FK 방식으로 전환하면 기존 참조 데이터 점검·정리와 FK 컬럼 이관이 필요하다.

## 미확정 사항

작성·삭제 잠금 대상과 획득 순서, 작성자 연결 해제와 댓글·알림 매핑 및 삭제 순서는
2026-10-30 [댓글 구현 명세](../comment-implementation.md)에서 구체화했다.
이 ADR의 원문 참조 선택은 유지하며, 실제 DB 동작 검증은 후속 구현 단계에서 수행한다.

## 후속 작업

- 댓글 정책과 이 결정을 기준으로 저장·조회·권한·삭제 interface와 동시성 제어를 구현 명세에 구체화한다.
- 모든 원문 삭제 경로에서 댓글·알림을 같은 트랜잭션으로 정리하고, 원문이 남은 탈퇴자 댓글은 보존한다.
- 댓글 정리에 필요한 조회 조건과 인덱스를 마이그레이션에 반영한다.
- ADR 0003과 ADR 0031에 따라 삭제 범위·롤백·탈퇴 후 보존과 PostgreSQL 생성·삭제 경합을 검증한다.
