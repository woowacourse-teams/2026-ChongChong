# 0004. 에러 응답과 에러 코드 형식을 통일한다

- 날짜: 2026-08-15
- 관련 이슈: [#29](https://github.com/woowacourse-teams/2026-ChongChong/issues/29)

## 배경

도메인마다 에러 응답과 코드 형식이 다르면 클라이언트가 API별 예외 처리를 구현해야 한다. HTTP 상태, 애플리케이션 에러
코드와 메시지의 역할을 구분하고, 하나의 요청에서 여러 필드가 실패할 수 있는 입력값 검증 에러를 일관된 형태로 제공해야
한다. 예상하지 못한 예외에서는 내부 구현 정보가 노출되지 않아야 한다.

## 결정

모든 에러 응답은 `code`와 `message`를 포함한다. HTTP 상태는 응답 본문의 `status` 필드로 중복하지 않고 HTTP 응답
상태 코드로 전달한다.

### 비즈니스 에러

```json
{
  "code": "USER_NOT_FOUND",
  "message": "존재하지 않는 사용자입니다."
}
```

### 입력값 검증 에러

```json
{
  "code": "INVALID_INPUT_VALUE",
  "message": "입력값이 올바르지 않습니다.",
  "errors": [
    {
      "field": "email",
      "reason": "이메일 형식이 올바르지 않습니다."
    },
    {
      "field": "password",
      "reason": "비밀번호는 8자 이상이어야 합니다."
    }
  ]
}
```

- `errors`는 필드 단위 검증 실패에만 포함한다. 각 항목은 클라이언트가 입력 필드를 식별할 수 있는 `field`와 실패 이유인
  `reason`을 갖는다.
- 하나의 입력에서 여러 필드가 실패하면 모든 필드 에러를 `errors` 배열에 담는다.
- 비즈니스 에러와 요청 본문 파싱 실패처럼 필드 목록이 의미 없는 에러에는 `errors`를 포함하지 않는다.
- `timestamp`는 운영 과정에서 응답만으로 발생 시점을 식별해야 할 필요가 확인되기 전까지 포함하지 않는다. 도입한다면
  일부 에러에만 추가하지 않고 모든 에러 응답에 동일한 ISO 8601 형식과 시간대로 적용한다.
- 예상하지 못한 예외는 서버에 원인과 스택 트레이스를 기록하되, 응답에는 예외 메시지나 내부 정보를 노출하지 않는다.

에러 코드는 대문자 스네이크 표기법을 사용한다.

- 도메인 에러: `{DOMAIN}_{REASON}` 형식을 사용한다. 예: `USER_NOT_FOUND`, `STUDY_ALREADY_CLOSED`.
- 공통 에러: 특정 도메인 이름을 붙이지 않고 요청 실패의 의미를 표현한다. 예: `INVALID_INPUT_VALUE`,
  `INVALID_REQUEST`, `INTERNAL_SERVER_ERROR`.
- 숫자 코드(`USER_001`)는 코드만으로 의미를 알기 어렵기 때문에 사용하지 않는다.
- `NOT_FOUND_USER`처럼 이유를 앞에 두지 않고 도메인을 먼저 표기해 관련 코드를 함께 찾을 수 있게 한다.
- 각 에러 코드는 대응하는 HTTP 상태와 기본 메시지를 정의한다. 같은 코드를 서로 다른 HTTP 상태로 반환하지 않는다.

## 선택 이유

HTTP 상태를 본문에 반복하지 않으면 서로 불일치할 가능성을 없앨 수 있다. 의미 기반 코드는 로그와 클라이언트 코드에서
문제를 바로 식별할 수 있고, 도메인을 앞에 두면 관련 에러가 자연스럽게 묶인다. `errors`를 검증 에러에만 선택적으로
추가하면 단일 에러와 복수 필드 에러를 하나의 기본 규격으로 표현할 수 있다.

## 검토한 대안

### 본문에 HTTP `status` 포함

본문만 보아도 상태를 확인할 수 있지만 HTTP 응답 상태와 같은 정보를 중복하며 두 값이 달라질 위험이 있다.

### 숫자 기반 에러 코드

코드 길이가 짧고 외부 메시지와 독립적이지만 별도 문서를 조회하지 않으면 의미를 알기 어렵고 코드 리뷰에서 의도를
파악하기 어렵다.

### 모든 응답에 `timestamp` 포함

장애 발생 시각을 클라이언트 응답에서 확인할 수 있지만 서버 로그의 요청 식별자와 시각으로 추적할 수 있다면 모든 응답의
크기와 계약만 늘어난다. 운영상 필요가 확인되면 일관된 형식으로 도입한다.

## 영향

### 긍정적 영향

- 클라이언트가 모든 API 에러를 공통 로직으로 처리할 수 있다.
- 코드 이름만으로 에러의 도메인과 원인을 파악할 수 있다.
- 예상하지 못한 예외의 내부 정보 노출을 방지할 수 있다.

### 부정적 영향과 위험

- 에러 코드와 HTTP 상태 및 메시지를 중앙에서 일관되게 관리해야 한다.
- 에러 코드 이름을 변경하면 클라이언트와의 계약이 깨질 수 있다.
- 복합 객체나 배열 입력의 `field` 경로 표현 규칙이 없으면 클라이언트 해석이 달라질 수 있다.

## 미확정 사항

- 운영 추적에 `timestamp` 또는 별도의 요청 식별자가 필요한지 운영·로깅 전략과 함께 결정해야 한다.
- 중첩 객체와 배열의 검증 실패를 `field`에 어떤 경로 형식으로 표현할지 결정해야 한다.

## 후속 작업

- 공통 에러 코드 인터페이스와 공통 에러 코드 목록을 이 규격에 맞춰 구현한다.
- 비즈니스 예외, 입력값 검증 실패, 읽을 수 없는 요청 및 예상하지 못한 예외를 전역 예외 처리기에서 변환한다.
- 대표 비즈니스 에러와 입력값 검증 에러의 HTTP 상태 및 응답 본문을 인수 테스트로 검증한다.
