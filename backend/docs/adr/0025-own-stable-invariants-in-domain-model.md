# 0025. 모든 생성 경로에서 성립할 불변식은 도메인 모델이 보호한다

- 날짜: 2026-09-02
- 관련 이슈: [#243](https://github.com/woowacourse-teams/2026-ChongChong/issues/243)
- 관련 ADR: [0003. 백엔드 테스트 범위와 역할을 정의한다](0003-define-backend-test-strategy.md),
  [0006. 공통 예외 처리 타입의 책임을 분리한다](0006-design-common-exception-types.md)

## 배경

과제와 공지의 제목·내용, 제출물의 내용·링크처럼 일부 규칙은 엔티티의 생성 및 변경 메서드가 직접 검증한다. 반면
`Study` 이름, `User` 이름과 `PushToken`의 필드는 요청 DTO나 호출자가 유효한 값을 전달한다고 가정한다. 같은
영속 모델이 aggregate마다 서로 다른 검증 기준을 사용하고 있다.

HTTP 요청만 엔티티를 생성하는 동안에는 Request DTO의 Bean Validation으로 빈 값을 거를 수 있다. 그러나 배치, 이벤트,
관리 도구와 테스트 fixture처럼 Controller를 거치지 않는 진입점이 추가되면 유효하지 않은 상태가 엔티티 생성자까지
도달할 수 있다. 데이터베이스의 `NOT NULL`과 길이 제약은 저장 시점에야 실패하므로 도메인 오류를 일관된 예외로 설명하기도
어렵다.

`StudyMember.isLeader()`가 nullable인 `role`에 인스턴스 메서드를 호출하는 것도 같은 문제를 드러낸다. 정상 생성
경로에서는 `role`이 필수지만 fixture나 프레임워크용 기본 생성자로 만들어진 불완전한 객체에서는 권한 검사 중
`NullPointerException`이 발생할 수 있다.

## 결정

### 입구 검증과 도메인 불변식을 목적에 따라 구분한다

- Controller의 Request DTO는 필수 필드 누락, 문자열 형식, 요청 컬렉션의 원소 형식처럼 전송 계층에서 해석할 수 있는
  입력 오류를 검증한다.
- 엔티티는 HTTP, 배치, 이벤트, fixture 등 호출 경로와 무관하게 모든 생성·변경 경로에서 항상 성립해야 하는 상태를
  보호한다.
- 같은 조건이 입구와 엔티티에 함께 존재할 수 있다. 입구 검증은 필드별 오류를 빠르게 응답하기 위한 것이고, 엔티티
  검증은 유효하지 않은 도메인 객체가 만들어지는 것을 막기 위한 것이므로 중복의 목적이 다르다.
- 데이터베이스 제약은 동시성이나 외부 쓰기를 포함한 마지막 무결성 방어선으로 사용하며 엔티티 검증을 대신하지 않는다.

### 필수 상태는 공개된 모든 생성·변경 경로에서 검증한다

- 이름, 역할, 연관 엔티티처럼 객체가 존재하는 동안 반드시 필요한 값은 정적 팩터리 또는 생성자에서 검증한다.
- 변경 가능한 필드는 최초 생성과 변경 메서드에 같은 규칙을 적용한다. 규칙 구현은 엔티티 내부의 하나의 검증 메서드로
  모아 생성과 변경의 기준이 달라지지 않게 한다.
- 검증 실패는 해당 도메인의 `BusinessException`과 `ErrorCode`로 표현한다. Bean Validation 예외나 데이터베이스 예외가
  도메인 계층의 계약이 되지 않게 한다.
- JPA가 요구하는 `protected` 기본 생성자는 프레임워크 전용 경로로 본다. 애플리케이션과 테스트는 기본 생성자나
  reflection으로 불완전한 엔티티를 직접 만들지 않고 공개된 정적 팩터리를 사용한다.

### 권한 판별은 불완전한 상태에서도 안전하게 실패한다

- `StudyMember.role`은 생성 시 null을 허용하지 않는 불변식으로 보호한다.
- `isLeader()`처럼 권한 허용 여부를 반환하는 메서드는 enum 상수 기준으로 비교하여 예기치 않은 null 상태에서도 예외로
  요청 처리가 중단되지 않고 권한을 허용하지 않는 방향으로 실패하게 한다.
- null을 정상적인 `MEMBER` 상태로 간주하지 않는다. 생성 경로의 검증과 테스트를 통해 null 상태 자체는 계속 결함으로
  다룬다.

### 값 객체는 규칙과 행위를 응집할 실익이 있을 때만 도입한다

- 여러 엔티티에서 같은 규칙을 공유하거나, 여러 원시 값이 하나의 개념을 이루거나, 타입으로 잘못된 값의 전달을 막아야
  하거나, 정규화·비교 같은 행위가 함께 있을 때 값 객체를 고려한다.
- 단순한 null·공백 검증 하나만 있고 재사용이나 독립 행위가 없는 필드는 엔티티 내부 검증으로 보호한다.
- 모든 문자열과 식별자를 일괄적으로 값 객체로 감싸지 않는다. 값 객체 도입 여부는 변경 이유와 오류 의미가 독립적인지를
  기준으로 각 aggregate에서 판단한다.

## 선택 이유

엔티티가 안정적인 불변식을 보호하면 호출자는 어떤 진입점을 사용하더라도 유효한 객체만 받는다. 검증 실패가 저장보다
가까운 생성·변경 지점에서 발생하므로 원인을 찾기 쉽고, 도메인별 예외 계약도 유지할 수 있다.

입구 검증을 함께 유지하면 클라이언트는 여러 필드 오류를 한 번에 확인할 수 있다. 두 검증의 목적을 구분하면 HTTP 응답
품질을 유지하면서 Controller를 거치지 않는 경로의 무결성도 보장할 수 있다.

값 객체를 규칙의 복잡도와 재사용 필요에 따라 선택하면 의미 있는 타입은 얻되, 단순 필드마다 파일과 변환 코드를 추가하는
비용은 피할 수 있다.

## 검토한 대안

### Request DTO에서만 검증한다

HTTP 요청의 오류를 빠르게 반환하고 엔티티 코드가 짧아진다. 하지만 Controller를 거치지 않는 생성 경로가 같은 검증을
반복해야 하고, 호출자가 누락하면 유효하지 않은 엔티티가 생성되므로 선택하지 않았다.

### 데이터베이스 제약에만 맡긴다

모든 영속화 경로를 마지막에 차단할 수 있다. 그러나 실패 시점이 늦고 제약 위반을 도메인 오류로 해석하기 어려우며,
저장 전 메모리 상태에서는 불변식이 깨진 객체가 존재할 수 있어 선택하지 않았다.

### 모든 필드를 값 객체로 표현한다

컴파일 시점 타입 구분과 검증 재사용 범위가 넓어진다. 현재 단순 필드까지 모두 감싸면 타입, JPA 변환과 DTO 매핑이
과도하게 늘어나므로 일괄 적용하지 않는다.

## 영향

### 긍정적 영향

- HTTP 이외의 진입점에서도 같은 도메인 불변식이 적용된다.
- 유효하지 않은 상태가 영속화 전에 도메인별 예외로 실패한다.
- aggregate마다 달랐던 생성·변경 검증의 기준이 일관된다.
- 권한 판별이 불완전한 상태에서 권한을 허용하지 않는 방향으로 동작한다.
- 값 객체가 필요한 기준과 불필요한 기준이 명확해진다.

### 부정적 영향과 위험

- Request DTO와 엔티티에 의도적으로 같은 조건이 존재할 수 있다.
- 기존 fixture가 기본 생성자나 reflection에 의존한다면 공개 생성 경로를 사용하도록 수정해야 한다.
- 기존 데이터에 새 불변식을 위반하는 값이 있으면 적용 전에 데이터 확인과 보정이 필요하다.
- 값 객체 도입 기준에는 판단이 필요하므로 aggregate별 리뷰에서 근거를 확인해야 한다.

## 미확정 사항

없음.

## 후속 작업

- `Study`, `User`, `StudyMember`, `PushToken`의 생성·변경 경로와 데이터베이스의 기존 값을 점검한다.
- 필수 값과 각 도메인의 에러 코드를 정의하고 엔티티 생성 경로에 검증을 추가한다.
- `StudyMember.isLeader()`가 null 상태에서도 권한을 허용하지 않도록 비교 방식을 변경한다.
- 엔티티 단위 테스트에 정상 경계값과 잘못된 생성·변경 입력 사례를 추가한다.
- 새로운 aggregate를 리뷰할 때 입구 검증과 안정적인 도메인 불변식이 각각 보호되는지 확인한다.
