# 0009. 내 스터디 목록에서 스터디별 집계 쿼리를 사용한다

- 날짜: 2026-08-19
- 관련 이슈: 해당 없음

## 배경

`GET /studies/me`는 현재 사용자가 가입한 스터디를 가입 순서의 최신순으로 조회하고, 각 스터디의 멤버 수를 함께 반환한다.

현재 사용자당 가입 가능한 스터디는 최대 50개이고, 스터디 하나의 멤버 수는 최대 30명이다. 스터디 목록을 조회한 뒤 각 스터디의 멤버 수를 구하는 과정에서, 스터디마다 `countByStudyId` 쿼리를 실행하는 방식과 모든 스터디의 멤버 수를 `GROUP BY`로 한 번에 조회하는 방식을 비교해야 했다.

또한 공지 개수와 과제 개수는 현재 목 데이터이며, 추후 공지 확인 상태와 과제 제출 상태에 따라 사용자 역할별 집계 기준이 달라질 예정이다. 이 상태에서 모든 집계를 하나의 복잡한 프로젝션 쿼리로 묶으면 향후 도메인 구현에 따라 쿼리를 크게 수정해야 한다.

## 결정

현재 `GET /studies/me`의 멤버 수는 스터디별 개별 집계 쿼리로 조회한다.

- `StudyMember` 목록은 사용자의 가입 순서 최신순으로 조회한다.
- 스터디별 멤버 수는 목록을 순회하며 `StudyMemberRepository.countByStudyId(studyId)`를 호출한다.
- 현재 단계에서는 여러 스터디의 멤버 수를 `GROUP BY`로 묶는 커스텀 조회나 통합 프로젝션 쿼리를 추가하지 않는다.
- 이 결정은 현재 구현 가능한 멤버 수 집계에만 적용한다. 공지·과제의 실제 역할별 집계가 구현되면 해당 집계 방식은 별도로 재검토한다.

## 선택 이유

현재 최대 50개의 스터디만 조회하므로, 한 요청에서 발생하는 추가 멤버 수 쿼리도 최대 50개로 범위가 제한된다. 각 스터디의 최대 멤버 수 역시 30명으로 제한되어 있어, 현재 요구사항과 데이터 규모에서는 개별 쿼리의 비용을 감수할 수 있다고 판단했다.

개별 집계 쿼리는 서비스 코드의 흐름이 단순하고, 멤버 수라는 한 가지 값을 조회하는 저장소 메서드의 책임도 명확하다. 반면 `GROUP BY` 조회는 스터디 ID 목록을 전달하고 결과를 ID별로 매핑하는 코드가 추가되며, 현재 목 데이터인 공지·과제 집계까지 함께 묶을 경우 역할별 조건과 여러 도메인의 책임이 하나의 쿼리에 결합될 수 있다.

## 검토한 대안

### `GROUP BY`를 사용한 일괄 집계

`study_id IN (...) GROUP BY study_id` 형태로 모든 스터디의 멤버 수를 한 번에 조회하면 데이터베이스 왕복 횟수와 쿼리 수를 줄일 수 있다. 다만 조회 결과를 스터디 ID와 매핑하는 로직과 전용 프로젝션이 필요하고, 현재의 제한된 데이터 규모에서는 그 복잡성이 얻는 이점보다 크다고 판단해 채택하지 않았다.

### 모든 응답 필드를 하나의 프로젝션 쿼리로 조회

스터디 정보와 멤버 수, 공지 수, 과제 수를 하나의 조회로 반환하는 방법이다. 조회 횟수는 줄일 수 있지만, 공지 확인 여부와 과제 제출 여부가 역할에 따라 달라지고 관련 도메인이 아직 구현되지 않았다. 여러 도메인의 집계 기준과 변경 주기가 하나의 쿼리에 결합되므로 현재 단계에는 적합하지 않다.

### 연관관계 조회만으로 해결

`StudyMember`와 `Study`를 함께 조회하면 스터디 목록을 가져올 때 발생하는 지연 로딩 문제는 줄일 수 있다. 그러나 멤버 수는 별도의 집계값이므로 연관관계를 함께 조회하는 것만으로 스터디별 멤버 수 집계 쿼리까지 제거할 수는 없다.

## 영향

### 긍정적 영향

- 현재 요구사항에 필요한 코드와 쿼리 구조가 단순하다.
- 집계 책임이 `StudyMemberRepository`에 남아 도메인 간 쿼리 결합을 줄인다.
- 공지·과제 도메인이 구현될 때 각 집계 기준을 독립적으로 설계할 수 있다.
- 현재 제한된 데이터 규모에서 구현 복잡도를 늘리지 않고 기능을 완성할 수 있다.

### 부정적 영향과 위험

- 스터디 수에 비례해 멤버 수 집계 쿼리가 증가하는 N+1 형태가 남는다.
- 스터디 최대 개수나 목록 조회 범위가 커지면 응답 시간이 증가할 수 있다.
- 공지·과제의 실제 집계까지 같은 방식으로 개별 조회하면 요청 하나에서 발생하는 쿼리 수가 더 증가할 수 있다.

## 미확정 사항

- 실제 운영 데이터와 데이터베이스 실행 계획 기준의 성능은 아직 측정하지 않았다.
- 공지·과제의 역할별 미확인·미제출 집계가 구현된 뒤에도 개별 쿼리 방식을 유지할지는 정하지 않았다.

## 후속 작업

- 현재 구조를 유지하되, 스터디 수 제한 변경이나 목록 범위 확대 시 쿼리 수와 응답 시간을 확인한다.
- 모니터링 또는 성능 측정에서 병목이 확인되거나 공지·과제 실데이터 집계가 추가되면 `GROUP BY ... IN` 일괄 조회 또는 별도 조회 모델을 검토한다.
- 일괄 조회로 변경할 때는 기존 ADR을 수정하지 않고, 변경 이유와 기존 결정의 대체 관계를 새 ADR로 기록한다.
