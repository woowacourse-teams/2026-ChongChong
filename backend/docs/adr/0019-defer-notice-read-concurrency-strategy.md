# 0019. 공지 읽음 시각의 동시성 보장 방식을 후속 결정으로 유보한다

- 날짜: 2026-08-24
- 관련 이슈: [#88](https://github.com/woowacourse-teams/2026-ChongChong/issues/88)

## 배경

공지 수신자는 처음 읽은 시각을 `readAt`에 기록하고, 이후의 읽음 요청에서는 기존 시각을 유지한다. 현재 구현은
Transaction에서 조회한 Entity의 `readAt == null` 여부로만 최초 읽음을 판단하므로 순차 요청에서는 멱등성을 보장하지만,
동일한 수신자에 대한 요청이 서로 다른 Transaction에서 동시에 실행되는 상황은 보장하지 않는다.

두 Transaction이 모두 아직 읽지 않은 Entity를 조회하면 각각 다른 시각을 기록할 수 있고, 나중에 Commit된 값이 먼저
저장된 시각을 덮어쓸 수 있다. 이 경우 최초 읽은 시각을 보존한다는 의미와 두 요청이 같은 `readAt`을 반환한다는 계약이
깨진다.

## 결정

- 현재 공지 읽음 처리의 멱등성 보장 범위는 순차 요청으로 한정한다.
- 동일한 수신자의 동시 읽음 요청에서 최초 읽은 시각을 원자적으로 보존하는 방식은 이번 구현 범위에서 결정하지 않는다.
- 후속 결정에서는 비관적 쓰기 잠금과 `read_at IS NULL` 조건의 원자적 Update를 비교한다.
- 동시성 보장을 도입할 때는 저장된 최초 읽음 시각을 모든 요청의 응답으로 반환한다.
- 두 개의 독립된 Transaction에서 읽음 요청을 병렬 실행하고, 두 응답과 최종 저장된 `readAt`이 모두 같은지 실제
  데이터베이스를 사용하는 통합 테스트로 검증한다.

## 선택 이유

비관적 잠금과 조건부 Update는 모두 최초 읽음 시각을 보존할 수 있지만 잠금 범위, 추가 조회 횟수, Repository 책임과
데이터베이스별 동작에 서로 다른 영향을 준다. 현재는 동일 수신자에 대한 동시 요청 빈도와 실제 PostgreSQL에서의 경합
자료가 없으므로 특정 방식을 코드에 먼저 고정하지 않고, 요구되는 원자성 계약과 검증 조건을 기록한 뒤 별도 작업에서
결정한다.

## 검토한 대안

### 공지 수신자를 비관적 쓰기 잠금으로 조회한다

같은 수신자의 읽음 요청을 직렬화하므로 기존 Entity 상태 변경 흐름을 유지할 수 있다. 반면 읽음 요청마다 잠금을 획득하고
대기하므로 경합 시 처리량과 Transaction 시간이 영향을 받으며, 잠금 순서에 따라 교착 상태 가능성도 검토해야 한다.

### `read_at IS NULL` 조건으로 원자적 Update를 수행한다

`read_at`이 비어 있을 때만 갱신하므로 별도의 조회 시점과 무관하게 데이터베이스에서 최초 기록을 보호할 수 있다. 반면
Update 결과가 0건인 경우 이미 저장된 값을 다시 조회해 응답해야 하며, 영속성 Context와 벌크 Update의 상태를 일치시키는
방법을 함께 정해야 한다.

## 영향

### 긍정적 영향

- 이번 기능 범위에서 근거 없이 잠금 전략을 고정하지 않는다.
- 후속 구현이 충족해야 하는 원자성 계약과 통합 테스트 조건이 명확해진다.

### 부정적 영향과 위험

- 후속 결정 전까지 동일 수신자의 동시 읽음 요청에서는 최초 `readAt`이 덮어써질 수 있다.
- 현재 테스트는 순차 요청의 멱등성만 보장하며 다중 Transaction 동작을 보호하지 않는다.

## 미확정 사항

- 비관적 잠금과 조건부 Update 중 어떤 방식을 적용할지 결정하지 않았다.
- 조건부 Update를 선택할 경우 저장된 값을 반환하기 위한 조회 방식과 영속성 Context 동기화 방식을 결정해야 한다.

## 후속 작업

- 실제 PostgreSQL에서 두 방식을 비교하고 공지 읽음 처리의 동시성 전략을 별도 ADR로 결정한다.
- 선택한 전략을 구현한 뒤 두 독립 Transaction의 병렬 요청이 동일한 `readAt`을 반환하는 통합 테스트를 추가한다.
