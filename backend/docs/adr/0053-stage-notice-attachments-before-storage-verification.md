# 0053. 공지 첨부를 실제 업로드 검증과 분리해 단계적으로 구현한다

- 날짜: 2026-10-20
- 관련 이슈: [#542](https://github.com/woowacourse-teams/2026-ChongChong/issues/542)
- 원본 이슈: [#275](https://github.com/woowacourse-teams/2026-ChongChong/issues/275)
- 선행 결정: [ADR-0052](0052-use-presigned-urls-for-file-uploads.md)
- 부분 대체: 공지 검증기 호출·저장 시 완료 전환·제거 파일 재사용 금지는 [ADR-0055](0055-connect-completed-files-to-notices.md)에서 변경한다. 아래 본문은 1단계 당시 결정 기록이다.

## 배경

S3 Presigned PUT URL 발급과 사용자 소유 PENDING 메타데이터 저장은 구현되어 있다.
S3의 실제 업로드 결과 조회는 팀원이 별도로 구현할 예정이므로 공지 첨부의 도메인 구현과 테스트를
먼저 진행한다. 이 단계가 실제 파일 검증 없이 첨부를 완료 처리하는 경로가 되어서는 안 된다.

또한 공통 업로드 기반은 향후 사용자 프로필 이미지에서도 사용한다. 모든 파일에 스터디와 사용 목적을
미리 강제하면 스터디에 속하지 않는 프로필 이미지까지 같은 제약을 받는다.

## 결정

### 공지 첨부 저장과 실제 업로드 검증을 나누어 진행한다

1. 이번 작업(#542): 공지 생성·수정 요청의 attachmentFileIds로 첨부 목록과 표시 순서를 받고,
   상세 응답의 attachments로 파일 식별자·이름·형식·크기·순서를 제공한다. 첨부 관계 저장과 파일 상태 변경,
   파일 소유자·상태·이미지 정책 검증을 구현한다. 실제 업로드 검증은 인터페이스 호출까지만 준비한다.
   S3 조회가 연결되기 전에는 메타데이터 검증을 통과하더라도 새 파일 첨부에 503을 반환하고 전체 변경을 롤백한다.
2. 팀원 작업: S3 object key를 사용해 실제 파일의 존재·크기 등 업로드 결과를 조회하는 기능을 구현한다.
3. 후속 공지 작업: 실제 조회 기능을 공지 저장 시 호출하는 검증 인터페이스에 연결하고,
   업로드 성공·실패에 따른 저장과 롤백을 dev에서 통합 검증한 뒤 prod 배포를 판단한다.

이번 작업만으로 새 이미지를 첨부한 공지를 정상 저장하거나 화면에 이미지를 표시할 수 있는 것은 아니다.
첨부 없는 공지와 기존 첨부 유지·순서 변경·제거는 처리할 수 있으며, 파일 접근 URL 발급은 별도 후속 작업이다.

### 공통 파일과 도메인 연결을 분리한다

기존 FileMetadata의 User 소유자·파일명·object key·형식·크기·상태를 유지한다.
studyId, purpose, upload_assignment_id는 추가하지 않는다. 기존 업로드 준비 요청도 유지한다.
ADR-0052의 StudyMember 소유자 설명은 이 결정으로 구체화하여 User 소유자를 사용한다.
대상 스터디의 역할과 권한, 파일 형식·용량·개수는 공지 저장 시 검증한다.

notice_attachments에는 notice_id, file_id, sort_order를 저장한다. file_id 중복과 공지 내 순서 중복을 DB에서 막는다.
신규 파일 연결은 file_metadata 행을 ID 순서로 잠그고 PENDING인지 확인한다. 공지 수정·삭제도 공지 행 잠금을
사용한다. 다른 도메인의 후속 첨부 구현도 같은 파일 상태·잠금 계약을 따라야 중복 사용을 막을 수 있다.

### 실제 업로드 검증은 인터페이스로 분리한다

공지 첨부 서비스는 새 파일에 대해 UploadedFileVerifier.verify(FileMetadata)를 호출한다.
정상 반환은 실제 업로드 검증 성공을 뜻하며, 파일 미존재·크기나 형식 불일치·조회 실패는 예외로 전달한다.
실제 S3 조회는 팀원이 구현하고, 후속 공지 작업에서 이 인터페이스에 연결한다.

실제 업로드 검증을 연결하기 전의 기본 빈 UnavailableUploadedFileVerifier는 항상 FILE_VERIFICATION_UNAVAILABLE(503)을 반환한다.
환경 설정으로 이를 무조건 성공으로 바꾸는 옵션은 제공하지 않는다. 검증 성공 대체는 테스트의 Mockito 빈에만 둔다.
새 파일이 없는 요청, 기존 첨부 유지·순서 변경·제거는 이 검증을 호출하지 않는다.

### 저장은 한 트랜잭션으로 처리한다

모든 새 파일 검증에 성공한 뒤 공지·첨부 관계와 PENDING → COMPLETED 변경을 함께 저장한다.
한 파일이라도 실패하면 공지 내용·리마인드·첨부·파일 상태·알림을 부분 반영하지 않는다.
수정 시 기존 첨부 유지에는 현재 공지 수정 권한을 적용하며, 리더가 바뀌어도 기존 파일 유지가 가능하다.
새로 추가할 파일은 요청자 소유여야 한다.

제거한 파일은 DELETE_PENDING으로 전환하고 재사용을 금지한다. S3 물리 삭제·재시도는 후속 작업이다.
순서를 바꿀 때 기존 첨부 행 삭제를 먼저 flush한 뒤 새 순서로 연결하여 UNIQUE 충돌을 방지한다.

### 공지 이미지 정책을 설정으로 관리한다

현재 합의는 JPEG·PNG·WebP, 파일당 최대 5MiB(5,242,880바이트), 최대 10장이다. 빈 파일은 거부한다.
확장자 대신 contentType을 기준으로 1차 검증하며 실제 내용 검증은 후속 UploadedFileVerifier의 책임이다.
정책을 공통 FileMetadata의 불변식으로 만들지 않는다.

- NOTICE_ATTACHMENT_MAX_COUNT: 기본 10
- NOTICE_ATTACHMENT_MAX_SIZE_BYTES: 기본 5242880
- NOTICE_ATTACHMENT_ALLOWED_CONTENT_TYPES: 기본 image/jpeg,image/png,image/webp

설정 변경은 기존 무첨부 API와 다른 도메인의 정책에 영향을 주지 않는다. 기존 파일을 유지할 때는 새 파일의
형식·크기 정책을 다시 적용하지 않으며, 명시한 최종 첨부 목록의 개수 제한은 현재 정책을 따른다.

## 선택 이유

도메인 로직을 실제 S3 환경 준비와 독립적으로 검증하면서, 검증 누락이 배포 시 성공 처리로 이어지지 않게 한다.
공통 파일의 사용처를 미리 고정하지 않아 사용자 프로필 등 다른 도메인으로 확장할 수 있다.

## 검토한 대안

### 실제 검증이 완성될 때까지 모든 구현을 기다린다

통합 순서는 단순하지만 공지 요청·응답과 첨부 저장 로직까지 지연된다.

### dev에서는 검증을 건너뛰고 완료 처리한다

미업로드 파일도 정상 첨부가 되고 서버 환경 설정 실수로 같은 경로가 운영에 노출될 수 있어 채택하지 않는다.

## 영향

- 이번 작업은 공지의 첨부 요청·응답과 저장 구조를 dev에서 확인할 수 있는 기반이며,
  새 첨부의 정상 저장은 실제 업로드 검증 연결 전까지 503으로 차단된다.
- 첨부 없는 기존 공지의 생성·수정·조회·삭제는 유지한다.
- 상세 응답은 attachments 메타데이터만 제공한다. 파일 접근 URL 발급은 후속 계약으로 남긴다.
- 모든 파일의 PENDING 상태 전이를 공통으로 준수해야 하므로 과제·제출물 담당자와 잠금 계약 공유가 필요하다.
- 회원 탈퇴·스터디 삭제·S3 파일 청소 정책은 이 단계에서 완료된 것으로 간주하지 않는다.

## 후속 작업

1. 팀원: object key로 S3 실제 존재·크기 등 업로드 결과 조회를 구현한다.
2. 공지: 실제 조회를 UploadedFileVerifier에 연결하고 실패·내용 검증 계약을 보완한다.
3. dev에서 실제 PUT 이후 공지 저장과 실패 롤백을 검증한 뒤 prod 배포를 판단한다.
4. 파일 접근 URL과 S3 물리 삭제·미사용 파일 정리는 별도 후속 범위로 진행한다.
