# 0066. 과제 목록 무한 스크롤의 정렬 기준 시각을 첫 페이지 조회 시각으로 고정한다

- 날짜: 2026-11-24
- 관련 이슈: [#727](https://github.com/woowacourse-teams/2026-ChongChong/issues/727)
- 관련 결정: [ADR-0013](0013-unify-application-time-source.md)의 Clock 기준 시각,
  [ADR-0014](0014-introduce-cursor-page-request.md)의 커서 페이지 요청

## 배경

과제 목록의 마감순은 "진행 중 / 마감" 그룹으로, 미제출순은 "미제출 / 나머지" 그룹으로 먼저 나눈 뒤 정렬한다.
커서는 마지막 과제의 `id`만 담고, 서버는 다음 페이지 요청마다 커서 과제가 어느 그룹에 속하는지를 그 순간의 상태로 다시 계산한다.

페이지 사이에 마감 시각이 지나거나 사용자가 과제를 제출하면 그룹이 바뀌어 커서 위치가 어긋난다.
시각과 제출 상태를 바꿀 수 있는 재현 테스트로 H2와 PostgreSQL에서 모두 다음을 확인했다.

| 정렬 | 상황 | 결과 |
| --- | --- | --- |
| 마감순 | 1페이지 마지막 과제가 23:59에 마감되고 00:01에 2페이지 요청 | 2페이지가 빈 배열이 되어 남은 과제가 모두 누락된다 |
| 마감순 | 이미 본 과제가 마감 | 마감 그룹에서 다시 나온다 |
| 미제출순 | 1페이지 마지막 과제를 제출 | 남은 미제출 과제가 누락된다 |
| 미제출순 | 이미 본 과제를 제출 | 제출 그룹에서 다시 나온다 |

마감 직전은 과제 목록을 가장 많이 보는 시간이고, 누락된 과제는 새로고침 전까지 보이지 않는다.

## 결정

- 과제 목록 응답에 첫 페이지 조회 시각 `asOf`를 추가한다. 다음 페이지 요청은 `cursor`와 함께 `asOf`를 보낸다.
- `nextCursor`는 지금처럼 과제 `id` 숫자로 유지한다.
- 그룹은 `asOf` 기준으로 나눈다.
  - 마감순: `closeAt < asOf`이면 마감 그룹이다.
  - 미제출순: 본인이 제출 대상이고 `submittedAt IS NULL OR submittedAt > asOf`이면 미제출 그룹이다.
    `submittedAt`은 처음 제출할 때 한 번만 기록되므로 `asOf` 시점의 제출 여부를 다시 계산할 수 있다.
- 목록 항목의 진행 상태와 제출 상태는 지금처럼 실제 현재 시각으로 계산한다.
- `asOf`는 선택 값이다.
  - `cursor`가 없으면 `asOf`를 무시하고 현재 시각을 사용한다.
  - `cursor`가 있는데 `asOf`가 없으면 현재 시각을 사용한다. 기존 클라이언트는 지금과 같이 동작한다.
  - 미래 시각이면 400으로 거절한다.
  - 오래된 시각은 그대로 사용한다.

## 선택 이유

그룹을 바꾸는 원인은 페이지마다 달라지는 기준 시각과 제출 상태다. 기준 시각을 첫 페이지 시각으로 고정하면
마감순 그룹은 페이지 사이에 바뀌지 않는다. 미제출순도 `submittedAt`과 `asOf`를 비교하면 페이지 사이의 제출로 그룹이 바뀌지 않는다.

`nextCursor`를 숫자로 두고 `asOf`를 별도 값으로 추가하면 기존 응답 필드가 바뀌지 않는다.
`asOf`가 없을 때 현재 시각을 쓰므로 백엔드를 먼저 배포해도 기존 프론트가 지금처럼 동작한다.

진행 상태와 제출 상태를 `asOf`로 계산하면 이미 마감된 과제를 진행 중으로, 방금 제출한 과제를 미제출로 보여 준다.
목록 위치와 상태 표시가 잠시 어긋나는 것보다 사실과 다른 상태를 보여 주는 쪽이 사용자 판단을 더 크게 해친다.

미래 시각은 서버가 응답한 `asOf`를 그대로 돌려보내는 정상 흐름에서 나올 수 없으므로 클라이언트 오류로 본다.
오래된 시각을 거절하면 목록 화면을 오래 열어 둔 사용자의 스크롤이 끊긴다. `asOf`는 같은 스터디 안의 정렬만 바꾸므로
오래된 값을 허용해도 볼 수 없던 데이터가 노출되지 않는다.

## 검토한 대안

### 커서를 `asOf`, `closeAt`, `id`를 담은 문자열로 변경

커서 과제의 마감 시각까지 커서에 담으므로 페이지 사이에 리더가 마감 시각을 수정해도 위치가 어긋나지 않는다.
하지만 `nextCursor`의 타입이 바뀌어 프론트 스키마와 함께 배포해야 하고, 커서 인코딩과 검증이 추가된다.
마감 시각 수정은 드문 경우라 채택하지 않았다.

### 페이지 번호(OFFSET)

커서 과제의 그룹이 바뀌어 남은 과제가 통째로 누락되는 문제는 사라진다. 그러나 그룹이 바뀌면 순서가 밀려
여전히 일부 과제가 누락되거나 중복된다. 뒤 페이지일수록 앞 행을 읽고 버리는 비용도 커진다.

### 그룹을 정렬 대신 필터로 분리

진행 중 / 마감, 미제출 / 전체를 탭으로 나누고 각 탭을 변하지 않는 값으로만 정렬하면 누락과 중복이 생기지 않고
`(study_id, close_at, id)` 인덱스로 정렬할 수 있다. 하지만 한 목록에서 그룹 순서대로 보여 주던 화면을 바꿔야 해서 채택하지 않았다.

## 영향

### 긍정적 영향

- 페이지 사이에 마감이 지나거나 본인이 제출해도 과제가 누락되거나 중복되지 않는다.
- 커서 타입이 그대로라 백엔드와 프론트를 따로 배포할 수 있다.

### 부정적 영향과 위험

- 2페이지부터 진행 중 그룹 위치에 마감 상태 과제가, 미제출 그룹 위치에 제출 완료 과제가 보일 수 있다. 새로고침하면 다시 정렬된다.
- 페이지 사이에 리더가 제출 대상이나 마감 시각을 바꾸면 여전히 누락이나 중복이 생길 수 있다.
  제출 대상 변경(`assigned`)은 바뀐 시각을 기록하지 않아 `asOf`로 되돌려 계산할 수 없다.
- 프론트가 `asOf`를 보내기 전까지는 수정 효과가 없다.

## 미확정 사항

- 없음

## 후속 작업

- 과제 목록 조회에 `asOf` 요청 값과 응답 필드를 추가하고 마감순·미제출순 쿼리의 기준 시각을 바꾼다.
- 재현 테스트를 수정 후 누락·중복이 없는 기준으로 바꾼다.
- OpenAPI 명세에 `asOf`를 반영한다.
- 프론트 과제 목록 무한 스크롤에서 첫 페이지 응답의 `asOf`를 다음 페이지 요청에 보낸다.
