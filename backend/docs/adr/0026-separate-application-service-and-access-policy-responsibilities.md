# 0026. 애플리케이션 서비스와 접근 정책의 책임을 분리한다

- 날짜: 2026-09-02
- 관련 이슈: [#244](https://github.com/woowacourse-teams/2026-ChongChong/issues/244)
- 관련 ADR: [0002. 도메인 중심으로 패키지를 구성한다](0002-organize-packages-by-domain.md),
  [0003. 백엔드 테스트 범위와 역할을 정의한다](0003-define-backend-test-strategy.md),
  [0006. 공통 예외 처리 타입의 책임을 분리한다](0006-design-common-exception-types.md)

## 배경

서비스 계층은 트랜잭션을 열고 Repository에서 엔티티를 조회한 뒤 도메인 행위를 호출하고 응답을 조립한다. 여기에 리더
여부, 제출물 소유권과 리소스 소속 같은 권한 판단까지 함께 들어가면서 유스케이스의 핵심 흐름과 세부 조건을 한 번에
읽기 어려워졌다.

과제 도메인은 `AssignmentAccessPolicy`로 리더 권한과 제출물 소유권을 판단하지만, 공지와 스터디 도메인은 같은 성격의
조건을 서비스의 private 메서드나 분기문에서 직접 검사한다. 서비스마다 권한 규칙의 위치와 예외가 달라지면 규칙 변경 시
일부 API만 수정하거나 같은 권한을 서로 다른 에러로 반환할 수 있다.

서비스 메서드가 많아졌다는 이유만으로 Command와 Query 클래스를 나누는 얕은 CQRS도 검토할 수 있다. 그러나 현재 읽기와
쓰기 모두 같은 JPA 모델과 Repository, 트랜잭션 경계를 사용한다. 이름만 분리하면 책임은 그대로인 채 탐색할 클래스와
의존성만 늘어날 수 있다.

## 결정

### 애플리케이션 서비스는 유스케이스를 조율한다

- 애플리케이션 서비스는 트랜잭션 경계를 선언하고, 유스케이스에 필요한 엔티티 조회, 접근 정책 호출, 도메인 행위 호출,
  저장과 응답 조립의 순서를 조율한다.
- Repository를 이용한 존재 여부 확인과 `studyId` 등 요청 범위에 속하는 리소스 조회는 서비스가 담당한다. 가능하면
  `getByIdAndStudyIdOrThrow`처럼 범위를 포함한 Repository 조회로 다른 aggregate의 리소스가 섞이지 않게 한다.
- 한 엔티티의 상태만으로 판단할 수 있는 불변식과 상태 변경은 엔티티 메서드가 담당한다.
- 단순하고 한 곳에서만 쓰이는 응답 조립은 서비스에 둘 수 있다. 별도 클래스는 독립적인 변경 이유나 재사용이 생겼을 때
  도입한다.

### 여러 객체를 조합하는 권한 판단은 기능별 Access Policy가 담당한다

- 사용자 역할, 대상 리소스와 소유권을 조합하여 “누가 이 작업을 할 수 있는가”를 판단하는 규칙은 해당 기능의
  `AccessPolicy`로 분리한다.
- Policy의 공개 메서드는 `requireCanCreateAssignment`, `requireCanReadSubmission`처럼 허용하려는 행위를 이름에
  드러낸다. 여러 행위가 현재 같은 리더 조건을 사용하더라도 호출부의 의도와 향후 규칙 변경 범위를 보존한다.
- 허용되지 않으면 Policy가 인증·인가 영역의 `AuthException`과 합의한 `AuthErrorCode`를 발생시킨다. 생성 가능 수,
  중복 가입처럼 권한이 아닌 업무 제약은 해당 도메인의 예외로 구분한다.
- Policy는 상태를 갖지 않으며 Repository, HTTP 요청·응답과 트랜잭션에 의존하지 않는다. 서비스가 조회한 엔티티나
  판정에 필요한 값을 전달받아 결정한다.
- 한 엔티티가 자신의 상태만으로 답할 수 있는 `isOwnedBy` 같은 사실은 엔티티가 제공하고, Policy는 여러 사실을 조합하여
  최종 접근 여부를 결정한다.

### 모든 서비스 조건을 기계적으로 분리하지 않는다

- 유스케이스 순서, 조회 결과의 존재 보장과 단순 응답 변환은 Policy로 옮기지 않는다.
- 한 엔티티의 불변식은 서비스 private 검증이나 Policy 대신 엔티티가 보호한다.
- private 메서드라는 이유만으로 새 컴포넌트를 만들지 않는다. 권한이라는 독립 책임이 있거나 여러 유스케이스가 같은
  판단 기준을 공유할 때 분리한다.

### 현재는 CommandService와 QueryService를 분리하지 않는다

- 현재 서비스는 Command와 Query 모두 같은 도메인 모델, Repository와 트랜잭션 관리 방식을 사용하므로 기능 단위
  Application Service를 유지한다.
- 읽기/쓰기 메서드의 수만을 기준으로 `AssignmentCommandService`, `AssignmentQueryService`처럼 나누지 않는다.
- 다음 중 하나가 나타나 서비스의 범위가 다시 과해지면 얕은 CQRS 또는 읽기 모델 분리를 재검토한다.
  - 한 서비스의 읽기와 쓰기가 서로 다른 Repository·외부 시스템 의존성을 가져 변경 이유가 분리되는 경우
  - 조회 전용 Projection과 최적화가 도메인 모델 기반 조회보다 독립적으로 발전하는 경우
  - 읽기와 쓰기의 트랜잭션, 캐시, 확장 또는 장애 처리 요구가 달라지는 경우
  - 서비스가 커져 기능 단위 탐색과 테스트에서 서로 무관한 의존성을 계속 준비해야 하는 경우

## 선택 이유

서비스에 유스케이스 조율을 남기고 권한 판단만 Policy로 분리하면 핵심 실행 순서를 한눈에 읽을 수 있다. 권한 규칙은
행위별 이름 아래 한 곳에서 테스트하고 변경할 수 있어 API별 허용 범위와 에러 코드가 달라질 위험도 줄어든다.

Policy가 Repository나 HTTP 타입에 의존하지 않으면 트랜잭션과 데이터 접근은 서비스 경계에 유지되고, 준비된 도메인
객체만으로 빠르게 단위 테스트할 수 있다. 엔티티가 제공하는 사실과 Policy의 의사결정을 구분하여 한 엔티티에 외부 역할의
권한까지 떠넘기지 않는다.

현재 단계에서 기능 단위 서비스를 유지하면 읽기와 쓰기에 공통인 의존성과 흐름을 가까이 둘 수 있다. 실제 변경 이유와
운영 요구가 갈라질 때 CQRS를 도입하도록 조건을 남겨, 현재의 복잡도에는 맞지 않는 선행 추상화를 피한다.

## 검토한 대안

### 모든 검증을 애플리케이션 서비스에 둔다

호출 흐름을 한 파일에서 확인할 수 있지만 권한 규칙과 유스케이스 조율이 섞이고 같은 판단이 여러 서비스에서 중복된다.
규칙 변경의 누락 위험을 줄이지 못하므로 선택하지 않았다.

### 권한 규칙을 모두 엔티티에 둔다

도메인 행위와 규칙을 가까이 둘 수 있다. 그러나 현재 사용자의 역할과 다른 엔티티의 소유권을 조합하는 권한은 단일
엔티티의 불변식이 아니며, 엔티티가 인증·인가 예외와 외부 행위의 의미까지 알아야 하므로 선택하지 않았다.

### Policy가 Repository에서 필요한 객체를 직접 조회한다

서비스의 조회 코드가 줄어든다. 하지만 Policy가 데이터 접근과 트랜잭션에 결합되고 숨은 쿼리가 생겨 순수한 권한 판단을
독립적으로 테스트하기 어려워지므로 선택하지 않았다.

### 얕은 CQRS로 CommandService와 QueryService를 즉시 분리한다

읽기와 쓰기 메서드의 위치가 명확해지고 클래스 크기를 줄일 수 있다. 그러나 현재는 양쪽이 같은 모델과 의존성을 공유해
클래스 이름 외의 책임·데이터 모델·운영 특성이 분리되지 않는다. 지금 적용하면 코드 이동과 의존성 중복에 비해 얻는 효과가
작으므로 유보하고, 결정에 명시한 재검토 조건이 나타날 때 다시 논의한다.

## 영향

### 긍정적 영향

- 서비스 메서드에서 유스케이스의 조회, 도메인 행위와 저장 순서를 파악하기 쉬워진다.
- 같은 권한 규칙과 접근 거부 예외를 기능별 Policy에서 일관되게 관리할 수 있다.
- 권한 판단을 Repository나 Spring MVC 없이 독립적으로 단위 테스트할 수 있다.
- 엔티티, Policy와 서비스의 책임을 변경 이유에 따라 구분할 수 있다.
- 현재 규모에 불필요한 Command·Query 클래스와 의존성 중복을 만들지 않는다.

### 부정적 영향과 위험

- 단순한 권한 조건에도 Policy 호출과 클래스 이동이 추가된다.
- 행위별 Policy 메서드가 같은 내부 조건을 위임하면 메서드 수가 늘어날 수 있다.
- 서비스가 조회한 객체를 Policy에 전달해야 하므로 호출 순서와 인자가 늘어난다.
- CQRS 재검토 조건을 놓치면 기능 단위 서비스가 다시 비대해질 수 있다.

## 미확정 사항

없음.

## 후속 작업

- 공지와 스터디 서비스의 권한 조건을 분류하고 여러 객체를 조합하는 규칙을 기능별 Access Policy로 이동한다.
- 권한이 아닌 aggregate 불변식과 업무 제약은 엔티티 또는 해당 도메인 책임으로 이동한다.
- Policy 단위 테스트는 허용·거부 조합과 에러 코드를 검증하고, 서비스 테스트는 Policy 호출을 포함한 유스케이스 흐름을
  검증한다.
- 대표 API 인수 테스트로 역할과 소유권에 따른 성공·접근 거부 응답을 유지한다.
- 서비스 책임이 재검토 조건에 해당하는지 코드 리뷰에서 확인하고, 해당하면 Command·Query 분리를 별도 ADR로 논의한다.
