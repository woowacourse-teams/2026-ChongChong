# 0035. 수동 알림 검증 방식을 검토 및 선택한다.

- 날짜: 2026-09-21
- 관련 이슈: [#345](https://github.com/woowacourse-teams/2026-ChongChong/issues/345)
- 후속 ADR: [0038. 논리 알림과 Web Push 전달을 NotificationDelivery 파이프라인으로 분리한다](0038-separate-logical-notifications-and-web-push-delivery.md)에서 운영자 Discord 수동 전달 대신 사용자별 Web Push 전달로 전환하는 현재 구조를 결정한다. 백엔드에서 생성 이벤트를 감지한다는 경계는 유지한다.

## 1. 목적

공지, 과제, 제출 데이터가 생성될 때 해당 이벤트를 감지해 수동 알림을 수행한다.

- 공지·과제 생성: 해당 스터디원 정보를 운영자에게 알림
- 과제 제출: 해당 스터디장 정보를 운영자에게 알림
- 운영자는 알림을 확인한 뒤 별도 연락처로 직접 안내

향후 검증이 완료되면 운영자 알림을 실제 스터디원 또는 스터디장 대상 자동 알림으로 전환한다.

## 2. 검토 방식

### 방식 1. 백엔드 코드에서 이벤트 감지

```
공지·과제·제출 저장
  → 백엔드에서 알림 이벤트 생성
  → 알림 처리
  → Discord 등 외부 채널로 운영자에게 알림
```

백엔드의 저장 로직에서 데이터 생성과 알림 이벤트 생성을 함께 처리한다.

장점:

- 도메인 정보와 수신 대상을 백엔드에서 바로 확인할 수 있다.
- 별도의 EC2 감시기와 운영 환경이 필요하지 않다.
- 데이터 저장과 알림 이벤트 생성을 하나의 트랜잭션으로 관리할 수 있다.
- 수동 알림에서 자동 알림으로 변경할 때 알림 발송 대상과 처리 방식만 변경하면 된다.
- 백엔드 배포, 로그, 모니터링 체계를 그대로 활용할 수 있다.

단점:

- 기존 백엔드 코드 수정과 재배포가 필요하다.
- 백엔드를 거치지 않고 DB에 직접 데이터를 추가하는 경우에는 이벤트를 감지하지 못할 수 있다.
- 공지·과제·제출이 생성되는 모든 경로에 이벤트 처리가 적용되어야 한다.

### 방식 2. DB Trigger와 별도 EC2 감시기 사용

```
RDS PostgreSQL 행 추가
  → PostgreSQL Trigger
  → EC2 감시기
  → Discord 등 외부 채널로 알림
```

DB에 행이 추가되는 시점을 PostgreSQL Trigger로 감지하고, 별도 EC2 프로세스가 이벤트를 받아 알림을 보낸다.

장점:

- 기존 백엔드 코드를 수정하지 않아도 된다.
- 백엔드 외부에서 직접 DB에 데이터를 추가해도 감지할 수 있다.
- DB 변경을 중앙에서 감지할 수 있다.

단점:

- EC2에 감시기 프로세스를 별도로 배포하고 계속 실행해야 한다.
- RDS 접근 권한, 보안 그룹, SSM, 네트워크, 외부 통신 설정이 필요하다.
- 프로세스 재시작, 장애 처리, 로그, 비밀값 관리 등 운영 대상이 늘어난다.
- 수동 알림에서 자동 알림으로 변경할 때 감시기와 EC2 환경 설정을 다시 변경해야 할 수 있다.
- DB 이벤트와 도메인 정보를 별도로 조합해야 하므로 로직이 분산된다.

## 3. 선택한 방식

백엔드 코드에서 이벤트를 감지하는 방식을 선택한다.

```
백엔드 저장 로직
  → 알림 이벤트 생성
  → 수동 알림 처리
  → 향후 자동 알림 처리
```

## 4. 선택 이유

가장 큰 이유는 **수동 알림을 자동 알림으로 변경할 때 EC2와 같은 별도 실행 환경을 다시 구성하지 않기 위해서**다.

수동 알림과 자동 알림은 모두 같은 생성 이벤트를 기반으로 한다. 따라서 백엔드에서 이벤트를 생성하고, 알림 처리 방식만 변경하는 구조가 적합하다.

현재는 다음과 같이 동작시킨다.

```
이벤트 생성
  → 운영자에게 알림
  → 운영자가 직접 연락
```

향후에는 다음과 같이 변경한다.

```
이벤트 생성
  → 해당 스터디원 또는 스터디장에게 자동 알림
```

이때 DB 이벤트 감지와 실행 환경은 그대로 유지하고, 알림 대상과 발송 로직만 변경할 수 있다.

또한 백엔드는 스터디, 멤버, 과제, 제출, 스터디장 관계를 이미 알고 있으므로 DB Trigger와 EC2 감시기가 별도로 정보를 조합하는 것보다 도메인 규칙을 일관되게 관리할 수 있다.

## 5. 구현 방향

알림 발송 자체를 저장 트랜잭션과 분리할 수 있도록 알림 이벤트 또는 Outbox 구조를 사용한다.

```
도메인 데이터 저장
  → 알림 이벤트 저장
  → 알림 처리기 실행
  → 수동 알림 발송
```

초기에는 운영자에게 다음 정보를 전달한다.

- 이벤트 유형
- 스터디 정보
- 공지·과제·제출 정보
- 수동 연락이 필요한 대상자
- 관련 링크

수동 알림은 Discord를 사용한다.

- Slack은 사용할 수 있는 앱 또는 봇 권한이 부족하므로 사용하지 않는다.
- 개인 DM을 보내지 않고 프로젝트 팀원이 있는 Discord 채널에 메시지를 보낸다.
- Discord 사용자 ID를 직접 받아서 보내지 않는다. 사용자가 Discord ID를 별도로 제공해야 하므로 불편할 수 있기 때문이다.
- Discord 채널 메시지에는 이벤트 정보와 수동 연락 대상자의 본명을 포함한다.
- 수신자별로 동일한 메시지를 반복해서 보내지 않고, 하나의 이벤트마다 채널에 한 번만 메시지를 보낸다.

자동 알림으로 전환할 때는 운영자 대신 실제 수신자에게 발송하도록 알림 처리 부분만 변경한다.
