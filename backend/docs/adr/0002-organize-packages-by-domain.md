# 0002. 도메인 중심으로 패키지를 구성한다

- 날짜: 2026-08-15
- 관련 이슈: [#29](https://github.com/woowacourse-teams/2026-ChongChong/issues/29)

## 배경

공지, 과제, 스터디와 같은 기능 구현이 동시에 진행될 예정이다. 최상위 패키지를 `controller`, `service`, `repository`처럼
기술 계층으로 나누면 한 기능을 수정할 때 여러 최상위 패키지를 오가야 하고, 도메인의 책임과 경계가 드러나지 않는다.
특히 스터디 멤버, 공지 수신자, 제출물 및 리마인더처럼 특정 기능에 종속된 개념을 어느 패키지에 둘지 공통 기준이 필요하다.

## 결정

Java 기본 패키지는 애플리케이션 코드가 위치한 `withoutc.chongchong`으로 한다. 최상위 패키지는 도메인을 기준으로
나누고, 각 도메인 패키지 내부를 필요한 계층으로 구성한다.

```text
withoutc.chongchong
├── user
│   ├── controller
│   ├── service
│   ├── domain
│   └── repository
├── auth
├── study
├── notice
├── assignment
├── notification
└── global
    ├── exception
    ├── common
    └── config
```

위 트리는 책임의 경계를 보여 주는 예시다. 각 도메인은 실제로 필요한 하위 패키지만 만든다. 빈 계층 패키지를 미리
생성하지 않는다.

- `user`: 사용자 정보와 사용자 생명주기를 담당한다. 사용자 도메인의 영문 이름은 `user`로 통일한다.
- `auth`: 인증과 인가를 담당한다.
- `study`: 스터디와 스터디 멤버를 함께 관리한다.
- `notice`: 공지, 공지 수신자와 공지 리마인더를 함께 관리한다.
- `assignment`: 과제, 제출물과 과제 리마인더를 함께 관리한다.
- `notification`: 알림 전송과 알림 수신에 필요한 정보의 생명주기를 담당한다. 푸시 토큰의 최종 위치는 미확정 사항을
  따른다.
- `global`: 예외 처리, 공통 타입 및 프레임워크 설정처럼 여러 도메인에 공통으로 필요한 기술 코드를 둔다.

특정 공지나 과제의 생명주기에 속하는 리마인더 엔티티와 비즈니스 로직은 소유 도메인에 둔다. 리마인더라는 이름만으로
별도 최상위 도메인을 만들지 않는다. 스케줄 실행을 위한 범용 프레임워크 설정은 `global.config`에 둘 수 있지만, 어떤
리마인더를 언제 보낼지 결정하는 로직은 해당 도메인이 소유한다.

`global`은 특정 도메인의 규칙, 엔티티 또는 유스케이스를 포함하지 않는다. 둘 이상의 도메인에서 사용한다는 이유만으로
코드를 즉시 `global`로 이동하지 않고, 도메인 의미가 없는 공통 기술 책임인지 먼저 확인한다.

## 선택 이유

도메인 중심 구조는 함께 변경되는 코드를 가까이 두고 기능별 책임을 드러낸다. 스터디 멤버, 공지 수신자, 제출물과
리마인더를 소유 도메인에 포함하면 독립적인 생명주기를 갖는 것처럼 잘못 모델링하는 일을 피할 수 있다. `global`의 범위를
기술적 공통 코드로 제한하면 공통 패키지가 도메인 간 결합의 우회로가 되는 것을 방지한다.

## 검토한 대안

### 최상위를 기술 계층으로 분리

같은 기술 역할의 클래스를 찾기 쉽지만, 기능 하나가 여러 최상위 패키지에 흩어지고 도메인 간 경계가 약해진다.

### 리마인더를 독립 최상위 패키지로 분리

스케줄러와 진입점을 한곳에 모을 수 있지만, 공지 리마인더와 과제 리마인더의 규칙 및 생명주기가 각 소유 도메인에서
분리된다. 리마인더가 독립적인 생명주기와 유스케이스를 갖게 될 때 별도 ADR로 재검토한다.

### 재사용되는 코드를 모두 `global`에 배치

중복을 빠르게 줄일 수 있지만 서로 다른 도메인이 공통 구현에 결합되고 `global`의 책임이 계속 커진다.

## 영향

### 긍정적 영향

- 기능 변경 범위와 코드 소유권을 패키지 구조에서 파악할 수 있다.
- 종속 개념의 생명주기와 비즈니스 규칙을 소유 도메인 안에서 관리할 수 있다.
- 도메인별 병렬 개발에서 패키지 충돌을 줄일 수 있다.

### 부정적 영향과 위험

- 동일한 계층 이름이 여러 도메인 패키지에 반복된다.
- 도메인 경계를 잘못 정하면 패키지 간 순환 의존이 생길 수 있다.
- 실제 요구사항이 드러나면서 일부 개념의 소유 도메인을 다시 결정해야 할 수 있다.

## 미확정 사항

- 푸시 토큰을 사용자와 알림 중 어느 도메인이 소유할지, 토큰의 생성·갱신·삭제 유스케이스를 기준으로 결정해야 한다.
- 여러 도메인의 리마인더 실행을 시작하는 진입점이 필요할 때 어느 도메인이 오케스트레이션할지 결정해야 한다.

## 후속 작업

- 미확정 소유권을 팀 리뷰에서 결정한다.
- 각 기능을 구현할 때 이 ADR의 경계에 맞는 최소 하위 패키지만 생성한다.
- 독립 리마인더 도메인이 필요해지면 별도 ADR로 대안을 다시 평가한다.
