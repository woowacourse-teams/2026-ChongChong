# 0042. 자원 삭제 시 관련 인앱 알림을 삭제한다

- 날짜: 2026-10-01
- 관련 이슈: [#415](https://github.com/woowacourse-teams/2026-ChongChong/issues/415)
- 관련 ADR: [0024. 하드 삭제 시 데이터베이스 외래 키 CASCADE로 종속 데이터를 삭제한다](0024-use-database-cascades-for-hard-delete.md),
  [0038. 논리 알림과 Web Push 전달을 NotificationDelivery 파이프라인으로 분리한다](0038-separate-logical-notifications-and-web-push-delivery.md)
- 일부 대체 관계: [0038](0038-separate-logical-notifications-and-web-push-delivery.md)의 원본 자원 삭제 뒤에도 snapshot 알림을 보존하는 정책

## 배경

`Notification`은 `resourceType`과 `resourceId`로 공지, 과제, 제출물을 가리킨다. 이 다형 참조에는 외래 키가 없어 원본 자원이 삭제되어도 `Notification` 행은 남는다. `title`, `body`, `deepLink`를 snapshot으로 저장해 원본 값이 바뀌어도 알림 내용을 보여줄 수 있지만, 원본이 삭제된 뒤에도 알림을 유지하면 사용자가 존재하지 않는 자원으로 이동하게 된다.

`NotificationDelivery`는 `Notification`을 외래 키로 참조하며 `ON DELETE CASCADE`가 적용되어 있다. 따라서 논리 알림을 삭제하면 대기 중인 Web Push 발송 기록도 정리할 수 있다. 이미 Push Service가 전달한 푸시를 회수할 수는 없다.

## 결정

### 원본 자원과 논리 알림의 생명주기를 함께 둔다

- 공지 삭제 시 해당 공지를 가리키는 `NOTICE` 알림을 삭제한다.
- 과제 삭제 시 해당 과제를 가리키는 `ASSIGNMENT` 알림과 제출물을 가리키는 `ASSIGNMENT_SUBMISSION` 알림을 삭제한다.
- 스터디 삭제 시 스터디의 공지, 과제, 제출물을 가리키는 알림을 삭제한다.
- 멤버 제거와 사용자 탈퇴 시 함께 삭제되는 해당 멤버의 제출물을 가리키는 알림을 삭제한다.
- 자원·스터디·멤버·사용자 삭제와 관련 알림 삭제는 같은 데이터베이스 트랜잭션에서 수행한다.

자원 종류와 ID로 대상을 찾는 bulk delete를 사용한다. 과제·스터디·멤버·사용자 삭제처럼 하위 자원까지 삭제되는 경우에는 하위 제출물 ID를 한 행씩 조회하지 않고 데이터베이스 쿼리로 관련 알림을 삭제한다.

`Notification` 삭제 시 외래 키 CASCADE로 `NotificationDelivery`를 함께 삭제한다. 전달 대기 중인 기록은 더 이상 처리하지 않는다. 이미 전송됐거나 삭제 요청과 동시에 외부 Push Service로 전달 중인 푸시를 회수하는 기능은 제공하지 않는다.

### 기존 고아 알림을 한 번 정리한다

다형 참조에 외래 키가 없으므로 이전 삭제 경로에서 남은 알림은 자원 삭제 서비스에서 찾을 수 없다. Flyway V16은 현재 자원 행이 없는 `NOTICE`, `ASSIGNMENT`, `ASSIGNMENT_SUBMISSION` 알림을 한 번 삭제한다. 이에 연결된 발송 기록은 외래 키 CASCADE로 삭제된다.

### snapshot 정책을 제한한다

원본 자원의 제목·내용이 수정되어도 이미 생성된 알림의 표시 내용은 snapshot으로 유지한다. 원본 자원이 하드 삭제되면 해당 snapshot 알림 자체를 삭제한다. 제목·본문 snapshot은 이미 전송된 푸시를 회수하거나 보존하는 근거로 사용하지 않는다.

## 선택 이유

알림 목록에서 존재하지 않는 자원을 가리키는 항목을 제거하면 사용자가 유효하지 않은 딥링크를 열지 않는다. 관련 알림과 발송 대기 기록을 원본 삭제 트랜잭션에 묶으면 원본만 지워지고 알림이 남거나, 알림만 사라지고 원본 삭제가 실패하는 상태를 방지한다.

다형 참조에 외래 키를 추가할 수는 없으므로 자원 종류에 맞는 bulk delete와 한 번의 기존 데이터 정리가 현재 스키마에서 가장 작은 변경이다.

## 검토한 대안

### 자원 삭제 뒤에도 snapshot 알림을 보존한다

원본을 조회할 수 없어도 알림 제목과 본문은 표시할 수 있다. 그러나 딥링크가 삭제된 자원을 계속 가리키므로 목록에서 열 수 없는 알림이 남는다. 이번 제품 요구와 맞지 않아 채택하지 않는다.

### 외래 키가 없는 기존 고아 알림을 운영자가 수동으로 정리한다

배포 후 별도의 운영 절차를 수행해야 하고, 어느 환경에서 정리가 완료됐는지 추적하기 어렵다. 배포 migration에서 기존 고아 알림을 한 번 정리하는 방식을 선택한다.

### 모든 알림을 조회한 뒤 애플리케이션에서 필터링한다

알림 수만큼 행을 애플리케이션으로 가져와 비교해야 하고, 삭제 범위와 비용이 데이터 규모에 따라 커진다. 데이터베이스의 `EXISTS` 조건으로 삭제하는 방식을 선택한다.

## 영향

### 긍정적 영향

- 알림 목록에 삭제된 원본 자원을 가리키는 항목이 남지 않는다.
- 원본 삭제와 알림·발송 기록 삭제가 한 트랜잭션으로 처리된다.
- 과제·스터디·멤버·사용자 삭제에서 제출물 알림을 일괄 정리한다.
- 이미 남아 있는 고아 알림을 migration으로 정리한다.

### 부정적 영향과 위험

- 하드 삭제된 자원에 대한 알림 snapshot도 함께 없어져 알림함에서 과거 기록을 확인할 수 없다.
- V16은 notifications 테이블에서 자원별 존재 여부를 검사하므로 migration 실행 시간은 기존 알림 행 수에 영향을 받는다.
- 이미 기기에 표시된 푸시와 외부 전달이 진행 중인 푸시는 회수할 수 없다.
