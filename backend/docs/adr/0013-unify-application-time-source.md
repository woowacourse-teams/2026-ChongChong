# 0013. 애플리케이션 기준 시각을 Clock으로 통일한다

- 날짜: 2026-08-21
- 관련 이슈: 없음

## 배경

공지 리마인드 시각은 외부 요청의 `@Future`와 공지 도메인 규칙에서 각각 미래인지 검증한다. 공지 도메인은
`Asia/Seoul` 시간대의 애플리케이션 `Clock`을 사용하지만, Bean Validation은 기본 `ClockProvider`를 사용하므로 JVM 기본
시간대가 다르면 같은 시각이 요청 검증을 통과한 뒤 도메인 검증에서 거부될 수 있다. 테스트에서 현재 시각을 직접 생성하면
실행 시점에 따라 경계 검증 결과가 달라지는 문제도 있다.

## 결정

- 애플리케이션에서 현재 시각이 필요할 때는 `TimeConfig`가 제공하는 `Clock`을 주입받아 사용한다.
- 애플리케이션 `Clock`은 `Asia/Seoul` 시간대를 기준으로 한다.
- Bean Validation의 `ClockProvider`에는 애플리케이션 `Clock`을 등록한다.
- Spring Boot의 Validator 자동 설정을 유지하기 위해 `ValidationConfigurationCustomizer`를 사용한다.
- 시간 경계 테스트에서는 고정 `Clock`을 주입하여 현재 시각과 미래 시각을 검증한다.
- JVM 기본 시간대 설정을 애플리케이션의 시간 기준으로 사용하지 않는다.

## 선택 이유

외부 요청과 도메인이 같은 `Clock`을 사용하면 하나의 시각에 대해 서로 다른 검증 결과가 나오는 문제를 방지할 수 있다.
`Clock`을 주입하면 운영 시간대를 코드로 명시할 수 있고 테스트에서는 시간을 고정하여 경계 조건을 재현할 수 있다.
`ValidationConfigurationCustomizer`는 Validator를 직접 교체하지 않고 `ClockProvider`만 설정하므로 Spring Boot가 제공하는
자동 설정을 유지한다.

## 검토한 대안

### JVM 기본 시간대를 Asia/Seoul로 설정한다

코드 변경은 적지만 실행 환경 설정에 따라 애플리케이션 동작이 달라지고 테스트에서 시각을 고정하기 어렵다. 애플리케이션의
시간 정책이 외부 환경에 암묵적으로 의존하므로 채택하지 않았다.

### Bean Validation의 미래 시각 검증을 제거한다

도메인에서만 검증하면 기준 시각은 하나가 되지만 잘못된 요청을 웹 경계에서 검증하지 못하고 기존 공통 입력값 오류 계약도
달라진다. 동일한 Clock을 제공하여 두 경계의 검증을 유지하는 편이 적합하다.

### LocalValidatorFactoryBean을 직접 등록한다

Validator 전체 구성을 제어할 수 있지만 Spring Boot 자동 설정을 대체해야 한다. 필요한 변경은 `ClockProvider` 등록뿐이므로
더 작은 확장 지점인 `ValidationConfigurationCustomizer`를 선택한다.

## 영향

### 긍정적 영향

- 요청 검증과 도메인 검증의 현재 시각 기준이 일치한다.
- JVM 기본 시간대와 관계없이 동일하게 동작한다.
- 고정 Clock을 사용하여 시간 경계 테스트를 결정적으로 작성할 수 있다.

### 부정적 영향과 위험

- 현재 시각을 사용하는 컴포넌트는 `Clock`을 의존성으로 전달받아야 한다.
- 애플리케이션의 기준 시간대를 변경하면 Bean Validation과 모든 Clock 사용 컴포넌트에 함께 영향을 준다.

- 현재 시각을 직접 생성하는 코드가 추가되면 애플리케이션 `Clock`을 사용하도록 리뷰한다.
