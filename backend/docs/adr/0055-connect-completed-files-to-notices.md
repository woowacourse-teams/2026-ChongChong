# 0055. 공지 첨부는 업로드 완료 파일의 연결로 처리한다

- 날짜: 2026-10-21
- 관련 이슈: [#554](https://github.com/woowacourse-teams/2026-ChongChong/issues/554)
- 적용 상태: OpenAPI 반영, 구현 예정
- 부분 대체: [ADR-0052](0052-use-presigned-urls-for-file-uploads.md)의 공지 저장 시 업로드 검증·완료 전환
- 부분 대체: [ADR-0053](0053-stage-notice-attachments-before-storage-verification.md)의 공지 검증기·상태 전환·제거 파일 재사용 금지
- 관련 결정: [ADR-0054](0054-separate-upload-verification-from-database-transactions.md)

## 배경

공지 첨부 1단계는 PENDING 파일을 받아 공지 저장 과정에서 실제 업로드 검증과 COMPLETED 전환을
수행하도록 준비했다. 실제 검증이 연결되기 전까지 UploadedFileVerifier의 기본 구현은 새 첨부에 503을 반환한다.

이후 공통 업로드 완료 API가 구현됐다. 이 API는 S3의 파일 존재·실제 크기를 확인하고 COMPLETED로 전환하며,
과제·제출물은 이미 완료된 파일을 연결한다. 공지가 기존 조건을 유지하면 완료 API를 통과한 파일을 거부하고,
공지 저장 중에 같은 업로드를 다시 검증하는 구조가 된다.

완료 상태와 사용 여부의 의미도 정리해야 한다. 완료 API만 호출하고 글을 저장하지 않은 파일도 COMPLETED이므로,
파일 상태만으로 다른 글에 연결된 파일인지 판단할 수 없다. 공지는 제거 파일을 DELETE_PENDING으로 전환하지만
과제·제출물은 연결만 제거하고 있어, 공통 파일을 사용하는 도메인 사이의 생명주기 계약을 맞출 필요가 있다.

## 결정

### 업로드 검증·완료와 공지 연결의 책임을 나눈다

호출 순서는 다음과 같다.

1. 업로드 URL을 발급받아 PENDING 메타데이터를 만든다.
2. 클라이언트가 발급 시의 Content-Type과 If-None-Match: * 헤더로 S3 PUT을 수행한다.
3. 클라이언트가 POST /api/files/{fileId}/complete를 호출해 실제 업로드 검증과 COMPLETED 전환을 완료한다.
4. 성공한 파일 식별자를 공지 생성·수정 요청의 attachmentFileIds에 담는다.

공통 완료 API는 소유권·상태와 S3 파일 존재·실제 크기·선언 크기 일치·공통 용량 제한을 검증한다.
이때의 S3 호출 및 DB 트랜잭션 경계는 ADR-0054를 따른다.

공지는 작성·수정 권한과 첨부 자격을 검증하고 관계를 저장한다. 공지 트랜잭션에서 완료 API나 S3를
호출하지 않으며 FileMetadata.completeUpload도 호출하지 않는다. UploadedFileVerifier를 통한 임시 검증 경로와
새 첨부를 막던 FILE_VERIFICATION_UNAVAILABLE(503)은 제거한다.

### COMPLETED와 첨부 여부를 구분한다

신규 첨부는 요청자 소유의 COMPLETED 파일이며 공지·과제·제출물 어느 곳에도 연결되지 않은 파일이어야 한다.
PENDING·DELETE_PENDING 또는 이미 연결된 파일은 FILE_NOT_ATTACHABLE로 거부한다.
타인 소유 파일과 미존재 파일은 기존 FILE_NOT_OWNED와 FILE_NOT_FOUND로 구분한다.

첨부 테이블의 file_id UNIQUE는 각 테이블 내 중복만 막는다. 교차 도메인 중복은 파일 행을 ID 오름차순으로
잠근 뒤 세 첨부 테이블의 연결 여부를 조회하여 막는다. 새 파일을 연결하는 모든 경로가 이 규칙을 따라야 한다.
공지는 과제 서비스를 호출하지 않고 repository 조회로 연결 여부를 확인한다.

공지 수정·삭제는 기존의 공지 행 잠금 → 파일 행 잠금 순서를 유지한다. 수정에서 명시한 최종 파일과
기존 파일의 합집합을 잠그며, 삭제에서는 기존 파일을 잠근다. 관계 변경도 같은 트랜잭션에서 처리한다.
기존 관계를 지운 뒤 flush하고 최종 순서로 연결하여 공지 내 표시 순서 UNIQUE 충돌을 방지한다.

### 공지 저장 실패는 업로드 완료를 되돌리지 않는다

공지 내용·리마인더·첨부 관계·알림은 기존 공지 DB 트랜잭션에서 함께 처리한다.
첨부 검증이나 저장에 실패하면 이 변경들은 롤백되지만, 선행 완료 API에서 확정한 COMPLETED 상태는 유지한다.
따라서 다른 곳에 연결되지 않았다면 같은 파일로 공지 저장을 재시도할 수 있다.

완료 API 성공은 공지 작성 성공을 의미하지 않는다. 여러 파일 중 하나라도 첨부 검증에 실패하면
성공한 파일만 일부 연결하지 않고 공지 요청 전체를 실패시킨다.

### 첨부 제거는 연결만 정리한다

수정에서 빠진 파일과 삭제된 공지의 파일은 첨부 관계만 제거하고 COMPLETED로 유지한다.
파일 메타데이터와 objectKey를 보존하며 공지에서 S3 삭제나 DELETE_PENDING 전환을 수행하지 않는다.
분리된 파일은 소유자가 다른 도메인의 정책까지 충족하는 경우 다시 첨부할 수 있다.

이 결정은 ADR-0053의 제거 파일 재사용 금지를 대체한다. 기존 DELETE_PENDING 파일을 COMPLETED로
복구하지는 않는다. 미연결 파일의 유예기간·삭제·재시도는 [#531](https://github.com/woowacourse-teams/2026-ChongChong/issues/531)의
공통 정리 작업으로 남긴다. 정리 작업은 미연결 COMPLETED 파일도 고려하고, 같은 파일 행 잠금 아래
상태·실제 연결 여부를 재확인한 뒤 삭제 대상으로 전환해야 한다.

### 이미지 정책과 기존 첨부 유지 계약을 따른다

공지는 저장된 contentType 기준 JPEG·PNG·WebP, 장당 5MiB, 최대 10장을 기본으로 하고 빈 파일은 거부한다.
NOTICE_ATTACHMENT_ALLOWED_CONTENT_TYPES·NOTICE_ATTACHMENT_MAX_SIZE_BYTES·NOTICE_ATTACHMENT_MAX_COUNT로 변경한다.
공통 완료 API의 FILE_UPLOAD_MAX_SIZE_BYTES도 적용되므로 더 큰 파일을 허용하려면 두 용량 설정을 함께 검토한다.

생성에서 attachmentFileIds 생략·null·빈 배열은 무첨부다. 수정에서 생략·null은 유지, 빈 배열은 전체 제거,
배열은 최종 목록과 표시 순서다. 명시한 최종 배열 전체에는 현재 개수 제한을 적용한다.
소유권·형식·크기는 새로 추가하는 파일에 적용하고, 기존 파일은 COMPLETED 상태를 확인해 유지·재정렬한다.
이전 리더 소유의 기존 첨부를 현재 리더가 유지할 수 있다.

공통 완료 API의 존재·크기 검증이 실제 이미지 내용 검증을 뜻하지는 않는다.
파일 내부 형식 검사와 공지 이미지 조회 URL 제공은 별도 후속 범위다.

## 선택 이유

이미 공통화된 업로드 검증을 재사용하고, 공지 DB 트랜잭션이 S3 응답을 기다리지 않게 한다.
완료 상태와 실제 사용 여부를 분리하면 업로드 후 작성 취소·저장 실패·첨부 제거도 같은 기준으로 해석할 수 있다.
과제·제출물과 동일한 연결·정리 계약을 사용하면서 공지의 이미지 정책과 권한은 공지에 남긴다.

## 검토한 대안

### 공지 검증기에 S3 조회를 연결한다

1단계의 구조를 그대로 사용할 수 있지만 완료 API를 거친 파일을 다시 검증하게 된다.
PENDING만 받는 조건을 유지하면 다른 도메인과 업로드 절차가 달라지고 공지 저장 중 외부 호출도 남는다.

### COMPLETED 상태만 보고 연결을 허용한다

검사가 단순하지만 완료된 파일이 이미 과제·제출물에 사용 중인지 구분하지 못한다.
첨부 테이블별 UNIQUE만으로 교차 도메인 중복을 막을 수 없어 선택하지 않는다.

### 공지에서 제거한 파일은 계속 DELETE_PENDING으로 전환한다

제거 즉시 재사용을 막을 수 있지만 과제·제출물의 분리 정책과 다르다.
도메인에서의 연결 제거와 공통 파일의 삭제 판단을 분리하고, 실제 연결과 유예기간을 확인하는 정리 작업에 맡긴다.

## 영향

### 긍정적 영향

- 공지·과제·제출물이 같은 업로드 완료 API와 파일 연결 규칙을 사용한다.
- 공지 저장에 S3 호출이 포함되지 않고, 저장 실패 후 완료된 파일로 재시도할 수 있다.
- 기존 파일·첨부 테이블과 잠금 구조를 활용하며 현재 결정에 새 상태나 마이그레이션은 필요하지 않다.

### 부정적 영향과 위험

- 클라이언트가 파일마다 완료 API의 성공·실패를 관리한 뒤 공지 저장을 요청해야 한다.
- 완료 파일의 미사용 여부를 상태만으로 판단할 수 없어 실제 첨부 관계 조회와 동시성 검증이 필요하다.
- 공통 정리가 구현되기 전까지 작성 취소·첨부 제거 등으로 미연결 COMPLETED 파일이 남는다.
- 저장 명세만 반영한 단계에서는 운영 코드가 이전 동작이므로, 구현·테스트 전환을 같은 PR에서 완료해야 한다.

## 미확정 사항

- 미사용 파일의 유예기간·정리 주기·실패 재시도 정책은 #531에서 결정한다.
- 공지 이미지 조회 URL의 응답 계약과 파일 내부 형식 검사는 별도 작업에서 결정한다.

## 후속 작업

- 공지의 기존 연결 여부 조회, COMPLETED 파일 연결과 첨부 분리 처리를 구현한다.
- 생성·수정이 공유하는 검증 조건과 두 호출자의 완료 전환 제거, 기존 테스트 전환을 함께 수행한다.
- 완료 API → 공지 생성·수정, 미완료·타인 소유·중복 연결 거부, 저장 실패 후 재시도와 롤백을 검증한다.
- PostgreSQL에서 공지·과제·제출물의 같은 파일 동시 연결과 공지 수정·삭제 경합을 검증한다.
- dev에서 실제 S3 PUT 헤더·CORS·완료 API·공지 저장을 확인한 뒤 prod에 배포한다.
  배포 전 발급된 조건부 쓰기 없는 URL의 만료 대기는 [업로드 완료 운영 문서](../file-upload-completion.md)를 따른다.
