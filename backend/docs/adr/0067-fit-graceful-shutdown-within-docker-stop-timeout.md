# 0067. 앱 종료에 걸리는 시간을 docker stop 대기 시간 안으로 줄인다

- 날짜: 2026-11-25
- 관련 이슈: 없음
- 관련 결정: [ADR-0061](0061-clean-up-orphan-files-with-mark-and-sweep.md)의 고아 파일 정리 배치

## 배경

배포는 `docker stop --time ${BACKEND_STOP_TIMEOUT_SECONDS:-60}`으로 이전 앱을 멈춘다. SIGTERM을 받은 앱이
60초 안에 끝나지 않으면 Docker가 SIGKILL을 보낸다. 앱은 배포 JVM 옵션으로 `server.shutdown=graceful`과
`spring.lifecycle.timeout-per-shutdown-phase=30s`를 쓴다.

`timeout-per-shutdown-phase`는 종료 전체가 아니라 종료 단계마다 걸리는 제한이다. SIGTERM 뒤 앱은 아래를 차례로 기다린다.

| 순서 | 기다리는 것 | 상한(변경 전) |
| --- | --- | --- |
| 1 | 처리 중인 웹 요청 (`webServerGracefulShutdown` 단계) | 30초 |
| 2 | Tomcat 요청 스레드 정리 (Tomcat `executorTerminationTimeoutMillis` 기본값) | 5초 |
| 3 | 기본 스케줄러가 하던 일: 회차 생성, 리마인더 (`taskScheduler` 단계) | 30초 |
| 4 | 파일 정리 스케줄러 (`fileCleanupScheduler` 빈 정리 시 `awaitTermination`) | 30초 |
| 5 | 웹 푸시 발송 실행기와 발송 스케줄러 (빈 정리 시 `awaitTermination`) | 8초 + 8초 |

상한의 합은 111초다. 로컬에서 요청(S3 무응답), 회차 생성(DB 잠금 대기), 파일 정리(S3 배치 삭제 무응답)가 동시에
끝나지 않게 만들고 SIGTERM을 보내자 종료에 95.5초가 걸렸다. 웹 푸시 발송은 막지 않았다.

또 회차 생성 워커와 파일 정리 워커는 종료 신호를 보지 않아서 종료 중에도 남은 규칙과 새 정리 배치를 계속 집었다.

## 결정

- 회차 생성 워커와 파일 정리 워커는 웹 푸시 발송 워커처럼 `ContextClosedEvent`를 받으면 `stopping` 플래그를 켠다.
  처리 중인 규칙·배치의 트랜잭션만 마치고 다음 것을 집지 않는다.
- 리마인더 워커 등 알림 영역의 워커와 웹 푸시 발송 대기값은 이번 결정에서 바꾸지 않는다.
- `spring.lifecycle.timeout-per-shutdown-phase`를 30초에서 15초로 줄인다.
- 파일 정리 스케줄러의 `waitForTasksToCompleteOnShutdown`과 30초 `awaitTermination`을 없앤다.
  하던 배치는 기본 스케줄러와 같은 종료 단계(3번)에서 함께 기다린다.
바꾼 뒤 상한의 합은 15 + 5 + 15 + 8 + 8 = 51초다. 60초까지 9초가 남는다.
남은 시간은 JPA·Hikari 종료와 JVM 종료, 측정하지 않은 대기에 쓴다.

## 선택 이유

### 종료 신호 확인

웹 푸시 발송 워커가 이미 `ContextClosedEvent`와 `stopping` 플래그로 새 작업을 멈추고 있다.
같은 방식을 쓰면 새 추상화 없이 워커마다 몇 줄로 끝난다. `ContextClosedEvent`는 종료 단계보다 먼저 발행되므로
SIGTERM 직후부터 새 작업을 집지 않는다.

규칙·배치 하나가 트랜잭션 하나이므로, 멈춘 뒤 남는 일은 모두 다음 실행이 다시 집을 수 있는 상태다.

- 회차 생성: 생성 시각이 지난 규칙으로 남는다. 재시작 뒤 첫 실행에서 남은 규칙 4개가 모두 생성되는 것을 확인했다.
- 파일 정리: 선점하지 않은 삭제 대기 파일로 남는다. 선점 시도 횟수도 늘지 않는다.

### 파일 정리를 기본 스케줄러와 같은 단계에서 기다리기

기본 스케줄러처럼 `waitForTasksToCompleteOnShutdown`을 끄면 Spring은 종료 신호를 받을 때 다음 실행 예약을 취소하고,
실행기 종료 단계에서 하던 작업을 기다린다. 같은 단계의 빈은 동시에 기다리므로 회차 생성과 파일 정리가 함께 막혀도 15초로 끝난다.
빈 정리 시 따로 기다리면 그 시간이 종료 시간에 그대로 더해진다.

### 단계 제한 15초

1번과 3번 단계가 같은 값을 쓰므로 둘의 합과 고정값(Tomcat 5초, 웹 푸시 16초)이 60초 안에 들어와야 한다.
웹 푸시 대기값은 알림 영역의 설정이라 이번에는 바꾸지 않았다. 그러면 단계 제한은 19초 이하여야 하고,
여유를 두어 15초로 정했다.

### 측정 결과

로컬에서 `main` `2de59ab1`과 이 변경을 같은 방법으로 비교했다(Java 25, PostgreSQL 17 컨테이너, 가짜 S3, 초당 약 590건 부하).

| 항목 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 요청·회차 생성·파일 정리가 모두 막힌 경우 종료 시간 | 95.5초 | 35.5초 |
| 일반 부하 중 종료 시간(가장 긴 요청 28초) | 28.0초 | 20.6초 |
| 일반 부하에서 처리 중이던 요청(28초 업로드 제외) | 모두 성공 | 모두 성공 |
| 처리 중이던 25초·28초 업로드 완료 요청 | 성공 | T+15초에 끊김 |
| 회차 생성이 종료 중 새로 집은 규칙 | 4개 | 0개 |
| 파일 정리가 종료 중 새로 선점한 배치 | 2개 | 0개 |

## 검토한 대안

### `BACKEND_STOP_TIMEOUT_SECONDS`를 늘리기

단계 합(111초)보다 길게 두면 SIGKILL 전에 Spring이 스스로 정리를 끝낸다. 하지만 배포 교체가 그만큼 느려지고,
종료 중 새 작업을 집는 문제는 그대로라 채택하지 않았다.

### 단계 제한 20초 + 웹 푸시 대기 5초씩

합은 20 + 5 + 20 + 5 + 5 = 55초다. 20초까지 걸리는 요청을 살릴 수 있지만 여유가 5초뿐이고,
웹 푸시 발송 시간 제한(5초)과 같은 값이라 발송 중인 작업을 기다리지 못할 수 있다. 알림 영역 설정도 함께 바꿔야 해서 채택하지 않았다.

### 단계별로 제한을 다르게 두기

`DefaultLifecycleProcessor`는 단계별 제한을 지원한다. 웹 요청 단계만 길게 둘 수 있지만 Spring Boot가 만드는
`lifecycleProcessor` 빈을 직접 정의해야 한다. 지금 문제에 비해 설정이 늘어서 채택하지 않았다.

## 영향

### 긍정적 영향

- 모든 대기가 동시에 상한까지 걸려도 종료가 60초 안에 끝나 SIGKILL을 받지 않는다.
- 종료 중 새 규칙·배치를 집지 않아 종료 단계에서 기다릴 일이 줄어든다.

### 부정적 영향과 위험

- 종료 시점에 15초 넘게 걸리는 요청은 응답 없이 끊긴다. 이전에는 30초였다.
  이런 요청은 S3 무응답이나 DB 잠금 대기처럼 비정상인 경우였고, 끊긴 요청의 DB 변경은 롤백된다.
- 파일 정리 배치가 15초 안에 끝나지 않으면 스레드가 중단된다. 선점된 파일은 선점 만료(10분) 뒤 다음 실행이 다시 집는다.
- 웹 푸시 대기값이나 Tomcat 기본값이 바뀌면 이 계산을 다시 해야 한다.
- 리마인더 워커는 여전히 종료 신호를 보지 않는다. 종료 중에도 남은 리마인더 후보를 계속 처리하고,
  막히면 기본 스케줄러 단계(15초)까지 기다린 뒤 중단된다. 종료 시간 상한은 지키지만 종료 중 새 작업을 집는 한계는 남는다.

## 미확정 사항

- 종료 직후 keep-alive 연결의 첫 요청이 응답 없이 끊기는 문제는 그대로다. Tomcat은 graceful 종료로 멈춘 뒤
  keep-alive 연결에 들어온 요청을 읽지 않고 연결을 닫는다. 앱 설정으로는 바꿀 수 없다.
  운영 Nginx는 업스트림 연결을 재사용하지 않아(`keepalive` 미설정) 이 경로를 타지 않을 것으로 보지만 재지 않았다.

## 후속 작업

- 웹 푸시 발송 대기값을 바꿀 때 이 ADR의 합을 다시 확인한다.
- 리마인더 워커의 종료 신호 확인은 알림 영역 담당자와 따로 정한다.
