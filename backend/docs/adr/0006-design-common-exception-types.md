# 0006. 공통 예외 처리 타입의 책임을 분리한다

- 날짜: 2026-08-16
- 관련 이슈: [#30](https://github.com/woowacourse-teams/2026-ChongChong/issues/30)

## 배경

[에러 응답과 에러 코드 형식](0004-standardize-error-response.md)을 실제 코드에 적용하려면 HTTP 상태, 외부 에러 코드와
메시지를 여러 도메인에서 같은 방식으로 다루고, 비즈니스 실패와 입력값 검증 실패를 약속한 응답으로 변환해야 한다.
하나의 타입이 에러 정의, 예외 표현과 JSON 응답 생성을 모두 맡으면 새로운 도메인 에러가 추가될 때 전역 예외 처리 코드도
함께 변경될 수 있다. 반대로 역할마다 독립 타입을 과도하게 만들면 사용 범위가 제한된 값까지 별도 파일과 이름으로 관리해야
한다.

## 결정

### 에러 코드

- `ErrorCode`를 인터페이스로 정의하고 모든 에러 코드가 HTTP 상태, 외부 에러 코드와 기본 메시지를 제공하게 한다.
- 특정 도메인에 속하지 않는 공통 에러는 `CommonErrorCode` enum으로 정의한다. 도메인 에러 코드 enum도 같은
  `ErrorCode` 인터페이스를 구현한다.
- 외부 에러 코드는 enum 이름으로부터 계산하지 않고 각 enum 값에 문자열로 명시한다. Java enum 이름을 리팩터링하더라도
  클라이언트와 합의한 코드가 의도하지 않게 변경되지 않게 한다.

### 비즈니스 예외

- `BusinessException`은 도메인별 비즈니스 예외의 공통 부모인 추상 클래스로 정의하고 `RuntimeException`을 상속한다.
- 생성 후 에러가 바뀌지 않도록 `ErrorCode`를 `final` 필드로 보관하고, 전역 예외 처리기가 읽을 수 있게 접근자를 제공한다.
- 생성자는 하위 타입만 호출할 수 있도록 `protected`로 제한한다.
- `ErrorCode`의 메시지를 `RuntimeException` 생성자에도 전달하여 일반적인 예외 로깅과 `getMessage()`에서 같은 메시지를
  확인할 수 있게 한다.

### 에러 응답

- 비즈니스 에러와 입력값 검증 에러는 하나의 `ErrorResponse` record로 표현한다. 공통 필드는 `code`, `message`이며
  검증 에러에만 `errors`를 포함한다.
- 일반 에러는 `errors`에 빈 목록을 사용하고 JSON 직렬화 시 빈 목록을 제외한다. 검증 에러 목록은 복사하여 응답 생성 후
  외부의 리스트 변경이 응답에 영향을 주지 않게 한다.
- `errors`의 항목은 `ErrorResponse.FieldErrorDetail` 공개 중첩 record로 정의한다. `FieldErrorDetail`은 독립적인 응답이나
  도메인 개념이 아니라 `ErrorResponse`의 `errors` 안에서만 의미가 있으므로 소유 타입과 가까이 둔다.
- 전역 예외 처리기가 Spring의 필드 검증 실패를 `FieldErrorDetail`로 변환한다. `ErrorResponse`는 Spring 검증 타입을 직접
  입력받지 않고 완성된 `FieldErrorDetail` 목록만 받는다.
- `FieldErrorDetail`이 다른 응답에서도 재사용되거나 독립적인 동작과 변경 책임을 갖게 되면 별도 최상위 타입으로 분리한다.

## 선택 이유

`BusinessException`과 전역 예외 처리기가 구체적인 enum 대신 `ErrorCode`에 의존하면 도메인 에러 코드가 늘어나도 공통 처리
흐름을 변경하지 않을 수 있다. 외부 코드를 명시적인 값으로 관리하면 내부 식별자와 API 계약의 변경을 분리할 수 있다.

`BusinessException`은 실패를 발생시키는 도메인과 실패를 HTTP 응답으로 변환하는 전역 예외 처리기 사이에서 에러 정보를
손실 없이 전달한다. 부모 예외에도 메시지를 설정하면 응답 변환 코드를 거치지 않는 로그와 테스트에서도 실패 이유를 확인할
수 있다.

`FieldErrorDetail`을 중첩 타입으로 두면 `ErrorResponse`에 종속된 사용 범위와 소유 관계가 이름에 드러난다. 동시에 공개
중첩 타입으로 정의하여 전역 예외 처리기가 검증 실패를 응답 값으로 변환할 수 있다. Spring 검증 객체를 응답 DTO에 직접
전달하지 않으므로 프레임워크 예외 해석 책임은 전역 예외 처리기에 남는다.

## 검토한 대안

### enum 이름을 외부 에러 코드로 사용

코드 문자열의 중복을 없앨 수 있지만 enum 이름 변경이 API 계약 변경으로 이어진다. `ErrorCode`의 기본 메서드에서
`Enum.name()`을 사용하면 모든 구현체가 enum이라는 가정도 인터페이스에 포함된다.

### Lombok 생성자만 사용하여 비즈니스 예외 구성

필드 초기화 코드는 줄어들지만 `RuntimeException`의 메시지가 설정되지 않아 일반적인 예외 로그와 `getMessage()`에서 실패
이유를 확인할 수 없다. 부모 생성자를 호출해야 하므로 생성자를 직접 작성한다.

### 입력값 검증 전용 응답 타입 분리

검증 응답의 형태를 독립적으로 표현할 수 있지만 `code`와 `message`가 중복되고 에러 종류에 따라 응답 타입을 선택해야
한다. 선택적인 `errors`만으로 두 응답을 구분할 수 있으므로 하나의 `ErrorResponse`를 사용한다.

### `FieldErrorDetail`을 최상위 타입으로 분리

다른 클래스에서 짧은 이름으로 참조할 수 있지만 현재는 `ErrorResponse` 밖에서 독립적인 의미나 재사용 요구가 없다. 필요한
시점에 분리할 수 있으므로 중첩 타입으로 소유 관계를 먼저 표현한다.

### `ErrorResponse`가 Spring 검증 오류를 직접 변환

전역 예외 처리기의 매핑 코드를 줄일 수 있지만 응답 데이터 타입이 Spring 검증 타입에 의존한다. Spring 예외 해석과 API
응답 변환은 전역 예외 처리기에 두고 `ErrorResponse`는 응답 값만 표현한다.

## 영향

### 긍정적 영향

- 새로운 도메인 에러 코드와 구체 비즈니스 예외를 공통 처리 흐름의 수정 없이 추가할 수 있다.
- Java 예외 로그와 API 응답이 같은 기본 메시지를 사용한다.
- 단일 에러 응답 타입을 유지하면서 필드 검증 실패를 표현할 수 있다.
- 중첩 타입으로 필드 에러의 제한된 사용 범위와 소유 관계를 드러낼 수 있다.

### 부정적 영향과 위험

- enum 이름과 외부 에러 코드를 각각 작성하므로 두 값이 불필요하게 달라질 수 있다.
- 도메인마다 에러 코드 enum과 구체 비즈니스 예외 타입이 추가된다.
- 다른 클래스에서 필드 에러 타입을 참조할 때 `ErrorResponse.FieldErrorDetail`이라는 이름을 사용해야 한다.

## 미확정 사항

없음.

## 후속 작업

- `GlobalExceptionHandler`에서 비즈니스 예외, 입력값 검증 실패, 읽을 수 없는 요청과 예상하지 못한 예외를 변환한다.
- 대표 비즈니스 에러와 입력값 검증 에러가 약속한 HTTP 상태 및 응답 본문으로 반환되는지 검증한다.
