# 0070. 과제 제출의 과제 행 잠금 대기를 3초로 제한한다

- 날짜: 2026-11-26
- 관련 이슈: 없음 (측정 기록 "과제 제출의 잠금 대기 상한 재현")
- 관련 결정: [ADR-0054](0054-separate-upload-verification-from-database-transactions.md)의 업로드 완료 잠금 대기 3초,
  [ADR-0065](0065-disable-open-session-in-view.md)의 OSIV 끄기,
  [ADR-0031](0031-run-postgresql-specific-tests-with-testcontainers.md)의 PostgreSQL 전용 테스트

## 배경

과제 제출(`AssignmentSubmissionService.submit`)은 한 트랜잭션에서 잠금을 네 번 잡는다.
스터디원 `users` 공유 잠금, 과제 행 쓰기 잠금, 내 제출 행 쓰기 잠금, 새 첨부 파일 쓰기 잠금 순서다.
어느 잠금에도 대기 상한이 없었다.

로컬 재현에서 다른 트랜잭션이 과제 행을 8초 쥐고 있으면 제출도 8초를 그대로 기다렸다.
기다리는 동안 요청 스레드와 DB 연결이 함께 묶였다. 같은 과제에 6건이 동시에 제출하자 풀(테스트 5개)이 다 차서,
잠금과 상관없는 다른 과제의 조회도 6.6초를 기다렸다.

업로드 완료는 이미 `SET LOCAL lock_timeout = '3s'`로 파일 잠금 대기를 3초로 제한하고,
넘으면 `503 FILE_UPLOAD_BUSY`를 준다. 제출에도 같은 상한이 필요했다.

## 결정

- 제출 전용 과제 행 조회 `AssignmentRepository.findByIdAndStudyIdForSubmit`를 두고,
  이 조회에만 JPA 표준 힌트 `jakarta.persistence.lock.timeout = 3000`을 붙인다.
  과제 수정·삭제, 댓글, 제출 수정(`updateSubmission`)이 쓰는 기존 `findByIdAndStudyIdForUpdate`는 바꾸지 않는다.
- 값은 업로드 완료와 같은 3초로 시작한다. 측정에서 정상 제출의 과제 잠금 보유 시간은 2~9ms(첨부 0~10개),
  리더 50명 같은 극단 설정에서도 36ms였다. 3초는 정상 경합을 실패로 만들지 않을 만큼 크고,
  풀이 오래 막히지 않을 만큼 작은 값으로 본다. 운영 잠금 보유 시간을 잰 값은 아니다.
- 대기가 3초를 넘으면 서비스가 `PessimisticLockingFailureException`을 잡아
  `503 ASSIGNMENT_SUBMISSION_BUSY`("다른 요청을 처리하는 중이에요. 잠시 후 다시 시도해 주세요.")로 바꾼다.
  트랜잭션은 롤백되므로 제출 내용과 최초 제출 알림은 남지 않는다. `Retry-After` 헤더는 주지 않는다.
- 적용 범위는 제출 POST(최초 제출과 재제출)뿐이다.

PostgreSQL에서 Hibernate 7은 이 힌트를 아래 SQL로 바꿔 보낸다.
힌트가 없는 다음 조회 전에 값을 되돌리므로 상한은 이 조회 하나에만 걸린다.

```sql
select current_setting('lock_timeout', true)
set local lock_timeout = 3000
select ... from assignments ... for no key update
set local lock_timeout = 0   -- 다음 잠금 조회 전에 되돌림
```

## 선택 이유

- 측정에서 실제로 줄이 생긴 곳은 같은 과제의 동시 제출이 모이는 과제 행이다.
  상한을 이 한 곳에 걸어 피해가 가장 큰 경로를 막는다.
- 힌트 방식은 H2 테스트에서도 동작한다. H2는 `SET LOCAL lock_timeout` 문법을 몰라서,
  업로드 완료처럼 트랜잭션 첫 줄에 넣으면 제출을 부르는 H2 테스트 약 20개 클래스가 모두 깨진다.
  운영 코드에 H2 분기를 두었다가 지운 선례(#288 → #299)가 있어 분기는 넣지 않는다.
- 잠금 대기 초과는 실제 상태 충돌이 아니고 사용자가 고칠 것이 없다. 그래서 409보다
  "잠시 후 재시도"를 뜻하는 503이 맞고, 업로드 완료의 `FILE_UPLOAD_BUSY`와도 같은 모양이 된다.

## 검토한 대안

### 업로드 완료와 같은 `SET LOCAL` 한 줄 + H2 테스트를 PostgreSQL로 옮기기

운영 코드는 업로드 완료와 모양이 같고 SQL도 1개만 늘며, 네 잠금 모두에 상한이 걸린다.
대신 테스트 약 20개 클래스를 PostgreSQL로 옮겨야 하고 CI 시간이 늘어난다. 이번 범위를 넘어 선택하지 않았다.

### 네 잠금 조회 모두에 힌트 붙이기

빠짐없이 막지만 Hibernate가 조회마다 2~3문장을 더 보내 최초 제출 SQL이 약 8~9개 늘어난다.
측정상 연결 점유는 SQL 수를 따라 늘었으므로, 경합이 재현된 과제 행에만 붙였다.

### 전역 `lock_timeout`(connection-init-sql 등)

모든 경로를 덮지만 스케줄러·마이그레이션·다른 잠금 경로의 실패 처리를 함께 정해야 한다.
지금 잠금 실패를 처리하지 않는 경로가 모두 500이 되므로 선택하지 않았다.

### `GlobalExceptionHandler`에서 잠금 실패를 공통 503으로

경로별 메시지를 줄 수 없고, 댓글(409)·업로드(503)와 겹쳐 범위가 커진다.

## 영향

### 긍정적 영향

- 측정 기록과 같은 방법으로 쟀을 때(3회), 과제 행을 8초 쥔 상태의 단건 제출은 201·8.1초에서 503·3.0~3.1초로 줄었다
  (JVM 첫 실행 1회는 4.1초).
- 동시 제출 6건과 상관없는 조회 1건: 제출은 모두 8.1~8.3초 대기 뒤 201이던 것이 3.0~6.2초에 503으로 끝났다.
  상관없는 조회는 6.6~6.7초에서 1.6~1.8초로 줄었다.
- 타임아웃이 `500 INTERNAL_SERVER_ERROR` 대신 재시도 가능한 503으로 보이고, 실제 서버 오류 로그와 섞이지 않는다.

### 부정적 영향과 위험

- 나머지 세 잠금(스터디원 `users` 공유 잠금, 내 제출 행, 첨부 파일)은 여전히 상한이 없다.
  스터디원 탈퇴·방출이 `users` 행을 오래 쥐거나, 같은 사용자의 제출·수정이 겹치면 지금처럼 끝없이 기다릴 수 있다.
- 상한은 잠금 하나의 대기 시간이지 요청 전체 시간이 아니다. 풀이 비기를 기다린 시간에 3초가 더해져
  동시 제출에서는 6초에 503이 나기도 했다.
- 정상 제출의 SQL이 3개 늘었다(Hibernate가 기록한 문장 기준 12 → 15). 측정 기록의 로컬 왕복으로 약 0.4~0.5ms다.
- 같은 과제에 3초 넘게 줄이 생기면 정상 사용자도 503을 받는다. 사용자는 다시 제출하면 된다.
- 힌트 동작은 Hibernate 7의 PostgreSQL 잠금 지원에 기댄다. 버전을 올릴 때 `AssignmentSubmissionLockTimeoutApiTest`로 확인한다.

## 미확정 사항

- 나머지 세 잠금에도 상한을 걸지, 건다면 같은 힌트로 할지 테스트를 PostgreSQL로 옮기고 `SET LOCAL`로 할지
- 3초가 운영에서 적절한지(운영 잠금 보유 시간을 재지 않았다)
- 업로드 완료(503)와 댓글(409)의 잠금 실패 응답을 하나로 맞출지

## 후속 작업

- 프론트엔드가 503 `ASSIGNMENT_SUBMISSION_BUSY`를 재시도 안내로 보여 주도록 명세 `x-frontend`에 남겼다.
