# 0010. 스터디 삭제 시 하위 데이터를 서비스에서 명시적으로 삭제한다

- 날짜: 2026-08-20
- 관련 이슈: 해당 없음

## 배경

스터디 삭제 시 `Study`만 삭제하면 `StudyMember`, `Notice`, `Assignment`가 스터디를 참조하고 있어 외래 키 제약조건 위반이 발생할 수 있다.

현재 `Study` 엔티티에는 하위 엔티티를 가리키는 `@OneToMany` 연관관계가 없다. 반면 `StudyMember`, `Notice`, `Assignment`는 각각 `Study`를 `@ManyToOne`으로 참조한다. 특히 `Notice`와 `Assignment`는 `StudyMember`도 참조하므로, 하위 데이터를 삭제할 때 외래 키 의존 순서를 고려해야 한다.

스터디는 하위 데이터의 생명주기를 함께 관리하지만, JPA Cascade를 위해 `Study`에 여러 양방향 연관관계를 추가할지는 별도로 결정해야 한다.

## 결정

스터디 삭제 시 JPA Cascade를 추가하지 않고, `StudyService.deleteStudy`에서 하위 데이터를 외래 키 의존 순서에 따라 명시적으로 삭제한다.

삭제 순서는 다음과 같다.

1. `Assignment` 삭제
2. `Notice` 삭제
3. `StudyMember` 삭제
4. `Study` 삭제

각 하위 데이터 삭제는 해당 Repository의 `deleteAllByStudyId` 메서드를 사용한다. 전체 삭제 과정은 하나의 트랜잭션에서 수행한다.

향후 스터디에 종속된 엔티티가 추가되면, 해당 엔티티가 참조하는 대상이 삭제되기 전에 먼저 삭제되도록 순서를 추가한다.

## 선택 이유

서비스에서 삭제 순서를 직접 표현하면 외래 키 의존관계와 삭제 범위를 코드에서 명확하게 확인할 수 있다. 현재 `Study`가 하위 엔티티 컬렉션을 관리하지 않는 구조도 유지할 수 있으며, 삭제를 위해 엔티티 간 양방향 연관관계를 새로 추가하지 않아도 된다.

또한 `StudyMember`는 여러 스터디에서 공유되는 `User`를 참조한다. `StudyMember`의 `@ManyToOne`에 `CascadeType.REMOVE`를 설정하면 멤버 삭제가 연결된 `Study` 또는 `User` 삭제로 전파될 가능성이 있으므로 사용하지 않는다.

## 검토한 대안

### `Study`에 `@OneToMany(cascade = CascadeType.REMOVE)` 추가

`Study`에 `StudyMember`, `Notice`, `Assignment` 컬렉션을 추가하면 스터디 삭제 시 JPA가 하위 엔티티 삭제를 전파할 수 있다. 다만 양방향 연관관계와 컬렉션 상태를 함께 관리해야 하고, 하위 엔티티가 늘어날 때 `Study` 엔티티의 연관관계가 계속 확장된다. 현재 구조에 필요한 변경 범위보다 크다고 판단해 채택하지 않았다.

### 자식의 `@ManyToOne`에 `CascadeType.REMOVE` 추가

자식에서 부모로 삭제가 전파되는 방향이므로 적절하지 않다. `StudyMember`나 `Notice`를 삭제할 때 연결된 `Study`까지 삭제될 수 있어 데이터 손실 위험이 있다. `User`와 같이 여러 스터디에서 공유되는 엔티티에도 삭제가 전파될 수 있으므로 채택하지 않았다.

### 데이터베이스 외래 키에 `ON DELETE CASCADE` 설정

데이터베이스가 부모 삭제 시 자식 삭제를 처리하므로 애플리케이션의 삭제 코드를 줄일 수 있다. 하지만 삭제 동작이 애플리케이션 코드가 아닌 데이터베이스 설정에 숨겨지고, 개발·테스트·운영 데이터베이스의 스키마 설정이 일치해야 한다. 현재 프로젝트의 명시적 서비스 흐름보다 변경 영향 범위가 크다고 판단해 채택하지 않았다.

## 영향

### 긍정적 영향

- 외래 키 의존 순서가 서비스 코드에 드러난다.
- `Study` 엔티티에 새로운 양방향 연관관계를 추가하지 않아도 된다.
- 스터디 삭제 범위를 Repository 호출 단위로 확인할 수 있다.
- `User`와 같은 공유 엔티티로 삭제가 전파되는 위험을 방지한다.

### 부정적 영향과 위험

- 스터디 삭제 시 하위 엔티티마다 Repository 삭제 호출을 추가해야 한다.
- 새로운 스터디 하위 엔티티가 추가될 때 삭제 순서를 함께 갱신해야 한다.
- 삭제 순서를 잘못 지정하면 외래 키 제약조건 위반이 발생할 수 있다.
- 삭제 대상이 많아지면 Repository 호출과 삭제 성능을 별도로 검토해야 한다.

## 미확정 사항

- 현재 Repository의 파생 삭제 메서드가 생성하는 실제 SQL과 대량 데이터에서의 성능은 아직 측정하지 않았다.
- 하위 엔티티가 추가되거나 삭제 데이터가 증가하면 bulk delete 쿼리 또는 데이터베이스 cascade 도입을 재검토한다.

## 후속 작업

- 스터디 하위 엔티티를 추가할 때 `StudyService.deleteStudy`의 삭제 순서를 함께 검토한다.
- 삭제 대상 엔티티가 추가되면 외래 키 의존관계를 확인하고 관련 삭제 테스트를 보완한다.
- 삭제 성능 문제가 확인되면 bulk delete 쿼리, JPA Cascade, 데이터베이스 cascade 중 적합한 방식을 새 ADR로 결정한다.
