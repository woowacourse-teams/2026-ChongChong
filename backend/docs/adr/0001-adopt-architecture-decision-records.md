# 0001. Architecture Decision Record를 도입한다

- 날짜: 2026-08-15
- 관련 이슈: [#29](https://github.com/woowacourse-teams/2026-ChongChong/issues/29)

## 배경

기능 구현 전에 패키지 구조, 테스트 범위, 에러 규격처럼 여러 기능에 공통으로 적용되는 기준을 정해야 한다.
결론만 컨벤션으로 남기면 결정 당시의 문제와 검토한 대안을 알기 어려워 같은 논의를 반복하거나, 기존 결정의 의도를
모른 채 규칙을 변경할 수 있다.

## 결정

중요한 기술적 의사결정을 ADR로 관리한다.

- ADR은 `backend/docs/adr` 디렉터리에 저장한다.
- 파일명은 `NNNN-kebab-case-title.md` 형식을 사용하고 번호를 순서대로 부여한다.
- 각 문서에는 날짜, 관련 이슈, 배경, 결정, 선택 이유, 검토한 대안, 영향, 미확정 사항 및 후속 작업을 기록한다.
- 하나의 ADR은 독립적으로 승인하거나 대체할 수 있는 하나의 결정을 다룬다.
- 기존 결정이 바뀌면 기존 ADR의 결론을 덮어쓰지 않고 이를 대체하는 새 ADR을 작성한다. 두 문서에는 대체 관계를
  명시한다.
- ADR을 추가하거나 기존 결정을 대체할 때 [ADR 목록](README.md)을 함께 갱신한다.

## 선택 이유

결정별로 배경과 대안을 함께 보존하면 새 팀원이 현재 구조의 의도를 파악할 수 있고, 결정이 바뀌더라도 당시의 맥락을
추적할 수 있다. 문서를 주제별로 나누면 한 결정의 변경이 다른 결정의 내용에 영향을 주지 않는다.

## 검토한 대안

### 하나의 개발 컨벤션 문서로 관리

한 곳에서 모든 규칙을 읽을 수 있지만, 규칙별 변경 이유를 추적하기 어렵다. 서로 다른 시점에 변경되는 결정을
독립적으로 대체하기도 어렵다.

### 코드와 회의록만으로 관리

별도 문서 작성 비용은 없지만, 코드는 선택 결과만 보여 주고 회의록은 최종 결정과 현재 적용 중인 내용을 찾기 어렵다.

## 영향

### 긍정적 영향

- 의사결정의 배경과 대안을 코드 구현 전에 공유할 수 있다.
- 합의된 결정과 미확정 사항을 한 문서 안에서 구분할 수 있다.
- 변경된 결정의 전후 맥락을 보존할 수 있다.

### 부정적 영향과 위험

- 중요한 결정마다 문서를 작성하고 목록을 갱신하는 비용이 발생한다.
- 코드 변경과 ADR이 함께 관리되지 않으면 문서가 실제 구현과 달라질 수 있다.
