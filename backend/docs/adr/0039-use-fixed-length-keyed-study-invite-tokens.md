# 0039. 고정 길이 키 기반 스터디 초대 토큰을 사용한다

- 날짜: 2026-09-27
- 관련 이슈: [#382](https://github.com/woowacourse-teams/2026-ChongChong/issues/382)

## 배경

기존 스터디 초대 토큰은 `studyId`와 `purpose`를 담은 HS256 JWT였다. 토큰 길이가 약 112자라서 초대 링크를 공유하거나
직접 입력하기에 길었다.

초대 토큰을 데이터베이스에 저장하고 있지 않으므로, 토큰을 짧게 만들면서도 별도 저장·조회 없이 서버 시크릿만으로
유효성을 검증해야 했다. 기존 초대 토큰 사용 사례가 많지 않아 이전 JWT를 새 토큰으로 변환하거나 동시에 지원하는
호환 계층은 요구하지 않았다.

22자 토큰으로 줄인 뒤에는 `studyId`의 상위 바이트가 그대로 노출되어 작은 ID에서 `AAAA...`처럼 동일한 문자가
반복되는 문제가 확인되었다. ID 자체를 엄격히 숨기는 요구보다 링크가 알아보기 어려운 형태로 보이는 것이 주요
요구였지만, DB 없이 같은 길이를 유지하면서 이 문제를 함께 해결하기 위해 키 기반 변환을 적용한다.

이번 결정의 주요 요구사항은 다음과 같다.

- 초대 링크에서 사용할 수 있는 URL-safe 문자열이어야 한다.
- DB 저장 없이 `studyId`를 복원하고 위조를 검증해야 한다.
- 같은 스터디는 같은 토큰을 생성해야 한다.
- 토큰 길이는 22자로 고정한다.
- 기존 초대 링크 API 경로와 `token` 필드 계약은 유지한다.

## 결정

JWT 대신 고정 길이 토큰을 사용한다. 토큰 앞부분의 `studyId`는 기존 값 그대로 넣지 않고, 현재 프로젝트에 이미
존재하는 Bouncy Castle의 FF1(Format-Preserving Encryption)으로 변환한다. FF1은 입력 길이를 유지하므로 DB 없이
8바이트 ID를 다른 8바이트 값으로 바꿀 수 있다.

토큰의 원본 바이트는 다음 구조로 구성한다.

```text
[ FF1로 변환한 studyId 8바이트 ][ HMAC-SHA256 결과 앞 8바이트 ]
```

`studyId` 변환과 서명은 다음과 같이 계산한다.

```text
변환한 studyId = FF1(secret, radix=256, tweak="study_join", studyId 바이트)
서명 = HMAC-SHA256(secret, "study_join" + 변환한 studyId 바이트)
```

원본 16바이트를 패딩 없는 URL-safe Base64로 인코딩하면 22자가 된다. 토큰은 다음 규칙으로 생성·검증한다.

- `studyId`는 양수인 `Long` 값으로 8바이트에 저장한다.
- FF1 변환 결과도 8바이트로 유지하므로 토큰 길이 계산에는 영향을 주지 않는다.
- `purpose` 문자열은 토큰에 노출하지 않고 HMAC 입력과 FF1 tweak에 사용한다.
- 생성 시 변환한 `studyId`와 HMAC 결과의 앞 8바이트만 토큰에 포함한다.
- 검증 시 입력 토큰을 URL-safe Base64로 디코드한 뒤, 패딩 없이 다시 인코드한 값이 입력과 같은지 확인한다.
- 변환한 `studyId`에 대해 HMAC을 다시 계산하고, 서명이 일치한 뒤 FF1로 복호화한다.
- 서명 비교는 `MessageDigest.isEqual()`을 사용한다.
- 서명·형식·복호화 후 ID 검증에 실패하면 `INVALID_INVITE_TOKEN`으로 처리한다.
- HMAC API 오류는 `INVITE_TOKEN_SIGN_FAILED` 서버 오류로 처리한다.
- 기존 JWT 초대 토큰은 호환하지 않고 거부한다.

초대 링크 경로와 스터디 참여 요청의 `token` 필드는 변경하지 않는다. 토큰 전용 JJWT 의존성은 제거한다.

## 선택 이유

이 구조는 변환한 `studyId`를 토큰 안에 포함하므로 DB 조회 없이 복호화해 스터디를 찾을 수 있다. FF1은 토큰의
길이를 늘리지 않으면서 작은 ID에서 발생하던 반복적인 Base64 접두사를 줄인다. HMAC 서명은 토큰에 포함된 변환값이
변조되지 않았음을 확인한다. `purpose`를 HMAC 입력과 FF1 tweak에 포함해 같은 시크릿을 사용하는 다른 용도와
구분한다.

16바이트를 22자로 인코딩하는 구조는 현재 요구한 길이와 `Long` 기반 ID를 동시에 만족한다. 서명을 더 길게 만들면
위조 가능성은 낮아지지만 토큰도 길어진다. 현재 초대 링크의 사용 범위와 중요도를 기준으로 8바이트 서명, 즉 64비트
태그를 선택한다.

Bouncy Castle 의존성이 이미 프로젝트에 있어 새 의존성을 추가하지 않고 검증된 FF1 구현을 재사용할 수 있다. 직접
Feistel이나 유사한 키 기반 변환을 구현하는 것보다 암호 구현 오류와 유지보수 부담이 작다.

기존 JWT를 계속 지원하지 않으면 구현과 검증 경로가 하나로 유지된다. 기존 토큰의 사용량이 많지 않다는 제품 판단도
있으므로, 짧은 기간 동안 두 포맷을 동시에 해석하는 복잡성을 감수하지 않는다.

## 검토한 대안

### 기존 JWT를 유지한다

JWT 라이브러리가 서명 검증과 클레임 처리를 제공하고 기존 토큰과의 호환성이 유지된다. 그러나 JSON·헤더·서명으로
인한 길이가 약 112자이고, 이번 길이 요구를 해결하지 못한다. 토큰에 필요한 정보보다 표현 형식의 오버헤드가 커서
선택하지 않았다.

### 짧은 랜덤 토큰을 만들고 DB에 저장한다

`studyId`를 토큰에 노출하지 않고, 만료·폐기·사용 횟수 제한을 구현하기 쉽다. 반면 토큰 발급 시 저장하고 검증 시
조회해야 하며, 중복 방지·만료 데이터 정리·장애 시 저장소 의존성이 추가된다. 현재 DB에 초대 토큰을 저장하지 않는
운영 방식과 맞지 않아 선택하지 않았다.

### `studyId`를 그대로 넣고 HMAC만 붙인다

구현이 가장 단순하고 DB 없이 검증할 수 있다. 그러나 작은 ID에서는 Base64 인코딩 결과 앞부분에 `A`가 반복되고,
토큰에서 `studyId`를 바로 읽을 수 있다. 이번 링크 형태 문제를 해결하지 못하므로 선택하지 않았다.

### 직접 Feistel 또는 유사한 키 기반 변환을 구현한다

고정 길이와 DB 미사용 조건은 만족할 수 있지만, 암호 알고리즘을 직접 구현하면 구현 오류와 검증 부담이 커진다.
Bouncy Castle의 FF1 구현을 재사용할 수 있으므로 선택하지 않았다.

### HMAC 서명을 더 길게 사용한다

8바이트 ID와 12바이트 서명을 사용하면 약 27자, 16바이트 서명을 사용하면 32자가 된다. 현재 방식보다 위조 시도에
대한 여유가 커지지만, 사용자가 요구한 22자 조건을 충족하지 못한다. 보안 요구가 높아지거나 토큰 사용 범위가
확대되면 이 대안을 다시 검토한다.

## 영향

### 긍정적 영향

- 초대 토큰이 약 112자에서 22자로 줄어든다.
- 토큰 저장과 조회 없이 검증할 수 있다.
- 기존 초대 링크 경로와 API 요청 필드 계약을 유지한다.
- `studyId`가 토큰에 평문으로 들어가지 않아 `AAAA...`처럼 반복되는 형태가 줄어든다.
- HMAC 검증으로 변환된 `studyId`의 변조를 막는다.
- FF1이 ID 변환과 복호화를 담당하므로 직접 Feistel 구현이 필요 없다.
- JJWT 전용 의존성과 JWT 파싱·클레임 처리 복잡성을 제거한다.
- 같은 스터디는 같은 토큰을 생성하므로 별도 중복 저장이 필요하지 않다.

### 부정적 영향과 위험

- FF1과 HMAC이 같은 초대 시크릿을 사용하므로 시크릿 관리와 교체가 중요하다.
- FF1은 AES 기반이므로 현재 구현의 초대 시크릿은 16·24·32바이트 키 길이를 만족해야 한다.
- HMAC 결과 중 8바이트만 사용하므로 서명 위조 방어 강도는 64비트다. 고가치 초대나 대량 자동 요청 환경에는 충분하지
  않을 수 있다.
- 토큰에 만료 시각이나 폐기 상태가 없으므로 시크릿이 유지되는 동안 생성된 토큰은 계속 유효하다.
- 시크릿을 교체하면 기존 compact 토큰이 모두 무효화된다.
- 배포 이후 기존 JWT 초대 토큰은 새 검증기에서 사용할 수 없다.
- 같은 `studyId`와 같은 시크릿에서는 항상 같은 토큰이 생성된다.

## 미확정 사항

- 초대 토큰에 만료 시각을 도입할지 여부
- 시크릿 교체 시 기존 토큰을 유예할지 여부
- 초대 링크의 사용량과 위험도가 증가할 때 12바이트 이상 서명으로 늘릴지 여부
- 설정 단계에서 Base64 시크릿이 FF1의 키 길이를 만족하는지 명시적으로 검증할지 여부

## 후속 작업

- 새 토큰 형식에 대한 생성·검증 단위 테스트, 변환값 비노출 테스트, 스터디 참여 인수 테스트를 유지한다.
- OpenAPI의 토큰 길이·문자 집합·예시가 실제 포맷과 일치하는지 확인한다.
- 배포 후 `INVALID_INVITE_TOKEN` 증가 여부를 확인해 클라이언트의 오래된 링크 사용을 관찰한다.
- 만료·폐기·더 강한 위조 방지가 필요해지면 이 문서를 수정하지 않고 새로운 결정 문서에서 대체 방식을 결정한다.
