# 업로드 완료 처리

URL 발급 → S3 PUT → `POST /api/files/{fileId}/complete` 순서로 호출한다.
서버는 DB에 저장한 objectKey만 조회하며, 소유권과 실제 크기를 확인한 뒤 COMPLETED로 전환한다.
공통 크기 제한은 `FILE_UPLOAD_MAX_SIZE_BYTES`로 조정하며 기본값은 5MiB(5,242,880바이트)이다.
URL 발급 시 선언 크기와 완료 시 실제 크기에 같은 제한을 적용한다.

## 트랜잭션과 정리 작업

FileService는 전체 흐름을 진행하며, FileUploadTransactionService의 getOwnedFile 호출로
소유권과 상태를 읽는 짧은 읽기 트랜잭션을 실행한다. S3 조회는 트랜잭션 밖에서 수행하고,
이후 complete 호출의 짧은 쓰기 트랜잭션에서 파일 행을 잠가 상태를 다시 확인한다.
최초 조회는 엔티티 대신 값 투영으로 읽어, 요청 범위 영속성 컨텍스트에 남은 과거 상태를 재사용하지 않는다.
동시에 완료된 파일은 성공으로 처리하고, 삭제되거나 DELETE_PENDING이 된 파일은 복원하지 않는다.
향후 정리 작업도 같은 파일 행 잠금 아래 상태·첨부 여부를 재확인하고 삭제 대상으로 전환한 뒤
S3 객체를 삭제해야 한다. S3부터 삭제하면 완료 검증과의 경합을 막을 수 없다.

## 업로드 URL 재사용

새 URL은 `If-None-Match: *` 헤더를 서명에 포함한다. 클라이언트는 PUT 시 해당 헤더를 보내야 하며,
버킷 CORS에서도 이 헤더를 허용해야 한다. 기존 키의 객체를 덮어쓰는 PUT은 거부되므로 완료 후
검증한 파일이 같은 업로드 URL로 교체되는 것을 막는다.
근거: [AWS 조건부 쓰기](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html).

배포 전 발급된 URL에는 이 조건이 없다. 완료 API를 클라이언트에 연결하기 전 기존 URL의 최대
유효기간이 지나도록 기다려야 한다. S3 관리 권한으로 직접 변경·삭제하는 작업은 이 보장 밖이다.
삭제된 키에 만료 전 URL로 다시 업로드하는 경우에는 고아 정리가 필요하다.

## 검증 및 후속 연결

로컬 HTTP 테스트는 S3 조회만 대체하고 실제 서버·DB에서 인증, 검증, 상태 전환과 동시 요청을 실행한다.
실제 S3의 IAM, 조건부 PUT 거부 및 CORS 동작은 배포 환경에서 별도로 확인한다.
공지 첨부의 기존 PENDING 검증 경로와 과제·제출물의 COMPLETED 파일 연결은 각 도메인 작업에서 진행한다.
