# 무중단 배포와 롤백

관련 이슈: [#530 백엔드 무중단 배포 도입](https://github.com/woowacourse-teams/2026-ChongChong/issues/530).

## 왜 필요했는가

기존 단일 서버 배포는 백엔드를 교체하는 동안 요청을 처리하지 못했다. 운영 중에도 요청을 계속 처리하고, 배포에 문제가 생기면 직전 버전으로 돌아갈 수 있도록 edge Nginx와 백엔드 A/B 전환을 도입했다.

## 수행 과정과 결정

2026-10-29 prod의 기존 배포 산출물로 검증했다. 외부 노트북에서 공개 HTTPS 주소에 연속 요청을 보내면서 **B → 직전 버전 A 롤백 → 현재 운영 버전 B 재배포** 순서로 실행했다. 실험 종료 후에는 시작 당시 운영 버전을 유지했다.

- A: `3741e37f51d498f7b30e86154b5cad7ab8633e9d`
- B: `39a7fb50c034b06a4f340211cf1c7b7e428db06e`
- [두 버전 비교](https://github.com/woowacourse-teams/2026-ChongChong/compare/3741e37f51d498f7b30e86154b5cad7ab8633e9d...39a7fb50c034b06a4f340211cf1c7b7e428db06e): 최종 차이에 백엔드·DB 변경이 없어 호환성 위험을 줄일 수 있었다. 앱 설정 원본도 마지막 성공 배포 사본과 같음을 확인했다.
- [설계와 전환 절차](edge-deployment.md): readiness 통과 후 Nginx를 reload하고 실제 HTTPS 응답 대상을 검증한다. 이전 서버는 기존 요청 처리와 롤백을 위해 유지한다.
- 이번에는 CodePipeline을 새로 실행하지 않고 **prod에 설치된 배포 진입점**을 직접 실행했다. CI·빌드 전체의 재검증 결과는 아니다.

## 완료 조건 1: prod 배포 중 실패 요청 수와 끊긴 시간

| 측정 범위 | 요청 수 | 실패 수 | 관측 중단 |
| --- | --- | --- | --- |
| 전체: 15:12:07.688~15:15:08.019 KST | 868 | 0 | 0초 |
| 재배포 시작~성공 확인 | 212 | 0 | 0초 |
| 롤백 시작~완료 | 13 | 0 | 0초 |

전체 측정은 약 180.331초이며, 실제 요청 시작 간격은 평균 0.208초·최대 0.351초였다. 구간별 요청 수는 해당 구간에 시작한 요청으로 집계했다. [구간별 집계와 B → A → B 전환 기록](../evidence/prod-2026-10-29/operation-summary.json)에서 확인할 수 있다. 요청 ID 868개가 중복·누락 없이 기록됐다.

측정 대상은 `https://origin.chongchong.kr/actuator/health`다. 요청 사이에 0.2초를 두고 이전 요청 완료와 무관하게 다음 요청을 시작했다. 실제 간격에는 로컬 프로세스 실행 오버헤드가 포함된다. 요청 제한 시간은 2초이며, 재시도 없이 HTTP 200과 JSON `status=UP`을 모두 만족해야 성공으로 판정했다. 시각은 Unix epoch로 저장했다.

관측 중단 시간은 연속 실패 구간에서 첫 실패 요청 시작부터 다음 성공 요청 시작까지로 정의한다. 실패가 없으면 관측 중단은 0초다. 샘플 사이의 짧은 장애나 로그인·과제 제출 등 실제 업무 API의 성공까지 보장하는 결과는 아니다.

원본: [요청별 로그](../evidence/prod-2026-10-29/requests.jsonl), [전체 집계](../evidence/prod-2026-10-29/summary.json), [측정 설정](../evidence/prod-2026-10-29/settings.txt), [측정 스크립트](../scripts/measure-availability.sh).

측정 도구는 Bash 문법 검사, 정상 HTTPS 3건의 성공 판정, 연결 거절 3건의 실패 판정을 확인했다. 기록 누락 검사를 추가한 뒤에도 연결 거절 2건을 모두 실패로 집계했다. 이번 측정은 최대 1,500건으로 시작하고 후속 관측을 마친 뒤 출력 폴더의 `stop` 파일로 중지했다.

## 완료 조건 2: 직전 버전 롤백 절차와 실제 실행 기록

prod edge에 접속해 이전 서버가 정상인지 확인한 후 실행한다. 다음 배포가 이전 슬롯을 덮어쓰기 전에 수행해야 한다.

```bash
sudo bash /opt/chongchong/deploy/scripts/edge/edge-rollback.sh
```

현재 prod 산출물과 저장소는 `scripts/edge/` 경로를 사용한다. 실행 전 서버에 설치된 경로를 확인한다. 실행 로그에 시작·종료 시각과 종료 코드를 남기고, 외부 `X-Deploy-Backend`와 서버의 이미지 태그로 복구 대상을 확인한다.

| 항목 | 실제 기록 (KST) |
| --- | --- |
| 롤백 | B `39a7fb5` → A `3741e37` |
| 시작 | 2026-10-29 15:12:47.113 |
| 완료 | 2026-10-29 15:12:49.719 |
| 소요 | 약 2.606초 |
| 결과 | 종료 코드 0, HTTPS 대상 A 확인 |
| 현재 버전 재배포 시작 | 2026-10-29 15:13:08.335 |
| 재배포 성공 확인 | 2026-10-29 15:13:52.355 |
| 최종 상태 | B `39a7fb5` 활성, A/B readiness 모두 UP |

근거: [롤백 실행 로그](../evidence/prod-2026-10-29/rollback.log), [재배포 실행 로그](../evidence/prod-2026-10-29/deployment.log), [최종 버전·상태](../evidence/prod-2026-10-29/final-state.log). 원본 시각은 UTC다. 재배포는 성공 메시지를 확인한 뒤 별도 조회한 시각을 기록했으며, 정확한 스크립트 종료 시각은 수집하지 못했다. 배포 구간 집계에는 이 성공 확인 시각까지 포함한다.

배포 중 로그의 내부 readiness 연결 실패는 아직 기동 중인 비활성 B를 검사한 결과다. 공개 HTTPS 요청의 실패와 구분한다.

## 배운 점

새 서버를 실행하는 것과 사용자 요청을 받을 준비가 되는 것은 다르다. 준비될 때까지 기존 서버가 요청을 처리하고, 전환 후에도 이전 서버를 남겨 두어야 요청 처리와 빠른 롤백이 가능하다. 또한 서버 내부 상태 검사와 외부 요청 측정을 함께 남겨야 실제로 관측한 범위를 설명할 수 있다.
