# 무중단 배포와 롤백

기존 배포는 실행 중인 백엔드를 교체하는 동안 요청을 처리하지 못했다. 이를 줄이기 위해 백엔드 두 대를 두고, 새 버전이 준비되면 Nginx가 요청을 보내는 서버를 바꾸도록 구성했다. 2026-10-29 prod에서 롤백과 재배포를 진행하며 외부 요청 868건을 보냈고, 실패한 요청은 없었다.

관련 이슈는 [#530 백엔드 무중단 배포 도입](https://github.com/woowacourse-teams/2026-ChongChong/issues/530)이다. 제출 조건의 근거는 아래 두 절에서 확인할 수 있다.

- [완료 조건 1: 배포 중 실패 요청 수와 끊긴 시간](#완료-조건-1-배포-중-실패-요청-수와-끊긴-시간)
- [완료 조건 2: 직전 버전으로 되돌린 절차와 시각](#완료-조건-2-직전-버전으로-되돌린-절차와-시각)

## 왜 지금 필요했는가

운영 중에는 배포하는 동안에도 사용자가 서비스를 이용한다. 새 서버를 실행하자마자 요청을 보내면 앱이 아직 준비되지 않아 실패할 수 있다. 그래서 요청을 받는 edge 서버의 Nginx가 기존 백엔드로 계속 요청을 보내도록 하고, 새 백엔드의 준비 상태를 확인하는 readiness 검사를 통과한 뒤 대상을 바꾼다.

전환 직후에도 이전 백엔드를 남긴다. 이미 시작한 요청을 마무리하고, 새 버전에 문제가 생기면 이미지를 다시 설치하지 않고 요청 대상만 되돌리기 위해서다. 대신 두 버전이 동시에 실행되므로 DB와 앱 설정이 양쪽에서 동작해야 한다. 구성과 명령은 [A/B 배포 절차](edge-deployment.md)에 정리되어 있다.

## 어떤 순서로 확인했는가

검증을 시작할 때 B 서버는 현재 운영 버전 `39a7fb5`, A 서버는 직전 버전 `3741e37`을 실행하고 있었다. [두 버전의 최종 차이](https://github.com/woowacourse-teams/2026-ChongChong/compare/3741e37f51d498f7b30e86154b5cad7ab8633e9d...39a7fb50c034b06a4f340211cf1c7b7e428db06e)에는 백엔드·DB 변경이 없었고, 앱 설정 원본도 마지막 성공 배포 때와 같았다.

외부 노트북에서 요청을 계속 보내면서 B에서 A로 롤백했다. 이어서 현재 운영 버전을 B에 다시 배포하고 요청 대상을 B로 돌렸다. 검증이 끝난 뒤에는 시작 당시 운영 버전이 요청을 처리하도록 했다.

이번에는 prod에 설치된 배포 스크립트를 직접 실행했다. CodePipeline과 빌드를 포함한 CI/CD 전체를 다시 실행한 결과는 아니다.

## 완료 조건 1: 배포 중 실패 요청 수와 끊긴 시간

| 측정 구간 | 요청 수 | 실패 수 | 관측한 중단 시간 |
| --- | --- | --- | --- |
| 전체: 15:12:07.688~15:15:08.019 KST | 868 | 0 | 0초 |
| 재배포 시작~성공 확인 | 212 | 0 | 0초 |
| 롤백 시작~완료 | 13 | 0 | 0초 |

약 3분 동안 공개 주소 `https://origin.chongchong.kr/actuator/health`로 요청을 보냈다. 이전 요청이 끝나지 않아도 다음 요청을 시작했으며, 실제 요청 간격은 평균 0.208초·최대 0.351초였다. 요청당 제한 시간은 2초로 두고 재시도하지 않았다. HTTP 200과 응답 본문의 `status=UP`을 모두 만족해야 성공으로 집계했다.

중단 시간은 연속으로 실패한 첫 요청의 시작부터 다음 성공 요청의 시작까지로 정했다. 이번에는 실패가 없어 **관측한 중단 시간이 0초**였다. 요청 사이에 생긴 짧은 장애나 로그인·과제 제출의 성공까지 확인했다는 의미는 아니다.

원본은 [요청별 로그](../evidence/prod-2026-10-29/requests.jsonl), [전체 집계](../evidence/prod-2026-10-29/summary.json), [구간별 집계](../evidence/prod-2026-10-29/operation-summary.json)에 남겼다. 요청 ID 868개에 중복·누락이 없음을 확인했고, 구간별 수치는 그 구간에 시작한 요청을 집계했다.

측정에 사용한 [스크립트](../scripts/measure-availability.sh)와 [설정](../evidence/prod-2026-10-29/settings.txt)도 함께 남겼다. 스크립트는 문법 검사와 정상 응답·연결 거절 판정 확인을 거쳤다. 최대 1,500건으로 실행한 뒤 배포 후 관측을 마쳤을 때 출력 폴더에 `stop` 파일을 만들어 종료했다.

## 완료 조건 2: 직전 버전으로 되돌린 절차와 시각

prod edge에서 이전 백엔드가 정상인지 확인한 뒤 아래 명령을 실행했다. 이 명령은 이전 백엔드의 준비 상태를 검사하고 Nginx의 요청 대상을 되돌린다. 다음 배포가 이전 백엔드를 새 버전으로 교체하기 전에 실행해야 한다.

```bash
sudo bash /opt/chongchong/deploy/scripts/edge/edge-rollback.sh
```

시작·완료 시각과 종료 코드를 로그로 남겼다. 외부 응답의 `X-Deploy-Backend` 헤더로 요청을 처리한 서버를 확인하고, 그 서버의 이미지 태그로 직전 버전인지 확인했다.

| 항목 | 실제 기록 (2026-10-29, KST) |
| --- | --- |
| 롤백 대상 | B `39a7fb5` → A `3741e37` |
| 롤백 시작 | 15:12:47.113 |
| 롤백 완료 | 15:12:49.719 — 약 2.606초 소요 |
| 롤백 결과 | 종료 코드 0, 외부 응답 대상 A 확인 |
| 현재 버전 재배포 시작 | 15:13:08.335 |
| 재배포 성공 확인 | 15:13:52.355 |
| 검증 종료 시 상태 | B `39a7fb5`가 요청 처리, A/B 모두 준비 상태 UP |

근거는 [롤백 로그](../evidence/prod-2026-10-29/rollback.log), [재배포 로그](../evidence/prod-2026-10-29/deployment.log), [최종 버전과 상태](../evidence/prod-2026-10-29/final-state.log)에 있다. 원본 로그의 시각은 UTC다. 재배포는 정확한 스크립트 종료 시각을 수집하지 못해, 성공 메시지 이후 상태를 다시 확인한 시각을 기록했다. 재배포 구간의 요청 수도 이 시각까지 포함한다.

재배포 로그에는 B가 기동하는 동안 내부 readiness 연결에 실패한 기록이 있다. 이때 외부 요청은 A가 처리했으며, 외부 측정에서는 실패가 없었다.

## 배운 점

새 서버가 실행됐다고 바로 요청을 받을 수 있는 것은 아니다. 준비 검사가 끝날 때까지 기존 서버가 요청을 처리하고, 전환 후에도 진행 중인 요청과 롤백을 위해 이전 서버를 유지해야 한다. 또한 내부 준비 검사와 외부 요청은 결과가 다를 수 있으므로, 무중단 여부는 실제로 요청을 보낸 결과와 함께 설명해야 한다.

정상 배포만으로 모든 실패 상황을 확인할 수는 없다. [추가 검증 기록](deployment-failure-verification.md)에 준비·전환 실패, 긴 요청, 백그라운드 작업을 어디까지 확인했는지 정리했다.
